# MMORPG 매뉴얼

mmo의 구조, 규칙, 명령입니다. 소개는 [README.md](README.md)에, 만들 게임의 설계는 [docs/design.md](docs/design.md)에, 할 일은 [docs/backlog.md](docs/backlog.md)에 있습니다.

## 패킷 정의

- 원본은 `shared/contract/packets.proto`(proto3) 하나입니다. 서버(C#), Unity(C#), Unreal(C++)이 여기서 protoc로 생성한 코드를 씁니다.
  - 생성: 루트의 `npm run generate`가 `shared/contract/Contract.csproj`를 빌드하고, 그 빌드가 Google.Protobuf.Tools(NuGet 3.36.2)의 protoc 하나로 C#(`generated/Packets.cs`)과 C++(`generated/packets.pb.h`, `packets.pb.cc`)을 함께 만듭니다. 두 엔진 모두 MSBuild 생성을 쓰지 못하므로 생성 파일을 커밋해 서버, Unity, Unreal이 함께 씁니다. macOS용 protoc는 x86_64뿐이라 Apple Silicon에서는 Rosetta로 돕니다.
  - 버전: protoc, C# 런타임(Google.Protobuf), Unreal의 libprotobuf는 모두 36.2입니다(2026-11-09). C++ 생성 코드는 런타임과 버전이 다르면 컴파일되지 않으므로 셋을 함께 올립니다. 35.1에서 36.2로 바꿀 때 C# 생성 코드는 한 글자도 바뀌지 않았습니다.
  - Unity 조건: 프로젝트를 Unity와 같은 조건(.NET Standard 2.1, C# 9, 경고는 오류)으로 컴파일해 생성 코드가 Unity에서도 컴파일되는지 지킵니다. 생성 파일은 고치지 않고 `packets.proto`와 함께 커밋합니다.
  - 테스트: `npm run test:mmo`(`Contract.Tests`, xUnit)가 모든 패킷의 길이 구분 왕복, 패킷 번호, 아래 표의 와이어 크기를 확인합니다.
- 주고받는 것은 늘 `Packet` 하나이고, `body`(oneof)의 필드 번호가 패킷 번호입니다. 따로 번호 enum을 두지 않습니다. 기능마다 번호 범위 하나를 씁니다(1–99 세션(실패 알림 `ActionFailed` 포함), 100–199 월드, 200–299 전투, 300–399 성장과 아이템).
- 프레임은 Protobuf의 길이 구분 형식(varint 길이 + `Packet`)입니다. 받는 쪽은 길이가 상한을 넘거나 읽을 수 없는 패킷이면 `KICK_REASON_MALFORMED_PACKET`으로 끊습니다.
- 배포된 필드 번호와 enum 값은 바꾸거나 다시 쓰지 않고, 지운 필드의 번호는 `reserved`로 막습니다.
- 클라이언트는 `Login.protocol_version`에 `PROTOCOL_VERSION_CURRENT`를 싣고, 서버는 자기 값과 다르면 `LOGIN_RESULT_CODE_VERSION_MISMATCH`로 거절합니다. 필드를 더하기만 하면 모르는 쪽이 건너뛰므로 버전을 올리지 않고, 뜻이 바뀌어 옛 클라이언트를 받을 수 없을 때만 올립니다.
- 좌표 `x`, `z`는 1 m를 32칸으로 나눈 `sint32`(맵은 ±1,024 m 안), 방향 `yaw`는 한 바퀴를 256칸으로 나눈 칸 번호입니다. 높이는 보내지 않고 각자 지면에서 구합니다.
- 축과 방향: 위에서 볼 때 `+z`가 앞(북), `+x`가 오른쪽(동)입니다. `yaw` 0이 `+z`를 보고 시계 방향으로 늡니다(64가 `+x`). 서버는 방향을 전달만 하므로 두 클라이언트가 이 규약으로 맞춥니다. Unity는 `x`, `z`와 Y축 회전에 그대로 쓰고, Unreal은 `z`를 X(앞), `x`를 Y(오른쪽)에 쓰며 `yaw`는 같은 방향입니다.
- 함께 쓰는 수(1 m의 칸 수, 맵 반 너비, yaw 칸 수, 초당 틱 수, 최대 속도, Ping 간격, 무응답 시간 제한, 계정의 캐릭터 수)는 `packets.proto`의 `Constant` enum 값이 원본입니다. Protobuf에는 상수가 없어서 enum 값으로 두고, C#과 C++이 함께 생성됩니다. `shared/contract/Units.cs`는 그 값에 C#에서 쓰기 좋은 형으로 이름만 붙입니다. 패킷의 형식에 묶인 수와 서버가 검증하고 클라이언트의 화면도 쓰는 수는 여기에, 밸런스의 수(전투 상태 시간, 회복, 치명타 등)는 기획 데이터의 `Constants` 테이블에 둡니다.
- 끊긴 연결: 클라이언트는 5초마다 `Ping`을 보내고 서버는 그 틱에 `Pong`으로 답합니다. `Pong`과 `EnterWorldResult`에는 서버의 지금 틱 번호(`EntityMoves.tick`과 같은 수)가 실려, 주변에서 아무도 움직이지 않아도 클라이언트가 서버 시계를 맞춥니다. 어느 쪽이든 15초 동안 아무것도 받지 못하면 연결이 죽었다고 보고 끊습니다(서버는 `KICK_REASON_IDLE_TIMEOUT`). TCP는 망이 바뀐 휴대폰이나 멈춘 앱의 끊김을 몇 분 동안 알려 주지 않기 때문입니다. `Ping` 프레임은 3바이트이고 TCP/IP 머리 52바이트를 더해 연결 하나에 약 11 B/s(1,000명에 11 KB/s)이며, `Pong`은 그 틱의 버퍼에 함께 실립니다.
- 위치 되돌림: 서버는 `Move`를 거절하면 `ack`를 1 올린 `PositionReset`을 보내고, 그 `ack`를 실은 `Move`가 올 때까지 옛 `ack`의 `Move`를 버립니다. 되돌림을 받기 전에 보낸 `Move`가 다시 거절되어 되돌림이 이어지지 않게 하려는 것입니다.
- 서버는 한 틱 동안 한 연결로 보낼 패킷을 한 버퍼에 이어 쓰고 한 번에 보냅니다. TCP/IP 머리(약 52바이트)가 패킷마다가 아니라 틱마다 붙습니다.

### 형식을 고른 근거 (2026-11-06)

기준은 보이는 범위에서 움직이는 개체 50명, 20Hz, 틱마다 한 번 보내고 TCP/IP 머리 52바이트입니다. `EntityMoves`의 개체 하나(예: id 1234, x 123.4 m, z −512.5 m, yaw 200°)의 크기와 그 부하가 늘 이어질 때의 송신량입니다. Protobuf 줄은 `Contract.Tests`가 잰 값(개체 하나 15바이트, 50명을 담은 프레임 760바이트)입니다.

| 형식 | 개체 하나 | 클라이언트당 송신 | 동접 1,000명의 월 송신 비용(AWS $0.09/GB) | Hostinger KVM 4(월 16 TB)로 버티는 동접 |
| --- | --- | --- | --- | --- |
| 직접 만든 고정 크기(지운 안) | 9B | 10,240 B/s | 약 $2,400 | 약 590명 |
| MessagePack | 12B | 13,220 B/s | 약 $3,100 | 약 460명 |
| **Protobuf** | 15B | 16,240 B/s | 약 $3,800 | 약 375명 |

Protobuf의 15B는 원소 태그·길이 2 + `id` 3 + `x` 3 + `z` 4 + `yaw` 3바이트이고(태그 1바이트 + varint, 좌표는 zigzag), 프레임은 길이 2 + `Packet`의 태그·길이 4 + `tick` 4 + 개체 50 × 15입니다. MessagePack은 같은 값을 인코딩해 잰 값이고, 직접 만든 형식은 고정 크기의 합입니다. 서버 뼈대로 잰 실제 값은 [부하 측정](#부하-측정-2026-11-06)에 있습니다.

Protobuf를 고른 이유는 언어 중립 표준 정의 하나에서 protoc가 C#과 C++(Unreal)을 만들어 주고, 필드를 더해도 옛 쪽이 건너뛰어 버전을 맞추기 쉽고, 직접 만든 정의 문법과 생성기를 유지하지 않아도 되기 때문입니다. 대가는 개체 하나에 6바이트(송신 +58%)입니다. 이 결정으로 직접 만든 형식(`.def` 문법과 `tools/contract-tool`)은 지웠습니다.

## 기획 데이터

- 원본은 `data/`의 xlsx(테이블마다 하나, LFS)이고, 열은 [설계의 데이터 테이블](docs/design.md#데이터-테이블)이 원본입니다. 테이블은 그것을 쓰는 backlog 항목이 만듭니다. 지금은 `Enums`(`ZoneKind`, `MonsterKind`), `Constants`(키-값. 필드의 크기 600 m, 전투 상태 시간 5,000 ms, 회복 5%·전투 상태 1%, 치명타 5%·1.5배, 플레이어의 반지름 0.34 m, "닿을 수 없음" 5,000 ms, 길을 다시 찾는 대상의 이동 거리 3 m, 복귀의 길찾기 범위에 더하는 거리 4 m, 복귀 중의 회복 20%, 배회에서 서 있는 시간 3,000–6,000 ms, 부활할 때의 체력 30%, 죽은 몬스터가 남는 시간 3,000 ms), `Zones`(구역 6줄), `MapObjectKinds`(9줄), `Classes`(2줄: 기사 근접 2 m, 마법사 12 m와 발사체 20 m/s. 공격 간격과 발사체 속도는 72가 맞출 자리 값이고, 처음 상태의 열은 그 표를 만드는 항목 26, 32, 34, 94가 `ref`와 함께 더함), `Levels`(60줄: 직업 2 × 레벨 1–30. `id`는 직업 × 100 + 레벨이고 서버는 (직업, 레벨)로 찾음. 기사는 체력과 방어력이, 마법사는 마나와 공격력이 높은 자리 값을 72가 맞춤), `Monsters`(일반 9종: 사냥터 1은 비선공 3, 사냥터 2는 비선공 2와 원거리 선공 1, 사냥터 3은 비선공 1과 선공 2. 이름은 `Strings`의 키. 수치는 72가 맞출 자리 값이고, 쓰는 스킬과 드롭 묶음의 열은 그 표를 만드는 43, 33이 `ref`와 함께 더함), `Spawns`(40줄: 사냥터마다 12무리 60마리, 채집지에 사냥터 1의 비선공 한 종 4무리. 흩는 반경 5 m, 배회 반경 6 m, 다시 나오는 시간 30초)가 있습니다.
- 생성: 루트의 `npm run generate -- mmo`가 data-tool의 proto 출력([data-tool](../tools/data-tool/README.md#protobuf-출력))으로 `shared/data/proto/`(테이블마다 `.proto`), `shared/data/files/`(Protobuf 바이너리와 `data.hash`)를 내고, `shared/data/Data.csproj`의 `GenerateData`가 패킷과 같은 protoc 36.2로 `shared/data/generated/`에 C#과 C++을 만듭니다. 생성물은 커밋하고 `--check`가 원본과 어긋나지 않게 지킵니다. `Data.csproj`는 `Contract.csproj`처럼 Unity와 같은 조건(.NET Standard 2.1, C# 9)으로 컴파일합니다. 테이블이 없으면 `files/data.hash`만 생깁니다.
- 고른 근거: 서버(C#), Unreal(C++), Unity(C#)에 패킷 때문에 이미 있는 Protobuf 런타임으로 읽어 라이브러리를 더하지 않고, 타입이 있는 로더는 protoc가 만듭니다. 키우기의 MessagePack은 C#과 C++에 읽는 라이브러리를 더해야 해서 쓰지 않습니다.
- 데이터 해시: `data.hash`는 `files/`의 다른 파일을 이름 순으로 이은 SHA-256의 앞 8바이트(16진수 16자)입니다. 클라이언트가 `Login.data_hash`(`fixed64`, 태그까지 9바이트)에 실어 보내고, 서버의 것과 다르면 `LOGIN_RESULT_CODE_DATA_MISMATCH`로 거절합니다. 프로토콜 버전은 패킷만 보므로, 데이터만 바뀐 배포에서 옛 클라이언트가 틀린 수치와 옛 벽을 보이는 것을 이것이 막습니다.
- 시간: 데이터의 밀리초는 `Units.TicksFromMilliseconds`(C#, `shared/contract/Units.cs`)로 틱 수로 올림합니다(0 ms는 0틱, 1–50 ms는 1틱). 밀리초 열을 읽는 곳은 모두 이것을 씁니다.
- 맵: 원본은 `data/MapObjectKinds.xlsx`(종류마다 가로·세로, 막는지, 카메라를 막는지, 메시의 키)와 `data/MapObjects.tsv`(줄마다 종류, 위치 x·z(m), 방향 0·90·180·270도. 위치는 돌린 뒤의 작은 모서리)입니다. 맵 생성기 `tools/map/map.mjs`가 `npm run generate -- mmo`에서 data-tool 다음에 돌아, 막는 종류가 차지하는 칸을 1 m 격자에 펴서 `files/MapGrid.bytes`(`MapGrid` 메시지: 가로, 세로, 원점, 칸마다 막힘 1바이트. 가로·세로·원점은 `Constants`의 필드의 크기를 따름), 두 엔진의 에디터 도구가 읽을 목록 `files/Map.tsv`, 미리 보기 `preview/Map.svg`(해시에 들지 않음)를 내고 데이터 해시를 다시 구합니다. 게임의 테이블과 규칙을 아는 코드라 data-tool에 두지 않고 data-tool의 `readTables`·`dataHash`를 씁니다. 종류가 없거나 방향이 직각이 아니거나 필드 밖으로 나가거나, 마을의 부활 지점·무법자의 부활 지점이 막힌 칸 위에 있거나 무법자의 부활 지점이 마을의 부활 지점에서 네 방향으로 걸어서 닿지 않으면 모든 위반을 알리고 아무것도 쓰지 않습니다. `Spawns`의 무리의 자리도 막힌 칸 위가 아니고 마을의 부활 지점에서 걸어서 닿아야 하며, 몬스터 무리는 안전 지대 밖이어야 합니다(미리 보기에 보라 점과 "무리 번호·몬스터"로 그림). NPC, 채집물, 경비병의 검증은 그 테이블을 만드는 항목(37, 44, 47)이 더합니다. 테스트는 `tools/map/test/`이고 `test:mmo`가 돌리며, 커밋된 격자의 가장 바깥 칸이 모두 막힌 칸(테두리의 산)인 것도 봅니다. 지금의 배치는 마을(가운데, 울타리와 네 문), 사냥터 1(동)·2(서)·3(북), 채집지(남), 보스 자리(사냥터 3의 북쪽 끝)이고 무법자의 부활 지점은 마을 밖 (−140, −140)입니다.
- 비교 벡터: 서버와 두 클라이언트가 같은 답을 내야 하는 규칙은 서버의 테스트가 입력과 서버 구현의 답을 `shared/vectors/`의 탭으로 나눈 텍스트로 냅니다(머리에 그 벡터가 쓰는 입력 데이터, 그 아래 줄마다 입력과 답). 서버 테스트는 다시 만든 내용이 커밋된 파일과 같은지 보고 다르면 실패하며, `MMO_UPDATE_VECTORS=1`이면 파일을 고쳐 씁니다. 클라이언트의 엔진 없는 테스트가 같은 파일로 자기 구현의 답을 견줍니다. 지금은 구역(`zones.tsv`: 좌표 → 구역, 안전 지대, 격자 안)과 벽(`walls.tsv`: 글자로 그린 16 m 맵, 좌표 → 걸을 수 있는지, 두 점 → `HasLine`·`CanWalkLine`(플레이어 쪽). 정한 줄과 시드를 고정한 무작위 줄), 길찾기(`paths.tsv`: 글자로 그린 16 m 맵, 출발·도착 → 길이 있는지(플레이어 쪽, 범위는 필드 전체). 길은 같은 길이여도 다를 수 있어 클라이언트는 자기 길의 구간마다 `CanWalkLine`을 봄)가 있습니다.
- 공식: 원본은 formula-tool의 프로젝트 `data/formulas.json`이고(툴에서 열어 고치고 미리 봄), `npm run generate -- mmo`가 C# 내보내기(`tools/formula-tool/scripts/export-csharp.mjs`)로 `server/src/generated/Formulas.cs`(double로 계산하는 정적 함수)를, 같은 프로젝트의 능력치 키로 `AbilityType.cs`를 냅니다. 공식은 서버만 계산하므로 클라이언트에는 두지 않습니다. 난수는 인자로 받은 `Random`에서만 뽑습니다. 지금은 피해 하나입니다: `max(1, (공격력 × 계수 − 방어력 × 0.5) × 난수(0.9–1.1))`. 치명타의 배수와 소수 버리기는 서버의 `StatSystem.Damage`가 합니다.

## 서버

`server/src/`(.NET 10 콘솔 앱)입니다.

- **스레드**: 20Hz 틱 루프 하나만 월드(`World`)를 읽고 고칩니다. 연결마다 받기·보내기 작업이 있지만, 받기는 읽은 패킷을 큐에 넣기만 하고 보내기는 틱이 만든 버퍼를 보내기만 합니다. 그래서 잠금이 없고, 같은 ID의 두 연결도 틱 안에서 차례로 처리됩니다.
- **틱**: 큐 처리(연결, 로그인, 캐릭터 요청, `Move`, 끊김) → `World.Step`(예약한 일, 몬스터, 전투, 회복과 내 상태의 알림, 시야: 플레이어마다 지난 틱과 비교해 `EntitiesLeave` → `EntitiesEnter` → `EntityMoves`, 이동 거리 채우기, 저장) → 연결마다 이번 틱의 패킷을 한 버퍼로 보내기. 차례는 [설계의 틱의 차례](docs/design.md#틱의-차례)를 따릅니다. 전투의 사건은 시야를 보낸 뒤에 보냅니다.
- **구조**: `World`는 데이터와 시스템을 묶고 차례만 정합니다. 데이터는 `EntityTable`(개체 번호 → 개체)과 `Grid`(32 m 칸 → 개체. 시야와 원 안의 개체 찾기가 함께 씀)이고, 시스템은 `LoginSystem`(계정, 캐릭터, 월드에 들고 나기, 끊기), `MovementSystem`(이동 검증과 이동 거리), `ViewSystem`(시야), `SaveSystem`(위치 저장), `StatSystem`(능력치와 피해), `VitalsSystem`(회복과 체력·마나의 알림), `SpawnSystem`(몬스터 놓기), `AiSystem`(몬스터의 상태), `CombatSystem`(기본 공격)입니다. 시스템은 월드의 데이터를 고치는 코드만 가지고, 입력의 요청은 자기 플레이어의 상태만 고칩니다.
- **원 안의 개체**: `Grid.Query(중심, 반지름, 조건, 결과 목록)`이 원이 걸친 시야 칸(중심 ± 반지름의 사각형, 좌표 → 칸은 시야와 같은 내림)만 돌고 칸 안에서 거리의 제곱을 반지름의 제곱과 견줘, 경계 위(거리 = 반지름)를 넣습니다. 결과 목록은 먼저 비우고 부르는 쪽이 다시 써서 질의마다 할당하지 않으며, 차례는 칸(x, z의 차례)과 칸 안의 목록 차례입니다. 거리만 보므로 벽 너머의 개체도 들고, 거르는 것은 부르는 쪽이 후보마다 `FieldMap.HasLine`으로 합니다. 쓰는 곳(인식, 범위 스킬, 발사체, 보스 범위 공격, 줍기 등)은 그 항목들이 더합니다.
- **예약한 일**: `Scheduler`가 끝나는 틱에 할 일을 (끝나는 틱, 넣은 순번)이 키인 `PriorityQueue`에 두고, 틱의 둘째 차례에 "끝나는 틱 ≤ 지금 틱"인 것을 모두 꺼냅니다. 같은 틱의 일은 넣은 순서대로, 틱 번호가 건너뛰면 밀린 일이 틱과 순번의 차례대로 한 번씩 나옵니다. 일(`ScheduledJob`)은 종류, 주인 번호, 값 둘, 세대 번호만 가진 구조체라 예약마다 할당하지 않습니다. 넣을 때 주인의 그 종류의 세대 번호 칸에 서버 전체에서 한 번만 주는 번호를 쓰고(`Add(..., ref generation)`), 꺼낼 때 주인이 없거나 칸의 번호가 다르면 버립니다. 그래서 다시 넣으면 옛 일이 버려지고, 칸을 0으로 두면 취소이며, 번호를 다시 쓴 새 개체에 옛 일이 걸리지 않습니다. 세대 번호를 쓰지 않는 일(리스폰, 넘겨받기로 버리는 빼기)은 번호 0으로 넣습니다. 스킬과 공격의 결과를 내는 종류는 꺼낸 순서대로 `CombatJobs`로 옮겨 전투 차례(24)가 하고, 나머지는 꺼낸 자리에서 합니다. 종류마다의 주인 찾기, 전투 차례인지, 실행은 `World`의 `IScheduledRunner` 갈래이고, 지금은 종류가 없어 예약을 넣는 항목이 더합니다. 시간은 테이블을 읽을 때 `Units.TicksFromMilliseconds`(올림)로 바꾼 틱 수로 넣고, 예약은 저장하지 않습니다(틱 번호가 다시 뜨면 0부터). 쿨다운과 전투 상태는 예약하지 않고 쓸 때 끝나는 틱과 견줍니다.
- **지난 틱 수와 주기**: `World.Step(elapsedTicks)`의 지난 틱 수(지금은 늘 1, 틱이 밀릴 때 건너뛰는 것은 backlog 79)만큼 이동 거리가 찹니다. 주기로 하는 일(저장 60초, 통계 로그 10초)은 나머지 연산이 아니라 `Periodic`의 "다음에 할 틱 ≤ 지금 틱"으로 보아, 틱 번호가 건너뛰어도 한 번만 하고 다음 차례는 처음 위상에 둡니다.
- **로그인과 캐릭터**: 로그인 ID가 계정이고 계정마다 캐릭터를 4개(`CONSTANT_MAX_CHARACTERS`)까지 만듭니다. 세션은 로그인 전 → 캐릭터 선택 → 월드의 세 상태이고, 상태에 맞지 않는 요청은 `KICK_REASON_MALFORMED_PACKET`으로 끊습니다.
  - 로그인: 프로토콜 버전 → 데이터 해시 → ID 형식(영문 소문자·숫자·밑줄 4–16자) → 동시 접속 상한 순으로 검사하고, 실패하면 `LoginResult`를 보낸 뒤 끊습니다. 성공하면 `LoginResult`와 `CharacterList`를 보냅니다. 같은 계정이 이미 있으면 예전 연결을 `KICK_REASON_DUPLICATE_LOGIN`으로 끊고 새 연결이 이어 갑니다(상한이 가득 차도 자리를 넘겨받습니다). 연결하고 10초 안에 로그인하지 않으면 끊고, 로그인 전이든 뒤든 15초 동안 아무 패킷도 오지 않으면 `KICK_REASON_IDLE_TIMEOUT`으로 끊습니다.
  - 만들기(`CreateCharacter`): 직업은 기사·마법사, 이름은 한글·영문·숫자 2–12자이고 서버 전체에서 하나입니다(영문은 대소문자를 가리지 않음). 개수 확인과 넣기를 한 트랜잭션에서 하고, 이름은 `INSERT … ON CONFLICT (name) DO NOTHING`으로 넣어 겹치면 `NAME_TAKEN`입니다. 시작 위치는 마을의 부활 지점(`Zones`)이고, `--spawn-half-extent`를 주면 그 정사각형 안의 걸을 수 있는 무작위 자리입니다(막힌 칸이 뽑히면 100번까지 다시 뽑고, 그래도 막히면 부활 지점). 월드에 들어갈 때 저장된 자리가 막힌 칸이거나 필드 밖이면 부활 지점으로 옮기고 그 자리를 저장합니다. 성공하면 `CreateCharacterResult` 뒤에 새 `CharacterList`를 보냅니다.
  - 들어가기(`EnterWorld`): 자기 계정의 캐릭터만 들어갑니다(아니면 `NO_SUCH_CHARACTER`). 저장한 위치(아직 저장하지 않았으면 메모리의 위치)에서 새 개체 번호로 시작하고, `EnterWorldResult`에 내 개체 번호와 틱을 싣습니다. `LeaveWorld`는 월드에서 빼고(저장 대상) `CharacterList`를 다시 보내 캐릭터 선택으로 돌아갑니다.
- **이동 검증**: 최대 속도는 6 m/s입니다(`packets.proto`의 `Constant`. 서버가 검증하고 클라이언트의 화면도 쓰는 수라 데이터가 아니라 여기에 둡니다). 틱마다 최대 속도의 1.1배(클라이언트 시계 오차의 여유)만큼 이동 거리가 차오르고 1초 치까지 쌓이며, 받아들인 `Move`가 그 거리를 씁니다. TCP가 1초까지 몰아서 전한 `Move`는 받아 주고, 더 먼 `Move`, 필드 밖(아래의 `FieldMap` 격자 밖)으로 가는 `Move`, 지난 위치에서 곧게 걸을 수 없는(`CanWalkLine`, 플레이어 쪽) `Move`는 `PositionReset`으로 되돌립니다. 서버는 캐릭터를 점으로 봅니다. 선 검사는 좌표와 거리를 본 뒤에 해 패킷의 아무 좌표로 긴 선을 세지 않습니다. 클라이언트에 벽의 충돌이 들어오기 전(backlog 87)에는 막힌 칸으로 걸으면 되돌려집니다. `yaw`가 256 이상이면 `KICK_REASON_MALFORMED_PACKET`입니다.
- **개체**: 필드 위의 것은 모두 `Entity`(번호, 종류, 위치와 방향, 시야 칸)이고, 체력이 있는 것은 `Creature`(체력, 최대 체력, 죽었는지), 플레이어는 그 위의 `Player`입니다. 몬스터, NPC, 채집물, 바닥 아이템의 클래스는 그 항목이 만들고, 지금 월드에는 플레이어만 섭니다. 플레이어가 아닌 개체는 `World.AddEntity`·`RemoveEntity`로 넣고 뺍니다. `EntityEnter`는 개체가 스스로 채우고(`Fill`), 그 종류가 쓰지 않는 필드는 기본값이라 와이어에 실리지 않습니다(NPC는 10바이트).
- **개체 번호**: 번호 공간은 하나이고 `EntityTable`이 규칙을 지킵니다. 몬스터와 채집물의 놓인 점은 서버가 뜰 때 플레이어보다 먼저 번호를 받아(`ReservePlacedId`) 다시 나올 때도 그 번호를 쓰고, 바닥 아이템은 사라진 지 10초(200틱)가 지난 번호를 다시 쓰고(`NextGroundItemId`), 플레이어의 번호는 다시 쓰지 않습니다. 번호가 작아야 varint가 짧습니다.
- **필드와 구역**: `FieldMap`이 필드(`Constants`의 크기, 한 변 600 m, −300 m 이상 300 m 미만)를 1 m 칸의 배열 하나로 두고 칸마다 구역 번호를 가집니다. 좌표(1/32 m) → 칸은 내림이라 음수 좌표도 한 칸에 하나씩 대응하고, 정확히 +300 m는 격자 밖입니다. 뜰 때 `Zones`의 사각형(작은 모서리의 칸부터 큰 모서리 바로 앞의 칸까지)을 줄의 차례대로 펴서 겹치면 뒤 줄이 이기고, 어느 사각형에도 들지 않는 칸과 격자 밖은 구역 0(안전 지대 아님)입니다. 다른 시스템은 위치로 구역과 안전 지대를 묻고(`ZoneAt`, `IsSafe`), 개체를 구역별로 모아 두지 않습니다.
- **벽**: `FieldMap`이 맵 생성기의 격자(`files/MapGrid.bytes`, `GameData.Grid`)를 칸마다 막힘으로 읽고, 격자의 크기·원점이 필드와 다르면 서버가 뜨지 않습니다. 격자 밖도 벽입니다. 걷는 쪽(`Walker`)은 플레이어와 몬스터이고 몬스터에게는 안전 지대의 칸도 걸을 수 없습니다. `HasLine(a, b)`는 벽만, `CanWalkLine(a, b, 걷는 쪽)`은 그 걷는 쪽이 걸을 수 있는 칸만 봅니다. 선이 지나는 칸은 두 끝점의 칸(내림)과, 끝점을 뺀 선분이 닿는 닫힌 칸입니다. 그래서 모서리를 정확히 지나면 그 모서리의 네 칸을, 변 위를 따라가면 양쪽 칸을 보고(대각선으로 맞닿은 두 벽 사이를 지나지 못함), 끝점에서만 닿고 선이 들어가지 않는 칸은 보지 않으며(벽 곁의 경계까지 걸어올 수 있음), 길이가 0이면 그 칸만 봅니다. x 칸의 열마다 그 열 안의 z 범위를 정수(분모를 곱한 값)로 구해 나눗셈 없이 셉니다. 테스트의 맵은 `TestData.Map`·`WithMap`(글자: `#` 벽, `s` 안전 지대)으로 그립니다.
- **길찾기**: `PathFinder`가 `FieldMap`의 1 m 칸에서 A*로 찾습니다(몬스터가 쓰는 것은 backlog 23, 경비병 44, 소환수 95). 8방향, 대각선은 양옆 두 칸이 열려 있을 때만, 휴리스틱은 옥타일 거리(곧게 10, 대각선 14)이고, 우선순위가 같으면 비용이 큰 칸을 먼저 꺼냅니다. 걷는 쪽에게 걸을 수 있는 칸만 지나고, 살피는 범위(중심과 반지름, 1/32 m. 칸의 가운데가 원 안인 칸)를 받아 출발이나 도착이 범위 밖이거나 막혔거나 범위 안으로 이어지지 않으면 "길 없음"입니다. 찾은 칸들을 출발 → 출발 칸의 가운데 → 지난 칸들의 가운데 → 도착으로 잇고 같은 걷는 쪽의 `CanWalkLine`이 트인 가장 먼 점만 남겨, 꺾이는 점(출발은 빼고 도착을 넣음)을 냅니다. 열린 목록, 방문 표시, 비용 배열은 범위를 담는 정사각형만큼 가지고 표시 번호를 올려 다시 써 찾을 때마다 할당하지 않습니다. 시간은 `docs/performance.md`에 있습니다.
- **시야**: 맵을 32 m 칸으로 나누고 둘레 3×3칸(96 m 사방)의 개체가 보입니다. 보는 쪽은 플레이어이고 보이는 쪽은 모든 개체입니다. 내 개체는 로그인한 틱의 `EntitiesEnter`에만 들어가고 `EntityMoves`에는 들어가지 않습니다. 표시 상태(레벨, 이름 색, 입은 무기)가 바뀐 개체(`Player.SetDisplayState`)는 그 틱에 그 개체를 받은 연결과 본인에게 `EntityState`를 한 번 보내고, 같은 틱에 처음 받는 연결은 `EntityEnter`에 실린 지금 상태를 받습니다.
- **보내기**: 버퍼를 2초(40틱) 넘게 보내지 못하고 쌓이면 클라이언트가 따라오지 못하는 것으로 보고 끊습니다. 클라이언트가 보내는 패킷의 길이 상한은 256바이트입니다. 끊을 때는 남은 패킷을 보내고 FIN을 보낸 뒤 상대가 닫기를 5초까지 기다립니다.
- **저장**: 캐릭터(번호, 계정, 이름, 직업, 마지막 위치 `x`·`z`·`yaw`)를 SQLite(`Microsoft.Data.Sqlite`, `--database`, 기본은 작업 디렉터리의 `mmo.sqlite`)의 `characters` 테이블에 둡니다(`CharacterStore`). 나간 캐릭터(끊김, 강제 종료, 같은 계정의 재로그인, `LeaveWorld`)는 그 틱 끝에, 월드에 있는 캐릭터는 움직였으면 60초마다, 서버가 내려갈 때는 모두의 위치를 저장합니다. 한 번의 저장은 한 트랜잭션입니다. 틱 스레드에서 동기로 읽고 쓰므로 저장과 로그인이 엇갈리지 않고, 저장하기 전에 다시 들어오면 메모리의 위치에서 이어 갑니다. 저장이 실패하면 로그를 남기고 위치를 메모리에 둔 채 다음 틱(나간 플레이어)이나 다음 주기(접속 중인 플레이어)에 다시 씁니다. 서버 프로세스가 죽으면 마지막 주기 뒤의 이동(최대 60초)을 잃습니다. 커밋마다 fsync를 기다리지 않게 WAL과 `synchronous = NORMAL`이라, 전원이 나가면 마지막 커밋을 잃을 수 있지만 파일은 깨지지 않습니다. 스키마는 단계 목록과 `PRAGMA user_version`으로 올립니다(idle 서버와 같은 방식). 2단계가 로그인 ID별 위치를 두던 `players`를 지우고 `characters`를 만듭니다.
- **데이터**: 뜰 때 `--data`(기본은 실행 파일 옆의 `data/`)의 기획 데이터를 `GameData`로 한 번 읽어 시스템에 넘기고 바꾸지 않습니다. `Server.csproj`가 `shared/data/files/`를 빌드와 publish의 `data/`에 실으므로 릴리스 묶음에 함께 들어갑니다. 파일이 없거나 해시가 16진수 16자가 아니면 포트를 열지 않고 1로 끝납니다. 월드와 시스템의 테스트는 파일을 읽지 않고 시험용 `GameData`를 코드로 만듭니다(`test/TestData.cs`).
- **능력치**: `Creature`가 능력치(`Stats`: 최대 체력, 최대 마나, 공격력, 방어력), 체력과 마나, 전투 상태가 끝나는 틱(`CombatEndTick`. 쓸 때 지금 틱과 견주고 예약하지 않음. 미루는 것은 24, 26)을 가집니다. `StatSystem.Recalculate`가 그 직업과 레벨의 `Levels` 줄을 넣고(장비·강화·효과의 몫은 34, 35, 26이 더함), 최대값이 줄면 지금 값을 최대값으로 맞춥니다. 월드에 들어올 때 능력치를 구하고 체력과 마나를 가득 채웁니다(캐릭터 저장 38 전에는 늘 가득 참). 레벨은 31 전에는 모두 1입니다. `StatSystem.Damage(공격자, 대상, 계수)`는 공식에 `Constants`의 확률로 치명타 배수를 곱하고 소수를 버려 (피해, 치명타)를 냅니다(부르는 것은 24, 26). 난수는 월드에 주입한 `Random`이고 테스트는 씨앗을 고정합니다.
- **회복과 알림**: `VitalsSystem`이 틱의 회복 차례(예약한 일 다음, 시야 앞)에 돕니다. 20틱(1초)마다 `Periodic`으로 살아 있는 플레이어의 체력과 마나를 최대값의 5%(전투 상태면 1%, 소수는 버림)만큼 최대값까지 채우고, 피해가 아닌 까닭으로 체력이나 최대 체력이 바뀐 개체를 지난 틱의 시야에 그 개체가 든 연결마다 `EntityVitals` 하나로 모아 보낸 뒤 표시를 내립니다(자기 개체는 시야에 없어 본인은 받지 않음. 시야에 새로 드는 연결은 `EntityEnter`로 지금 체력을 받음). 틱마다 플레이어마다 능력치를 다시 구했으면 `SelfStats`를, 체력·마나·전투 상태가 끝나는 틱이 마지막으로 보낸 것과 다르면 `SelfVitals`를 본인에게만 보냅니다. 월드에 들어온 틱에는 `EnterWorldResult` 뒤에 둘 다 갑니다. 몬스터의 회복(복귀 중)은 23이 더합니다.
- **몬스터**: 서버가 뜰 때 `SpawnSystem`이 `Spawns`의 무리마다 무리의 자리(칸의 가운데)에서 흩는 반경 안이고 몬스터 쪽으로 곧게 걸어갈 수 있는 점을 수만큼 골라(주입한 `Random`, 같은 씨앗이면 같은 자리) 놓인 점(`PlacedPoint`)마다 플레이어보다 먼저 번호를 받아 `Monster`를 놓습니다. 다시 놓는 `Respawn`(가득 찬 체력, 대기, 빈 피해 표, 같은 번호)을 부르는 예약은 25가 넣습니다. `AiSystem`이 틱의 셋째 차례에 몬스터마다 봅니다.
  - 인식: 선공 몬스터는 `Periodic`(번호 % 5에서 시작해 5틱마다)으로 `Grid.Query`의 인식 범위 안에서 살아 있고 안전 지대 밖이며 선(`HasLine`)이 트인 플레이어를 피해 0으로 피해 표(`DamageTable`)에 넣습니다.
  - 대상: 피해 표는 든 차례로 플레이어마다 합을 두고, 편(`DamageTable.SideOf`. 지금은 플레이어 자신이고 42가 파티로 이음)끼리 합이 큰 쪽(같으면 먼저 든 쪽)에서 고를 수 있는 플레이어 가운데 피해가 큰 쪽을 칩니다. 죽었거나 안전 지대 안이거나 "닿을 수 없음"인 플레이어는 건너뛰되 표에 남고, 월드에서 빠진 플레이어는 표에서 뺍니다. 잡은 편은 `Killer`가 답합니다(31, 33).
  - 추적과 공격: 대상이 사거리 안이고 선이 트이면 서서 대상을 봅니다(공격 상태. 치는 것은 24). 아니면 몬스터 쪽의 걷는 선(`CanWalkLine`)이 트였으면 곧게 사거리의 0.25 m 안쪽까지, 막혔으면 놓인 점에서 추적 한계 안의 칸으로 A*를 찾아 따라가고, 대상이 길을 찾은 때의 자리에서 3 m 넘게 옮기면 다시 찾습니다. 길이 없으면 그 대상에 "닿을 수 없음"을 걸고 5초 뒤에 지우는 일을 예약합니다(`ScheduledKind.UnreachableEnd`. 세대 번호는 대상마다의 표시에 있음). 지난 틱 수만큼의 거리를 꺾이는 점을 따라 나눠 갑니다.
  - 복귀: 놓인 점에서의 직선거리가 추적 한계를 넘거나 고를 대상이 없는데 표가 비지 않았으면 표를 비우고 복귀합니다. 곧게 갈 수 없으면 놓인 점에서 "지금 거리 + 4 m" 안의 칸으로 찾은 길로, 길이 없으면 순간 이동합니다(`EntityMove.teleport`). 복귀하는 동안 1초마다 최대 체력의 20%가 차고(`EntityVitals`로 감) 인식하지 않으며, 놓인 점에 닿으면 대기입니다.
  - 배회: 대기에서 둘레 3×3 시야 칸에 플레이어가 있을 때만(`Grid.HasPlayerAround`), 놓인 점에서 배회 반경 안이고 지금 자리에서 곧게 걸어갈 수 있는 무작위 점(8번 시도)으로 걷고 닿으면 3–6초 섭니다.
  - 이동은 곧게 한 걸음마다 반올림한 다음 자리까지 걷는 선을 다시 보고, 움직였거나 방향이 바뀐 틱에 지금의 시야 규칙대로 `EntityMoves`로 갑니다(다음 꺾이는 점과 속도만 알리는 것은 54). 몬스터끼리는 겹칩니다. 몬스터 180마리와 플레이어 1명에서 틱 평균 0.14 ms였습니다(2026-11-14, Debug).
- **기본 공격**: `CombatSystem`이 틱의 넷째 차례에 돕니다.
  - `CanAttack(공격자, 대상)`: 플레이어와 몬스터 사이만 참이고, 플레이어가 안전 지대 안에 있으면 거짓입니다(안에서 밖의 몬스터를 치지 못하고, 몬스터는 안의 플레이어를 치지 못함). 플레이어 사이와 파티원은 44가 넓힙니다.
  - 요청: `AttackStart`는 대상이 있고 살아 있고 그 연결이 받은 개체(시야 집합)인지, `CanAttack`, 복귀 중인 몬스터가 아닌지를 보고 공격 상태(`Creature.AttackTarget`)를 켭니다(이미 공격 중이면 대상만 바꿈). 어긋나면 `ActionFailed`(이유 `NO_TARGET`이나 `INVALID_TARGET`, 요청 `ATTACK`)로 답하고 끊지 않습니다. `AttackStop`은 끕니다. 몬스터는 `AiSystem`의 공격 상태가 켜고 끕니다.
  - 시작: 공격 상태인 개체 가운데 다음 공격 틱이 된 것만 봅니다. 대상이 죽었거나 월드에서 빠졌으면 조용히, `CanAttack`이 거짓이 됐거나 대상인 몬스터가 복귀를 시작했으면 `ActionFailed`와 함께 끕니다. 사거리 안(중심 사이 거리)이고 선이 트였으면 `AttackSwing`을 내고 다음 공격 틱을 간격 뒤로 두며(멈춰도 남음) 공격자의 전투 상태를 5초 뒤로 미루고, 타격을 예약합니다(`ScheduledKind.Strike`, 세대 번호는 공격자의 `StrikeGeneration`이라 걸린 타격 여럿이 함께 살고, 죽으면 새 번호로 모두 버림). 타격할 틱은 시작한 틱 + 타격까지의 시간이고, 따라가는 발사체(마법사, 원거리 몬스터)는 시작한 틱의 거리 ÷ 발사체 속도(올림)를 더합니다. 0이면 같은 틱에 바로 칩니다.
  - 타격: 예약한 일이 넘긴 타격을 전투 차례가 차례대로 적용합니다. 공격자가 죽었거나 빠졌거나, 대상이 죽었거나 빠졌거나 `CanAttack`이 거짓이거나 복귀 중인 몬스터면 버립니다(사거리 밖으로 나간 대상과 공격을 멈춘 공격자의 타격은 맞음). 피해는 `StatSystem.Damage`(계수 1)이고 대상의 전투 상태를 5초 뒤로 미루며, 플레이어가 몬스터를 맞히면 그 몬스터의 피해 표에 쌓아 비선공 몬스터도 선과 상관없이 쫓습니다. 체력이 0이 되면 죽음 표시를 하고(공격 상태를 끄고 걸린 타격을 버림, 몬스터는 잡은 편 `Killer`를 기록) `Died`를 냅니다. 죽은 개체는 치지도 맞지도 회복하지도 않습니다.
  - 사건: `TickEvents`가 그 틱의 `AttackSwing`, `Damaged`, `Died`를 난 순서대로 쌓았다가 시야 차례가 들어옴·나감·움직임을 보낸 뒤 사건마다 대상 자신과, 대상 둘레 3×3 시야 칸의 플레이어 가운데 시야 집합에 대상이 든 연결에 보냅니다. 받는 연결이 받지 않은 행위자(공격자, 죽인 개체)의 번호는 0입니다.
- **죽음과 부활**: 전투 차례의 끝에서 `DeathSystem.Died`가 그 틱에 죽은 개체를 죽은 차례대로 정리합니다. 죽은 플레이어는 모든 몬스터의 피해 표에서 빠지고(몬스터는 다른 대상을 고르거나 복귀), 죽은 몬스터는 쓰러진 채 3초 동안 남았다가 사라지고(`ScheduledKind.Despawn`, 세대 번호는 몬스터의 `LifeGeneration`) 죽은 틱에서 `Spawns`의 다시 나오는 시간 뒤에 놓인 점에 같은 번호로 다시 나옵니다(`ScheduledKind.Respawn`, 주인은 놓인 점). 다시 나오는 시간이 남는 시간보다 짧으면 리스폰이 옛 몬스터를 먼저 빼고, 옛 몬스터에 걸린 예약은 새 몬스터에 실행되지 않습니다. 효과·진행 중인 일(26)과 선공 표시(44)를 떼는 것은 그 항목이 `Died`에 잇고, 쿨다운과 성향은 남깁니다. 죽은 동안에는 `Ping`, `LeaveWorld`, `Revive`, `AttackStop`(할 일 없음)만 받고, `Move`는 `PositionReset`으로 되돌리며, `AttackStart`는 `ActionFailed`(죽은 동안)로 답합니다(끊지 않음). `Revive`는 마을의 부활 지점으로 옮기고 체력을 최대의 30%로 둡니다(마나는 그대로). 보는 쪽에는 순간 이동 표시가 있는 움직임과 `Revived`가, 본인에게는 `PositionReset`, `Revived`, `SelfVitals`가 갑니다. 살아 있는 플레이어의 `Revive`는 `ActionFailed`(죽지 않았음, 부활)입니다. 캐릭터 저장(38) 전이라 죽은 채 나갔다가 들어오면 가득 찬 체력입니다. 사망 페널티는 45입니다.
- **종료**: SIGINT·SIGTERM을 받으면 모두에게 `KICK_REASON_SERVER_SHUTDOWN`을 보내고, 위치를 저장하고 내려갑니다.
- **로그**: 10초마다 플레이어 수, 평균 시야 개체 수, 틱 시간(평균·최대), 송신량, CPU, 메모리, 할당량, GC 횟수를 한 줄로 찍고, 그 아래 세 줄에 `TickProfile`이 모은 것을 찍습니다.
  - `phases`: 틱의 차례(`TickPhase`: 입력, 예약한 일, 몬스터, 전투, 회복과 알림, 시야(사건 보내기 포함), 저장, 보내기)마다 평균/최대 ms와 그 합. 입력은 `World.Receive`(`Drain`)와 다음 입력의 이동 거리 채우기, 보내기는 `Flush`(직렬화, 보내기 큐 넣기, 끊기)이고 나머지는 `World.Step`이 부르는 차례입니다. 합은 틱 시간과 같아야 합니다. 몬스터, 전투, 회복은 그 기능이 `World.Step`에 들어올 때 차례를 더합니다.
  - `timer`: 틱이 예정보다 늦게 시작한 시간(평균·최대)과 건너뛴 틱 수, 연결 가운데 가장 긴 보내기 큐(프레임 수). 예정은 지난 틱의 차례에서 한 틱 뒤이고, 더 일찍 시작한 틱이 오면 기준을 당깁니다. 한 틱 넘게 늦으면 `PeriodicTimer`가 그 사이의 차례를 버린 것이라 건너뛴 수로 셉니다.
  - `packets`: 패킷 종류별 보낸 수/바이트(길이 머리 포함)와 합. 합은 송신량과 같습니다(보내지 못하고 끊는 연결의 것까지 세어 조금 클 수 있음).
  - 50 ms(틱 하나)를 넘은 틱은 10초를 기다리지 않고 `slow tick` 한 줄을 그 틱의 차례별 시간과 함께 남깁니다. 집계는 시간을 인자로 받는 `TickProfile`이 해 시계 없이 테스트합니다.

DNS의 `mmo.dennou.cloud` A 레코드와 Hostinger 패널의 방화벽(쓴다면)은 손으로 맞춥니다.

## Unreal 클라이언트

`client-unreal/`(UE 5.8, C++)입니다. 대상은 Mac과 Android이고, 지금은 Mac에서 로그인해 캐릭터를 만들고 골라 Field 레벨을 걷고, 시야 안의 다른 플레이어가 보간되어 움직이는 데까지 있습니다.

- **시작**: 맵은 `Field`(`/Game/Maps/Field`) 하나이고 로그인 화면도 이 레벨에서 띄워 레벨을 옮기지 않습니다. `AMmoGameMode`는 컨트롤러만 정하고 폰은 처음부터 만들지 않으며, 화면은 화면 관리자가 로그인 화면부터 엽니다. 명령줄의 `-MmoServer=호스트:포트`(기본 `127.0.0.1:7777`)로 서버를 바꾸고, `-MmoLogin=아이디`가 있으면 로그인 화면이 처음 한 번 바로 로그인합니다. `-MmoEnter`를 더하면 캐릭터 선택 화면이 처음 한 번 첫 캐릭터로 들어가 클릭 없이 월드까지 갑니다(개발용). `-MmoWalkTo=x,z`(m)를 더하면 들어온 뒤 한 번 땅을 누른 것처럼 그곳까지 길을 찾아 걷습니다(눌러서 이동을 키 입력 없이 확인하는 개발용). `-MmoOpen=Settings|Confirm|Quantity|Notice`를 더하면 처음 월드에 들어간 뒤 그 화면을 엽니다(알림은 1초마다 한 줄씩. 화면 크기마다의 배치를 클릭 없이 보는 개발용).
- **에셋**: `Scripts/create_content.py`가 에디터 명령(아래 명령 표)으로 머티리얼 셋(`M_Ground`: 월드 자리로 얼룩진 풀밭에 1 m 칸의 옅은 선, `M_Sky`: 빛을 받지 않는 `IsSky` 하늘(지평선은 옅고 위는 짙은 파랑), `M_Placeholder`: 색을 컴포넌트의 커스텀 프리미티브 데이터 0–2에서 읽는 자리 표시)과 `Field` 레벨(엔진 평면 2,048 m, 해, 하늘 대기, 하늘빛, 하늘 구(엔진 구를 4,096 m로 키운 것), 지평선 색의 거리 안개. 모두 동적 조명)을 만듭니다. 모바일 렌더러는 하늘 메시가 없으면 하늘을 그리지 않아(안개색 배경) 모든 플랫폼에 같은 하늘 구를 둡니다. 하늘 구에 충돌이 있으면 그 안에서 시작하는 카메라 선이 막혀 카메라가 캐릭터 안으로 당겨지므로 충돌 프로필을 `NoCollision`으로 둡니다. 에셋은 손으로 고치지 않고 스크립트를 고쳐 다시 돌립니다(이미 있는 레벨은 열어서 액터를 비우고 다시 놓습니다). 그래서 에디터에만 PythonScriptPlugin을 켭니다. 코드가 경로로만 읽는 에셋(`/Game/Characters`, `/Game/UI`)은 레벨이 참조하지 않으므로 `DefaultGame.ini`의 `DirectoriesToAlwaysCook`에 둡니다.
- **맵의 것**: 맵에 놓인 것 하나가 `AMmoMapObject` 하나입니다. 놓을 때 읽은 종류의 줄 전체(`FMmoMapObjectKind`: 가로·세로, 막는지, 카메라를 막는지, 메시의 키)를 가지고, 자리는 차지하는 사각형의 가운데, yaw는 방향입니다. 막는 종류만 차지하는 칸의 경계 그대로인 상자(`UBoxComponent`)를 두어 폰을 막습니다. 상자의 높이는 메시의 높이이고(자리 표시는 집 4–5.5 m, 산 14 m) 캡슐을 막도록 2.5 m보다 낮게 두지 않으며, 카메라를 막는 종류(건물, 테두리의 산)의 상자만 `ECC_Camera`를 막습니다. 메시의 충돌은 끕니다. 카메라는 스프링 암의 선 충돌을 끄고, 내 캐릭터가 프레임마다 카메라가 놓일 자리(반지름 0.3 m)만 `ECC_Camera`로 보아 그 자리가 막는 것 안이면 밖으로 나올 때까지 0.5 m씩 당깁니다. 선 충돌은 건물이 캐릭터를 가리기만 해도 카메라를 코앞까지 당겼기 때문입니다(설계는 가려지는 것은 그대로 둠). 기본 거리와 각도에서 카메라는 9 m 넘게 높아 건물 안에 들 일이 없고, 테두리의 산 쪽으로 낮게 당겼을 때 당겨집니다.

- **세션과 월드**: `UMmoSession`(GameInstanceSubsystem)이 서버 주소, 로그인 ID, 월드(`MmoWorld::FWorldState`)를 가집니다. 연결의 패킷을 월드에 먼저 반영한 뒤 자기 델리게이트로 알리므로, 화면(위젯·액터)은 연결이 아니라 세션을 듣고 월드를 읽기만 합니다. `FWorldState`는 내 개체 번호, 시야 안의 개체(`EntitiesEnter`·`EntitiesLeave`·`EntityMoves`·`EntityState`. 개체마다 받은 `EntityEnter`를 그대로 `Info`에 두고 표시 상태만 `EntityState`로 고치며, 받지 않은 개체의 `EntityState`는 버림), 다음 `Move`에 실을 `ack`(`PositionReset`), 내 상태(`FSelfState`: `SelfVitals`의 체력·마나·전투 상태와 선공 표시가 끝나는 틱, `SelfStats`의 능력치)를 가집니다. 다른 개체의 체력은 `EntityVitals`와 `Damaged`가 그 개체의 `Info`(체력, 최대 체력)를, `Died`·`Revived`가 죽음 표시와 체력을 고칩니다(받지 않은 개체의 것은 버림). 내가 죽었는지는 `FSelfState.bDead`이고, 죽은 동안 컨트롤러는 이동·공격·대상 고르기의 요청과 `Move`를 만들지 않습니다(부활의 `PositionReset` 뒤에 다시 보냄). 내가 죽으면 전투 모델이 대상을 풀고 공격 중 표시를 내리되 `AttackStop`은 보내지 않습니다(서버가 이미 끝냄). 세션은 월드에 반영한 패킷을 이어 전투 모델 `FCombatState`(`World/CombatState`)에 넘깁니다: 내 대상(고르는 것은 클라이언트 안의 일), 공격 중인지와 내 첫 공격의 예측(`AttackStart`를 보낼 때 공격 동작을 미리 쌓고 그 `AttackSwing`은 다시 쌓지 않음. 공격의 `ActionFailed`가 오면 내림), 화면이 꺼내 갈 사건(공격 동작의 시작, 피해, 죽음. 받은 순서이고 공격자 번호 0이면 대상 쪽만), 따라가는 발사체(공격자의 `Classes`·`Monsters` 줄에 속도가 있으면 `AttackSwing`에서 타격까지의 시간 뒤에 공격자의 자리에서 나가 대상의 지금 자리 쪽으로 감)를 가집니다. 대상이 죽거나 나가면 풀고, 공격 중이었거나 공격 중에 대상을 바꾸면 `AttackStop`을 보냅니다. 클라이언트도 `Classes`와 `Monsters`를 읽습니다(사거리, 발사체, 몬스터의 이름과 레벨). 전투 상태인가(`InCombat`)는 어림한 서버 틱이 끝나는 틱 앞인지로 답합니다. 서버는 `EnterWorldResult`와 내 개체가 든 `EntitiesEnter`를 같은 틱에 보내는데, 화면이 아직 없어도 월드에 남습니다. 들어오고 나간 개체의 번호는 큐에 쌓이고 화면이 `TakeLeft`, `TakeEntered` 차례로 꺼내 액터를 지우고 만듭니다.
- **단위**: `World/Units.h`가 칸 ↔ 미터(미터 → 칸은 반올림), `yaw` 칸 ↔ 도(한 바퀴로 감음)를 바꿉니다. 값은 `Constant`에서 읽습니다.
- **다른 개체의 보간**: `FServerClock`이 받은 틱 번호(`EnterWorldResult`, `Pong`, `EntityMoves`)와 받은 때로 서버의 지금 틱을 어림합니다. 가장 빨리 도착한 값을 따르고, 늦게 온 값 쪽으로는 받을 때마다 2%씩만 내려가 TCP가 몰아 전해도 흔들리지 않습니다. 개체마다 `FEntityTrack`이 최근 8개의 (틱, 위치, `yaw`)를 가지고, 화면은 `RenderTick`(서버의 지금 틱 - 2)의 자리를 `Sample`로 얻습니다. 앞뒤 기록 사이는 선형으로, `yaw`는 가까운 쪽으로 돌고, 기록 밖이면 끝의 기록에 세워 앞질러 그리지 않습니다. 새 기록이 앞 기록보다 4틱 넘게 뒤면 한 틱 앞에 옛 자리를 끼워, 서 있던 개체가 출발할 때 미끄러지지 않게 합니다(한두 틱이 빠진 채 걷는 개체는 그대로 이어 그립니다). 순간 이동 표시(`EntityMove.teleport`)가 있는 움직임은 기록을 비우고 그 자리에 바로 놓습니다. `EntityEnter`에는 틱이 없어 들어온 개체의 첫 기록은 마지막으로 받은 틱에 둡니다.
- **Move 보내기**: `FMoveSender`가 프레임 시간을 모아 50 ms(서버 틱)마다, 마지막으로 보낸 위치·`yaw`·`ack`와 다를 때만 `Move`를 냅니다. 멈추면 선 자리가 한 번 더 가고 끝납니다. 간격을 빼며 세어 30 fps에서도 평균 20번/초이고, 서 있다가 움직이면 첫 프레임에 바로 보냅니다. 행동 패킷 직전의 `Flush`는 밀린 위치를 지금 보냅니다.
- **필드**: `World/FieldMap`(`MmoWorld::FFieldMap`)이 서버의 `FieldMap`과 같은 규칙으로 같은 생성물(`Constants`, `Zones`)에서 격자를 펴고, 벽(`MapGrid`)도 같은 규칙으로 읽어 걸을 수 있는지와 `HasLine`·`CanWalkLine`(플레이어 쪽뿐이라 둘이 같음)을 답합니다. 같은 답을 내는지는 비교 벡터(`shared/vectors/`의 `zones.tsv`, `walls.tsv`)로 엔진 없는 테스트가 봅니다. `World/PathFinder`(`FPathFinder`)는 서버와 같은 규칙의 A*이고 플레이어 쪽만 쓰므로 걷는 쪽과 범위를 받지 않는 대신, 한 번에 닫는 칸 수에 상한(`MaxClosedCells`, 20,000칸)을 두고 넘으면 길이 없는 것으로 봅니다. 버퍼는 필드 전체 크기(약 5.8 MB)로 한 번 만들어 다시 씁니다. 실제 맵의 두 대각선이 상한 안(약 18,300칸)에서 찾아지는 것을 엔진 없는 테스트가 봅니다. `FPathFollower`는 꺾이는 점의 목록을 받아 지금 위치에서 다음 점 쪽의 단위 방향을 주고, 점에서 0.5 m 안에 들면 다음 점으로 넘어가며 마지막 점에 닿으면 끝납니다. 이동 입력에 넣는 것은 눌러서 이동(backlog 88)이 처음 합니다. 길이 있는지는 비교 벡터 `paths.tsv`로 서버와 맞춥니다. 세션이 데이터를 읽을 때 만들어 둡니다(`UMmoSession::Field`).
- **기획 데이터**: `UMmoSession`이 시작할 때 엔진 없는 로더(`MmoData::Load`)에 파일을 이름으로 읽어 넘겨 데이터를 한 번 읽습니다. 개발 중(에디터, `-game`)에는 저장소의 생성물(`../shared/data/files`)을, 패키지에서는 `Content/Data`를 읽습니다. `package.mjs`가 패키징하는 동안만 생성물을 `Content/Data/`(커밋하지 않음)에 복사하고, `DefaultGame.ini`의 `DirectoriesToAlwaysStageAsUFS`가 쿠킹 없이 그대로 싣습니다. 읽지 못하면 오류 로그를 남기고 해시 0으로 로그인해 서버가 `DATA_MISMATCH`로 거절합니다. 엔진 없는 테스트는 커밋된 생성물을 실제로 읽습니다.
- **로그인과 캐릭터 선택**: 아이디 → `UMmoSession::LogIn` → 연결 → `Login`(`PROTOCOL_VERSION_CURRENT`, 데이터 해시) → `LoginResult`의 결과, `Kicked`의 이유, 연결 끊김, 로그아웃을 상태 줄에 한국어로 보여 줍니다. 실패 뒤 서버가 끊어도 실패 메시지를 덮지 않습니다. `VERSION_MISMATCH`와 `DATA_MISMATCH`는 다시 붙어도 같으므로 새 빌드를 받으라는 안내와 받는 곳(`UMmoSettings::ReleasesUrl`, 저장소의 릴리스 페이지)을 보이고, 다시 붙지 않습니다. 로그인 화면은 닫혀 있는 동안에도 세션을 들어, 게임 중에 끊긴 까닭이 다시 열릴 때 보입니다. 로그인하면 세션이 마지막 `CharacterList`를 가지고 캐릭터 선택 화면이 4칸에 이름과 직업을 보여 줍니다. 만들기 화면은 이름과 직업을 받아 `CreateCharacter`를 보내고 결과를 한국어로 보여 줍니다. 시작을 누르면 `EnterWorld`를 보내고, `EnterWorldResult`가 오면 월드가 내 개체 번호와 틱을 받아 HUD로 바뀝니다. 설정 창의 "캐릭터 선택으로"는 `LeaveWorld`를 보내고 월드를 비운 뒤 캐릭터 선택으로 돌아갑니다.
- **화면 관리자**: `UMmoUiManager`(`ULocalPlayerSubsystem`)가 컨트롤러가 생기면 뿌리 위젯(`UMmoUiRoot`)을 뷰포트에 올리고 로그인 화면을 엽니다. 뿌리는 아래에서 위로 이름표, HUD, 창, 팝업, 알림 층이고, 층 자체는 입력을 받지 않아 화면이 없는 곳의 터치와 클릭은 게임으로 갑니다. `Open(화면)`은 위젯 블루프린트를 비동기로 불러와 그 층의 맨 위에 올리고(이미 열려 있으면 맨 위로 옮김), 닫아도 위젯을 지우지 않고 다음에 다시 씁니다. 로그인하면 로그인 화면을 닫고 캐릭터 선택을, 월드에 들어가면 HUD를 열며, 연결이 끊기면 HUD와 창을 닫고 로그인 화면을 엽니다(게임 중에 끊겼으면 알림도). 지금 화면은 아래 목록뿐이고, 상점 등의 창은 그 항목에서 더합니다.
  - 판단: 무엇이 열렸는지, 뒤로 가기가 무엇을 닫는지, 입력을 어디로 보낼지는 엔진 없는 `MmoScreen::FScreenStack`이 정합니다. 화면마다 층, 뒤로 닫히는지, 입력(화면만·게임·창)이 정해져 있습니다. 뒤로 가기(Esc, Android 뒤로 버튼. 컨트롤러의 `Back` 액션)는 팝업 → 창 순서로 마지막에 연 것을 닫고, 닫을 것이 없고 게임 중이면 설정 창을 엽니다. 로그인 화면이 열려 있으면 입력은 화면만 받고(`FInputModeUIOnly`), 창이나 팝업이 열려 있으면 카메라는 돌지만 손 조작(WASD, 조이스틱, 땅 누르기)으로는 걷지 않고, 따라가던 경로는 이어 걷습니다(`AMmoPlayerController::SetManualMoveBlocked`. `SetIgnoreMoveInput`은 경로의 이동 입력까지 막아 쓰지 않음).
  - 초점: 게임으로 입력을 돌릴 때 초점을 게임 뷰포트로 옮깁니다(`SetAllUserFocusToGameViewport`). 입력 모드는 따로 정한 위젯이 없으면 초점을 옮기지 않아서, 로그인 화면의 글 상자에 남은 초점 때문에 Esc가 컨트롤러에 가지 않았습니다.
  - 화면: 로그인(`WBP_Login`), 캐릭터 선택(`WBP_CharacterSelect`, 창), 캐릭터 만들기(`WBP_CharacterCreate`, 팝업), HUD(`WBP_Hud`, 터치 기기에서만 가상 조이스틱 `WBP_Joystick`, 왼쪽 위에 내 체력·마나 바(지금 / 최대. 세션의 `FSelfState`를 프레임마다 읽어 바뀔 때만 고침)와 그 아래 지금 구역의 이름과 권장 레벨, 안전 지대 표시. 위 가운데에 내 대상의 정보(이름과 레벨, 체력 바), 오른쪽 아래에 터치 기기에서만 보이는 대상 고르기와 공격 버튼. 대상의 발밑에는 노란 원(자리 표시)이 놓이고, 따라가는 발사체는 보라 구(자리 표시)로 그립니다(이펙트는 27). 내가 죽으면 열린 창을 닫고 사망 화면(`WBP_Death`: 부활 버튼. 손 조작을 막고 뒤로 가기로 닫히지 않음)을 띄우며, 부활 버튼은 `Revive`를 보내고 답이 올 때까지 누를 수 없고(부활의 `ActionFailed`가 오면 다시 누를 수 있음) `Revived`가 오면 닫힙니다. 부활한 개체에는 1초 동안 초록 구(자리 표시. 이펙트는 27)가 보입니다. 개발용 `-MmoRevive`면 사망 화면이 뜬 3초 뒤에 부활을 누릅니다. 뒤로 가기(Esc, Android의 뒤로)는 열린 창이 있으면 맨 위 창을 닫고, 없으면 대상을 풀고, 대상도 없으면 설정 창을 엽니다(`FScreenStack::Back`). 구역은 내 캐릭터 액터의 자리를 세션의 `FFieldMap`에 물어 바뀔 때만 고치고, 이름은 `Strings`가 생길 때까지(backlog 74) 키를 그대로 보임), 설정(`WBP_Settings`: 캐릭터 선택으로, 로그아웃, 닫기), 확인 팝업(`WBP_Confirm`: 예·아니요), 수량 입력(`WBP_Quantity`, 팝업: 1부터 받은 최대까지를 −10·−1·+1·+10·최대로 고르고 확인. `UMmoUiManager::Quantity`), 알림(`WBP_Notice`: 위 가운데에 줄 넷까지 쌓고 새 줄이 아래, 줄마다 3초 뒤에 사라지며 넘치면 가장 오래된 줄을 뺌), 이름표(`WBP_NameTag`)입니다. 가상 조이스틱은 누른 손가락을 붙잡아 가운데에서 끈 만큼을 프레임마다 키보드와 같은 이동 액션에 넣습니다(`InjectInputForAction`).

  - 크기와 비율: 기준 해상도는 1920×1080이고 UI 배율은 화면의 짧은 변으로 정합니다(`DefaultEngine.ini`의 `UIScaleRule=ShortestSide`와 짧은 변 1080이 1.0인 곡선).   - 이름표 층: `UMmoNameTagLayer`가 프레임마다 시야 안의 개체(내 캐릭터 포함)의 머리 위(높이 2.1 m. 바닥이 평평하다고 봄)를 화면 좌표로 바꿔 이름표를 놓습니다. 이름표는 개체마다 만들지 않고 풀에서 꺼내 쓰고, 개체가 나가거나 화면 밖이면 감춰 풀로 돌립니다. 몬스터는 이름(`Strings`의 키, 74 전)과 레벨을 보이고 선공 몬스터는 이름 색이 다르며, 플레이어와 몬스터는 이름 아래에 체력 바가 있습니다(내 것은 `SelfVitals`). 피해 숫자도 이 층이 그립니다: 내가 주거나 받은 피해만 맞은 개체의 머리 위에 1초 동안 떠오르며 사라지고(받은 것은 빨강), 치명타는 크고 노랗게 그립니다(글 위젯을 풀로 돌려씀).
  - 위젯 블루프린트: C++ 기반 클래스(`UMmoLoginWidget` 등, `BindWidget`)를 부모로 하는 위젯 블루프린트를 에디터 모듈의 생성기 `UMmoCreateWidgetsCommandlet`이 만듭니다(아래 명령 표). 배치의 원본은 그 코드이고, 에디터에서 고친 배치는 다시 만들 때 덮입니다. 엔진이 위젯 블루프린트의 위젯 트리를 Python에 내놓지 않아 레벨처럼 스크립트로 만들 수 없기 때문입니다(2026-11-11 정함). 생성기 맨 위의 스타일 표(`FMmoStyle`: 색, 글꼴 크기, 버튼의 높이·둥근 모서리·안쪽 여백, 창 틀의 색·여백, 창의 폭, HUD의 여백)가 모든 화면의 모양이고, 화면을 만드는 함수는 이 값과 배치 함수(`Window`: 가운데 창, `SafeCanvas`와 `Corner`: 모서리에 붙인 HUD, `Row`: 나란한 버튼)만 씁니다. 공용 버튼을 맨 먼저 만들고 다른 화면이 그것을 놓습니다. 스타일 표의 버튼 색 하나를 바꾸고 다시 만들면 모든 버튼이 바뀌는 것을 봤습니다. 생성기가 처음 빈 트리로 한 번 컴파일할 때 "필수 위젯 바인딩을 찾지 못했습니다" 경고가 찍히지만, 트리를 채운 뒤의 컴파일과 저장은 성공합니다. 위젯 블루프린트는 코드만 참조하므로 `/Game/UI`를 늘 쿠킹합니다.
- **protobuf**: `Source/ThirdParty/MmoProtobuf/`가 libprotobuf 36.2와 abseil 20250512.1(protobuf가 정한 버전)의 정적 라이브러리와 헤더를 링크합니다. `build.mjs`가 두 소스를 SHA-256으로 확인하고 받아 Mac(arm64·x86_64, macOS 14)과 Android(arm64-v8a, API 26, 정적 libc++)용으로 빌드합니다(M4 Max에서 두 플랫폼 72초). 결과는 LFS로 커밋하고 버전을 바꿀 때만 다시 돌립니다.
  - 크기: Mac 15 MB, Android 11 MB, 헤더 9.3 MB(561개). NDK 툴체인이 Release에도 `-g`를 넣어 Android는 디버그 정보를 지우기 전 145 MB였습니다.
  - 엔진의 `Protobuf` 모듈(30.0)은 쓰지 않습니다. Mac·Windows·Linux 라이브러리뿐이고, 서버와 버전이 다르고, 엔진을 올리면 바뀝니다. 그것을 쓰는 MetaHumanSDK 플러그인은 아래처럼 꺼져 있어 엔진 쪽 protobuf가 함께 링크되지 않습니다.
  - 빌드에는 cmake(3.16 이상)·ninja와, Android는 `NDKROOT`에 UE 5.8이 요구하는 NDK r27c가 필요합니다. 아래 Android 도구 폴더의 `env.sh`를 source하면 둘 다 갖춰집니다(SDK의 cmake 3.22.1과 ninja, NDK 27.2.12479018). 지금 커밋한 Android 라이브러리는 같은 버전의 NDK(Unity 6000.3.15f1에 든 것)로 빌드했습니다.
- **서버 주소**: `UMmoSettings`(`DefaultGame.ini`, 기본 `127.0.0.1:7777`)가 기본값이고 명령줄의 `-MmoServer=호스트:포트`가 이깁니다. `Scripts/package.mjs <mac|android> [--target local|live]`가 대상의 주소를 `BuildCookRun -cmdline`으로 패키지의 `UECommandLine.txt`에 넣어, 커밋한 ini를 바꾸지 않고 패키지마다 주소를 정합니다. local은 Mac이 `127.0.0.1`, Android가 이 Mac의 LAN 주소(같은 Wi-Fi의 휴대폰과 BlueStacks가 붙음)이고, live는 서버 배포(backlog 10)에서 주소를 정할 때까지 멈춥니다. 서버는 모든 인터페이스(`IPAddress.Any`)에서 받습니다.
- **Mac 패키지**: `Scripts/package.mjs mac`이 `BuildCookRun`으로 `Saved/Archive/`에 `.app`(arm64)을 만들고, 실행 파일의 로컬 심볼을 지운(`strip -x`) 뒤 다시 서명합니다(2026-11-11, 212 MB, 로컬 서버에 로그인해 걷는 것까지 확인). C++ 빌드가 된 뒤 쿠킹부터 Development 94초, Shipping 50–55초였습니다. 크기와 줄인 방법은 아래 표에 있습니다. Xcode 26부터 Metal Toolchain을 따로 받아야 하고(`xcodebuild -downloadComponent MetalToolchain`, 838.9 MB), 없으면 에디터 열기와 쿠킹이 셰이더 컴파일에서 멈춥니다.
- **플러그인**: `.uproject`의 `DisableEnginePluginsByDefault`로 엔진 플러그인(기본으로 켜지는 것 187개)을 모두 끄고 쓰는 것만 켭니다. 게임에는 EnhancedInput(과 그것이 쓰는 DataValidation), AndroidDeviceProfileSelector(Android 기기별 설정), AndroidPermission(UE의 `GameActivity.java`가 그 Java 클래스를 import해 없으면 Gradle 컴파일이 실패함), ACLPlugin(엔진 기본 애니메이션 압축), 에디터에만(`TargetAllowList`) 콘텐츠 브라우저, 에셋 정의, 플러그인 창, Xcode·Rider 연동, PythonScriptPlugin(에셋을 만드는 스크립트)이 켜집니다. 기본으로 켜져 있던 것 중 MetaHumanSDK(엔진 protobuf), AndroidFileServer(켜 두면 `DefaultEngine.ini`에 기기 연결용 `SecurityToken`을 써 넣음), NNEDenoiser(ONNX Runtime 97 MB)도 이렇게 꺼집니다. 플러그인이 필요해지면 `.uproject`에 켭니다.
  - 에디터에만 켠 플러그인도 쿠커(에디터 프로세스)가 모듈을 불러 그 셰이더가 게임에 들어갈 수 있습니다. Interchange(에셋 임포트)를 에디터에만 켜면 셰이더 약 11 MB가 늘고 그 콘텐츠의 쿠킹이 실패해서(게임에 모듈이 없음), 에셋을 임포트할 때 다시 켜고 `DefaultGame.ini`의 `DirectoriesToNeverCook`에 `/Interchange`를 더합니다.
- **렌더러**: 조명은 동적 조명만 쓰도록 Lumen, Nanite, 가상 그림자, 메시 거리장, 레이 트레이싱, 라이트맵(정적 조명)을 `DefaultEngine.ini`에서 끕니다. 그래서 그 기능들에 필요한 SM6 없이 Mac 셰이더를 SM5 한 벌만 싣습니다(SM5는 DirectX 11급 기능으로 모든 Metal Mac에서 돌고, SM6는 Nanite 등이 쓰는 DirectX 12급 기능으로 Apple Silicon·macOS 14 이상). 셰이더가 줄고, Android의 모바일 렌더러와도 표현이 가까워집니다. 필요해지면 그 줄을 지우면 됩니다.
- **Android**: `Config/DefaultEngine.ini`에 패키지 이름(`cloud.dennou.mmo`), arm64만, API 26–36, APK 하나에 데이터를 넣는 설정이 있습니다. `Scripts/package.mjs android`가 `Saved/Archive/Android_ASTC/`에 APK를 만듭니다. BlueStacks Air(Mac, arm64-v8a, Android 13)에서 로그인해 걷고 카메라를 돌리는 것까지 확인했습니다(2026-11-11). 실제 기기는 아직입니다.
  - 렌더러: Vulkan만 싣습니다(`bSupportsVulkan=True`, `bBuildForES31=False`). BlueStacks에서 OpenGL ES 렌더러가 에뮬레이터 드라이버 안에서 크래시가 났기 때문입니다(2026-11-10). 엔진의 Android 기본 기기 프로필은 Vulkan을 끄고(`r.Android.DisableVulkanSupport=1`) 목록에 있는 일부 기기만 켜므로, `Config/DefaultDeviceProfiles.ini`에서 모든 기기에 켭니다. 그러지 않으면 목록에 없는 기기(BlueStacks 포함)가 "Unable to run on this device"로 멈춥니다. Vulkan 1.1 드라이버가 없는 기기는 엔진의 드라이버 검사에서 그대로 거절됩니다.
  - 하늘: 모바일 렌더러는 `SkyAtmosphere`를 그리려면 `IsSky` 머티리얼의 메시가 따로 있어야 해서 지금은 하늘 없이 안개색 배경입니다(Development 빌드는 화면에 경고를 띄움).
  - BlueStacks: 설정에서 ADB를 켜면 `adb connect 127.0.0.1:5555`로 붙고, `adb install -r`로 넣고 `adb shell input`으로 누르고 끌 수 있습니다(아래 명령 표). 휴대폰은 같은 Wi-Fi에서 local APK가 이 Mac의 서버에 붙습니다.
  - 필요한 것: 엔진의 Android 대상 플랫폼 구성 요소(Epic Games Launcher의 선택 다운로드, 엔진 쪽 약 2.5 GB. 없으면 UBT가 시작부터 멈춤), 아래 도구 폴더, SDK 폴더의 라이선스 동의(`sdkmanager --licenses`가 `licenses/`에 씀. 없으면 APK 단계에서 멈춤).
  - 도구 폴더: Unity처럼 엔진 버전마다 Android Studio·Unity와 따로 `/Users/Shared/Epic Games/Android/UE_5.8/`에 둡니다(SDK 3.0 GB, JDK 335 MB). `Scripts/setup-android.mjs`가 받는 파일을 배포처의 체크섬으로 확인하며 만듭니다. 받는 것은 Temurin JDK 21.0.13, cmdline-tools 21.0, 엔진의 `Engine/Config/Android/Android_SDK.json`이 정한 platform(android-36)·build-tools(36.0.0)·cmake(3.22.1)·NDK(27.2.12479018)입니다. 빌드 전에 그 폴더의 `env.sh`를 source해 `ANDROID_HOME`, `NDKROOT`, `JAVA_HOME`을 줍니다. 셸 프로필은 고치지 않습니다.
  - JDK: UE 5.8의 Gradle 8.13은 Java 23까지만 돌아서 Android Studio 2026.2에 든 JDK 25를 쓸 수 없습니다. 엔진의 `SetupAndroid.command`도 그 JDK를 `~/.zshrc`에 써 넣으므로 쓰지 않습니다.
  - cmdline-tools: 22.0부터 `sdkmanager`가 Android CLI(`android sdk`)로 바뀌어 `--licenses`가 라이선스 파일을 쓰지 않고(UE는 그 파일이 있어야 APK를 만듦), CLI가 기본으로 사용 통계를 보냅니다. 그래서 21.0으로 고정합니다.
  - 빌드 가속기(UBA): UBA는 컴파일러에 라이브러리를 주입(DYLD)해 돌리는데, NDK의 clang은 Google이 hardened runtime으로 서명해 주입이 막힙니다(Xcode의 clang은 막히지 않아 Mac 빌드는 UBA로 돕니다). 그래서 Android는 `-UbtArgs=-NoUBA`로 끕니다. 켜 두면 컴파일마다 `not active but did not get exit message` 오류가 찍힙니다.
  - 크기: Vulkan만 실은 APK가 75.8 MB입니다(2026-11-11, 콘텐츠가 늘었습니다). 아래는 2026-11-09의 74.4 MB APK입니다: `libUnreal.so`가 압축 전 94.6 MB(APK 안 37.9 MB), 데이터(`main.obb.png`) 31.4 MB, Java(`classes.dex`) 9.2 MB입니다. 셰이더는 Vulkan과 OpenGL ES 3.1 두 벌(압축 전 각 6.8 MB, 5.3 MB)입니다. Unity의 SDK로 만들었을 때는 `libUnreal.so`에 디버그 정보가 남아 APK가 96.6 MB였는데, 까닭은 찾지 못했습니다.
