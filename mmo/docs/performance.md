# 성능 수치

같은 방법으로 다시 재서 바뀐 것과 견주려고 남기는 수치입니다(키우기의 [성능 수치](../../idle/docs/performance.md)와 같은 방식, [설계: 최적화](design.md#최적화)). 줄마다 잰 날, 커밋, 환경(기기, 빌드, 봇 수와 걷는 넓이, 평균 시야)과 수치를 적습니다. 송신량은 한 달의 GB와 VPS의 동시 접속으로 바꾼 값도 적습니다.

## 재는 순서

1. **먼저 잽니다.** 고치기 전에 아래의 같은 방법으로 재서 줄을 남깁니다. 재지 않은 것은 고치지 않습니다.
2. **가장 큰 것부터 고칩니다.** 서버 로그의 차례별 시간(`phases`)과 패킷 종류별 바이트(`packets`)에서 가장 큰 것을 고릅니다.
3. **같은 방법으로 다시 재서 전과 후를 남깁니다.** 기계의 다른 부하에 따라 같은 코드도 구간마다 10%쯤 달라지므로, 고치기 전의 커밋(임시 worktree에서 빌드)과 고친 뒤를 같은 셸에서 번갈아 세 번씩 재서 평균을 적습니다.

## 재는 방법

- **서버 부하**: 서버와 봇을 한 기계에서 루프백으로 돌린 Release 빌드입니다. 서버는 빈 데이터베이스와 봇과 같은 정사각형으로 띄웁니다. 봇이 들어온 뒤 첫 10초 구간은 로그인과 JIT라 빼고, 그 뒤 10초 구간들의 평균(최대는 가장 큰 값)을 적습니다.

  ```sh
  dotnet run -c Release --project mmo/server/src -- --port 7800 --spawn-half-extent 285 --max-players 2500 --database /tmp/load.sqlite
  dotnet run -c Release --project mmo/server/tools/load-test -- --port 7800 --bots 2000 --half-extent 285 --seconds 70
  ```

  봇은 서버와 같은 격자를 읽어 서버의 `FieldMap.CanWalkLine`으로 막힌 곳으로 걷지 않고 돌아섭니다. 봇이 끝에 찍는 `resets`(받은 `PositionReset`)가 0이어야 정상 클라이언트의 부하입니다. 서버 로그의 줄은 [MANUAL의 서버](../MANUAL.md#서버)에 있습니다.
- **어느 함수에 시간이 드는지**: `dotnet-trace`로 틱 스레드를 봅니다. `dotnet tool install -g dotnet-trace` 뒤 `dotnet-trace collect -p <서버 pid> --duration 00:00:20 --format speedscope`로 20초를 기록하고 speedscope에서 `GameServer.RunTick` 아래를 봅니다.
- **할당과 GC**: `dotnet-counters`로 봅니다. `dotnet tool install -g dotnet-counters` 뒤 `dotnet-counters monitor -p <서버 pid> --counters System.Runtime`에서 할당률, 세대별 GC 횟수, GC에 든 시간의 비율을 봅니다.
- **송신량을 비용으로**: 클라이언트당 송신(B/s)에 TCP/IP 머리(틱마다 한 세그먼트, 52 × 20 = 1,040 B/s)를 더해 한 달(30.4일, 2,626,560초)을 곱합니다. VPS의 동시 접속은 Hostinger KVM 4(월 16 TB, 4 vCPU)의 송신량을 그 값으로 나눈 것입니다.

- 셋째 줄은 봇이 벽을 모르고 걸어 받은 `Move`의 약 4분의 1이 되돌려진 값이라(움직이지 않은 봇이 많아 `EntityMoves`가 작음) 견주는 기준으로 쓰지 않습니다. 재는 코드(29)를 넣기 전과 후의 틱 평균을 번갈아 세 번씩 재서 12.13 ms와 12.07 ms로 같은 것을 본 줄입니다.
- 넷째 줄이 맵을 넣은 뒤의 기준입니다. 봇이 받은 `PositionReset`은 0이었습니다. 첫째·둘째 줄과의 차이는 맵의 막힌 칸만큼 봇이 고르게 흩어지지 않은 것과 측정의 흔들림 안입니다.

- 50 ms를 넘은 틱(`slow tick`)은 봇 2,000명이 한꺼번에 들어오는 첫 구간에만 8번 있었고(56–104 ms, 시야와 보내기가 큼), 그 뒤에는 없었습니다. 타이머가 늦게 시작한 시간은 평균 1.5 ms, 최대 2.0 ms이고 건너뛴 틱은 없었습니다. 보내기 큐는 연결마다 1프레임을 넘지 않았습니다.
- 10초에 `EntityMoves` 40만 개가 약 290 MB로 송신량의 98%입니다(`EntitiesEnter` 4.4 MB, `EntitiesLeave` 0.7 MB). 시야와 보내기가 틱의 97%라, 서버의 최적화(51부터)는 이 둘부터 합니다.
