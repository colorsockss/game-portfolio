# MMORPG 구현 목록

MMORPG 포트폴리오(`mmo/`)의 할 일 목록과 마일스톤입니다. 어떤 게임이고 각 시스템을 어떻게 만드는지는 [게임 설계](design.md)에, 이미 만든 것의 구조와 규칙은 [MANUAL](../MANUAL.md)에 있습니다. Unity(C#만, UI Toolkit + App UI) 클라이언트와 Unreal(C++, UMG) 클라이언트가 MMO 서버(C#) 하나에 붙고, 패킷은 Protobuf입니다. 클라이언트 포트폴리오라 서버는 프로세스 하나로 두고 거래소는 만들지 않습니다. 서버에서는 MMO에 꼭 필요한 최적화까지 합니다(2026-11-10 정함).

Unreal 클라이언트를 기능, 최적화, 완성도까지 다 만든 뒤(M7까지), Unity 클라이언트는 그것을 C#과 UI Toolkit으로 옮기듯이(포팅) 만듭니다(2026-11-09 정함). 그래서 Unreal 쪽에서 기능과 구조를 정하고, Unity에서는 같은 기능을 엔진에 맞게 옮기기만 합니다. Unity 클라이언트 구현은 키우기(`idle/`)에 이미 있어 아직 없는 Unreal을 먼저 만들고, 구조가 엄격한 Unreal(Actor, Subsystem, UMG)에서 정한 구조는 느슨한 Unity로 그대로 옮겨지지만 반대로 옮기면 Unreal답지 않은 코드가 되기 쉽습니다.

키우기(`idle/`)의 서버는 요청-응답과 커맨드마다 저장하는 구조라서 쓰지 않습니다. MMO 서버는 틱마다 이동과 전투를 계산하고 주변 플레이어에게 계속 보내는 상태 서버입니다. 두 게임이 함께 쓰는 것은 루트의 `tools/`뿐입니다.

## 현재 있는 것

- 계약: `packets.proto`의 패킷 10개(로그인, 이동, 시야, 연결 확인)와 함께 쓰는 수(`Constant`), 축·`yaw` 규약. protoc 36.2가 C#과 C++을 함께 만듭니다(3).
- 서버: 로그인(텍스트 ID), 20Hz 틱 루프, 시야(32 m 칸, 3×3), 이동 검증, 마지막 위치의 SQLite 저장, 15초 무응답 끊기. 봇 2,000명 부하를 쟀습니다(6).
- Unreal 클라이언트: Mac·Android 빌드, 서버 연결(`UMmoConnection`), 세션과 엔진 없는 월드 모델(`UMmoSession`, `FWorldState`), 로그인 화면(8). Mac에서 로그인해 `Field` 레벨을 걷고, 시야 안의 다른 플레이어를 보간해 그립니다. 캐릭터는 자리 표시용 도형입니다(11–13). 화면 관리자와 층, HUD의 가상 조이스틱, 이름표, 설정·확인 창이 있고 위젯 블루프린트는 생성기가 만듭니다(16). Mac `.app`과 Android APK를 대상 서버 주소로 패키징하고 BlueStacks에서 돌립니다(15).

## 폴더

```
client-unity/        Unity, C#만, UI Toolkit + App UI
client-unreal/       Unreal, C++, UMG
server/              MMO 서버 (C#, .NET 10)
shared/contract/     packets.proto → protoc로 서버·Unity(C#), Unreal(C++) 코드 생성
data/                기획 데이터 원본
```

## 목록

1–10의 번호는 다른 문서가 가리키므로 바꾸지 않습니다. 11부터는 만드는 차례대로 마일스톤마다 묶었습니다. 71–77은 검사(2026-11-10)로, 78–81은 MMO 서버 기술을 조사해(2026-11-10) 더한 항목이라 번호는 뒤지만 자리는 마일스톤을 따릅니다. 49와 58은 뺀 항목입니다. 번호 뒤의 `M1`–`M9`는 [마일스톤](#마일스톤)입니다.

11부터의 항목은 누가 무엇을 어떻게 만드는지를 나눠 적습니다. 규칙(무엇이 맞는 동작인가)은 [게임 설계](design.md)에 있고, 여기에는 만드는 방법을 적습니다. 클래스와 패킷의 이름은 만들 때 정하는 이름의 초안입니다.

| 표시 | 뜻 | 일하는 곳 |
| --- | --- | --- |
| **계약·데이터** | 더할 패킷(`packets.proto`)과 데이터 테이블 | `shared/contract/`, `data/` |
| **서버** | 서버 코드와 구현 방식 | `server/`. 엔진 없이 테스트하므로 worktree 세션에서 할 수 있음 |
| **모델** | 클라이언트의 엔진 없는 코드(월드 모델, 판단) | `client-unreal/`의 `Protocol/`, `World/`. 엔진 없이 테스트하고 Unity로 그대로 옮김 |
| **화면** | 클라이언트의 Unreal 코드와 에셋(액터, 위젯, 애니메이션) | `client-unreal/`. 에디터가 필요해 메인 체크아웃에서 한 번에 하나씩 |
| **확인** | 테스트와 눈으로 볼 것 | |

한쪽이 할 일이 없으면 "없음"이라고 적습니다. **클라이언트**라고만 적은 것은 모델과 화면을 나눌 것이 없는 경우입니다.

### A. 먼저 정할 것

- [x] **1. 서버 언어** `M1` — C#(.NET 10)입니다. 서버 코드는 Unity 클라이언트와도 나눠 쓰지 않습니다. 두 클라이언트가 같은 조건이 되도록, Unity(C#)와 Unreal(C++) 모두 패킷 정의(3)에서 protoc가 생성한 코드를 받습니다. Unreal을 UnrealSharp(C#)로 쓰는 안은 2026-11-06에 접고 C++로 정했습니다.
- [x] **2. 전송** `M1` — TCP 위에 Protobuf의 길이 구분 형식(varint 길이 + 메시지)으로 패킷을 보냅니다. 서버(C#)와 Unity는 `System.Net.Sockets`, Unreal은 `Sockets` 모듈의 표준 소켓만 쓰고, 신뢰성 계층은 만들지 않습니다. 대신 패킷 하나가 손실되면 뒤의 패킷도 재전송을 기다리므로 손실 있는 망에서 이동이 잠깐 멈출 수 있습니다. 서버 판정에 클라이언트 보간을 하는 MMO에서는 견딜 만한 수준으로 봅니다. 패킷 형식(3)은 전송과 따로 정의하므로, 나중에 UDP로 바꿔도 소켓 계층만 바뀝니다.

### B. 공용

- [x] **3. 패킷 정의** `M1` — `shared/contract/packets.proto`(proto3)에 첫 기능(로그인, 이동, 주변 플레이어 표시)의 패킷 8개와 연결 확인(`Ping`, `Pong`)이 있습니다. 함께 쓰는 수는 `Constant` enum 값으로 두어 C#과 C++이 같이 생성됩니다(2026-11-10). `Packet`의 oneof 필드 번호가 패킷 번호이고, 배포된 번호와 enum 값은 바꾸지 않습니다. `npm run generate`가 Google.Protobuf.Tools(NuGet 3.36.2)의 protoc로 C#(`generated/Packets.cs`, Google.Protobuf 3.36.2)과 C++(`packets.pb.h`, `packets.pb.cc`)을 만들어 커밋하고 서버, Unity, Unreal이 함께 씁니다. `npm run test:mmo`가 왕복과 와이어 크기를 확인하고, 형식을 고른 근거와 수치는 [MANUAL](../MANUAL.md#형식을-고른-근거-2026-11-06)에 있습니다. C++ 생성을 더하며 protoc를 Grpc.Tools 2.85.0의 35.1에서 런타임과 같은 36.2로 바꿨습니다(2026-11-09, C# 출력은 같음). 직접 만든 형식(`.def` 문법과 `tools/contract-tool`)은 Protobuf로 정하며 지웠습니다(2026-11-06).
- [ ] **4. 데이터** `M3` — `data/`의 xlsx를 data-tool로 변환합니다. 테이블 목록은 [설계](design.md#데이터-테이블)에 있고, 기능을 만들 때 그 기능의 테이블을 더합니다. data-tool에 mmo용 출력을, formula-tool에 double 기준 C# 내보내기를 더합니다(아래의 "툴". 키우기의 `Big`은 쓰지 않습니다). 루트의 `npm run generate -- mmo`와 `--check`가 패킷에 더해 MMO 데이터도 만들게 합니다. 이때 `mmo-ci.yml`의 `paths`에 `tools/**`, `package-lock.json`, `.gitattributes`를, 단계에 `npm ci`와 `mmo/data/*.xlsx`의 LFS를 더하고, `scripts/check.mjs`에서 `tools/`가 mmo도 검사하게 합니다.
  - **툴**: data-tool에 mmo용 출력을 더합니다. 테이블마다 `.proto`(줄 하나의 메시지와 줄의 목록)와 그 형식의 바이너리 파일을 내고, protoc가 만든 C#과 C++이 로더가 됩니다. 서버와 두 클라이언트에 이미 있는 Protobuf 런타임으로 읽으므로 MessagePack(키우기의 형식)을 읽는 라이브러리를 더하지 않습니다. 스키마 시트의 검사(참조, 범위, Enum)는 지금 것을 그대로 씁니다. formula-tool은 공식을 C# 함수로 냅니다(피해 공식은 서버만 계산합니다. C++은 클라이언트가 미리 보여 줄 공식이 생기면 더합니다). 생성물 전체의 해시도 냅니다. 테이블은 그것을 쓰는 항목에서 하나씩 더합니다(`Zones`는 19, `Monsters`는 23).
  - **서버**: 뜰 때 생성된 로더로 모든 테이블을 읽어 바꾸지 않는 객체로 두고, 참조가 깨진 줄이 있으면 뜨지 않습니다. `Login`에 실려 온 데이터 해시가 자기 것과 다르면 `LOGIN_RESULT_CODE_DATA_MISMATCH`로 거절합니다.
  - **모델**: 같은 생성물을 C++ 로더로 읽습니다. 엔진 없는 테스트가 서버와 같은 줄 수와 값을 읽는지 봅니다. `Login`에 데이터 해시를 싣습니다.
  - **화면**: 생성된 데이터 파일을 패키지에 싣고(쿠킹하지 않는 파일로) 시작할 때 읽습니다.
  - **확인**: 서버와 엔진 없는 테스트가 같은 생성물에서 같은 줄 수와 값을 읽는 것, 참조가 깨진 데이터로 서버가 뜨지 않는 것, 데이터 해시가 다른 `Login`이 거절되는 것을 봅니다.
- [ ] **5. 규칙 비교 벡터** `M3` — 클라이언트가 서버 규칙을 예측해야 하면(이동, 쿨다운 등), 서버 구현이 만든 입력 → 출력 쌍으로 두 클라이언트의 구현을 검사합니다. 예측이 필요한 규칙이 생길 때 합니다.
  - **서버**: 테스트가 규칙마다 입력 → 출력 쌍을 탭으로 나눈 텍스트 파일로 써서 `shared/`에 커밋합니다(쿨다운, 구역, 걸을 수 있는 칸). JSON으로 두지 않는 것은 엔진 없는 C++이 라이브러리 없이 읽게 하려는 것입니다.
  - **모델**: 엔진 없는 테스트가 그 파일을 읽어 C++ 구현의 답과 비교합니다. Unity도 같은 파일을 씁니다.
  - **확인**: 비교 벡터를 일부러 틀리게 바꾸면 엔진 없는 테스트가 실패합니다. 구역의 비교 벡터는 19와 함께 만듭니다.

### C. 서버

- [x] **6. 서버 뼈대** `M1` — `server/`(2026-11-06). 로그인(텍스트 ID), 20Hz 틱 루프, 시야(32 m 칸, 3×3), 이동 검증(속도 예산과 `PositionReset`), 마지막 위치의 SQLite 저장(나갈 때, 60초마다, 내려갈 때)입니다. SQLite는 idle 서버처럼 같은 VPS에서 프로세스와 비용을 더하지 않아 골랐고, 서버 프로세스 여러 개가 한 데이터베이스를 나눠 써야 하면 다시 고릅니다. 구조와 규칙은 [MANUAL의 서버](../MANUAL.md#서버), 봇 2,000명의 틱 시간·CPU·송신량·메모리·저장 시간과 동접 기준 비용은 [부하 측정](../MANUAL.md#부하-측정-2026-11-06)에 있습니다.

### D. 클라이언트

- [ ] **7. Unity 클라이언트** `M8` — `client-unity/`. Unreal 클라이언트를 기능(M2–M6)에 더해 최적화와 완성도(M7)까지 다 끝낸 뒤에 시작하고, 그 기능과 구조를 옮기듯이(포팅) 만듭니다. 최적화로 정한 구조(관리자 하나가 다른 캐릭터를 갱신, 풀, 보이는 줄만 만드는 목록)도 처음부터 그대로 옮기고, 같은 방법으로 프레임을 재서 Unreal의 수치와 나란히 적습니다. 프로젝트 루트에 Unity 규칙의 `.gitignore`(`idle/client/.gitignore`와 같음)를 둡니다. C#만 쓰고(PuerTS 없음) UI는 UI Toolkit과 [App UI](https://docs.unity3d.com/Packages/com.unity.dt.app-ui@latest)(`com.unity.dt.app-ui`)입니다. 패킷은 생성한 C#과 Google.Protobuf 런타임을 쓰고, IL2CPP에서 도는지는 이때 확인합니다. 경계는 asmdef 참조가 지킵니다. 엔진이 필요한 테스트와 빌드는 로컬에서 합니다(10). 이때 더하는 `mmo-unity-ci.yml`은 `mmo/client-unity/**`와 생성된 C#(`mmo/shared/**/*.cs`)이 바뀌면 엔진 없는 코드만 검사합니다. 패킷·규칙 코드를 `noEngineReferences` asmdef에 두고, 같은 `.cs`를 읽는 테스트 csproj(Unity와 같은 C# 9, .NET Standard 2.1)를 `dotnet test`로 돌립니다. 66처럼 `mmo-ci.yml`과 `scripts/check.mjs`에서 `mmo/client-unity/`를 뺍니다.
- [x] **8. Unreal 클라이언트 뼈대** `M1` — `client-unreal/`(2026-11-10). Unity 클라이언트(7)가 옮겨 올 기준 구현이라 기능(M2–M6)을 여기서 먼저 만듭니다. C++이고 UI는 UMG입니다. 대상은 Mac과 Android이고 처음부터 두 플랫폼으로 빌드합니다. iOS는 나중에 같은 방법으로 더하고, Windows 패키지는 Mac에서 만들 수 없어 Windows PC가 있을 때 만듭니다. 패킷은 protoc가 만든 C++이고, protobuf는 서버의 C# 런타임(Google.Protobuf 3.36.2)과 같은 36.2로 통일합니다(2026-11-09). C++ 생성 코드는 런타임과 버전이 같아야 컴파일되므로 C#과 C++을 같은 protoc 36.2로 만듭니다. libprotobuf 36.2와 그 버전이 요구하는 abseil은 래퍼 ThirdParty 모듈에 플랫폼별(Mac arm64·x86_64, Android arm64-v8a)로 직접 빌드해 빌드 스크립트와 함께 LFS로 커밋합니다. Android는 엔진과 같은 NDK(r27c)와 C++ 표준 라이브러리 설정으로 빌드하고, RTTI 설정도 엔진에 맞춥니다. UE 5.8에도 `Protobuf` 모듈(30.0)이 있지만 라이브러리가 Mac·Windows·Linux용뿐이고 버전이 서버와 다르며 엔진을 올리면 바뀌어서 쓰지 않습니다. 엔진 쪽 protobuf가 함께 링크되지 않도록 그것을 쓰는 MetaHumanSDK 플러그인은 `.uproject`에서 끕니다.
  - 한 것: MmoProtobuf(Mac·Android 라이브러리와 `build.mjs`), protoc 36.2의 C++ 생성, 프로젝트 뼈대, 서버 연결(`UMmoConnection`)과 C++로 만든 로그인 화면까지 했고, Mac에서 로컬 서버에 로그인하는 것과 엔진 없는 프레임 테스트(`Tests/run.mjs`)를 확인했습니다. - [ ] **17. 틱의 차례와 시스템** `M3` — 콘텐츠를 넣기 전에 서버의 구조를 나눕니다. [설계: 틱의 차례](design.md#틱의-차례)
  - **서버**: 지금 `World` 하나에 있는 코드를 데이터(`EntityTable`, `Grid`)와 시스템(`LoginSystem`, `MovementSystem`, `ViewSystem`)으로 나눕니다. 틱은 시스템을 정해진 차례(입력 → 예약한 일 → 몬스터 → 전투 → 회복과 효과 → 시야 → 저장 → 보내기)로 부릅니다. 입력(`World.Receive`)과 보내기(`GameServer.Flush`)는 지금 자리에 두고 `World.Step`이 그 사이의 차례를 부릅니다. 입력 차례의 요청 처리는 자기 플레이어의 상태만 고칩니다. 다른 개체를 고치는 결과(피해, 죽음, 효과 붙이기)는 전투 차례로 넘깁니다(요청 하나의 예외가 남의 상태를 반쯤 고친 채 두지 않게 하려는 것입니다. 39). 시스템은 (지금 틱, 지난 틱 수)를 받습니다. 주기로 하는 일은 나머지 연산이 아니라 "다음에 할 틱 ≤ 지금 틱"으로 보고, 밀려도 한 번만 한 뒤 `다음 += 주기`를 지금 틱을 넘을 때까지 되풀이해 위상을 지킵니다. 개체마다 같은 주기로 하는 일은 처음의 `다음 = 번호 % 주기`로 엇갈립니다. 지금 코드의 저장과 로그 주기(나머지 연산)도 여기서 이 방식으로 바꿉니다. 그러면 틱 번호가 건너뛰어도(79) 시스템은 고칠 것이 없습니다. 시스템 사이는 `TickEvents`(그 틱의 사건 목록: 죽음, 아이템 얻음)로 잇고, 사건은 그 틱 안에서 다 처리합니다.

- [ ] **24. 기본 공격** `M3` — 대상을 정해 칩니다. [설계: 전투](design.md#전투)
  - **계약**: `AttackStart`(대상 번호), `AttackStop`, `Damaged`(공격자, 대상, 피해, 남은 체력), `Died`(개체, 죽인 개체). 모두 200번대. 실패 이유 enum(`FailReason`)과, 요청 번호가 없는 요청(공격, 부활, 파티 초대, 채집 시작)의 실패를 알리는 `ActionFailed`(이유, 세션 범위)도 여기서 둡니다. 뒤의 `SkillFailed`(26)가 같은 enum을 씁니다.
  - **서버**: `CombatSystem.CanAttack(공격자, 대상)`이 칠 수 있는지를 한 곳에서 답합니다. M3에서는 플레이어와 몬스터 사이만 참이고, 44가 플레이어 사이로 넓힙니다. `AttackStart`를 받으면 `CanAttack`을 확인해 그 플레이어를 공격 중인 개체의 목록에 올리고, 거짓이면 `ActionFailed`로 답합니다. `AttackStop`을 받으면 목록에서 뺍니다. 몬스터는 `AiSystem`의 공격 상태가 목록에 올리고 뺍니다. `CombatSystem`은 전투 차례마다 목록에서 "다음 공격 틱"이 된 개체만 봅니다. 대상이 살아 있고 사거리 안이면 피해를 주고 다음 공격 틱을 간격만큼 미룹니다. 사거리 밖이면 치지 않고 기다립니다. 대상이 죽거나 시야에서 나가면 목록에서 뺍니다. `Damaged`와 `Died`는 그 틱의 사건으로 쌓았다가 시야 차례에 대상(맞은 쪽, 죽은 쪽)이 보이는 연결에 넣습니다. 뒤의 사건도 같고, "개체가 보이는 연결"에는 그 개체 본인의 연결도 듭니다.
  - **모델**: `FCombatState`가 내 대상과 공격 중인지를 가집니다. `Damaged`는 개체의 체력에 반영하고, 화면이 꺼내 갈 사건 목록(피해 숫자, 공격 동작)에 쌓습니다. "가장 가까운 적"을 고르는 함수를 여기 둡니다.
  - **화면**: 누른 곳의 액터에서 개체 번호를 얻어 대상으로 정하고, 탭 키와 모바일 버튼은 가장 가까운 적을 고릅니다. 공격 버튼을 누르면 사거리까지 걸어가 `AttackStart`를 보냅니다. `Damaged`의 공격자에게 공격 몽타주를, 대상에게 피격 반응을 재생합니다. 피해 숫자(풀), 이름표의 체력 바, 대상 정보창을 둡니다.
  - **확인**: 서버 테스트로 공격 간격, 사거리 밖에서 쉬었다가 이어 치기, 죽은 대상, 대상이 나갔을 때, `AttackStop` 뒤에는 치지 않는 것, 플레이어를 대상으로 한 `AttackStart`가 실패로 답해지는 것, 공격 상태의 몬스터가 간격마다 치는 것을 봅니다. 23에서 미룬 것(맞으면 추적하는 것, 대상 바꾸기, 복귀 중 무적)도 여기서 봅니다. 엔진 없는 테스트로 체력 반영과 가장 가까운 적을 봅니다.

- [ ] **25. 사망과 부활** `M3` — 죽고 다시 일어납니다. [설계: 성장](design.md#성장)
  - **계약**: `Revive`(요청), `Revived`(개체, 체력). `EntityMove`에 순간 이동 표시를 더합니다(부활, 귀환 주문서). 죽음은 표시 상태 비트로도 보냅니다(나중에 시야에 들어온 쪽이 알 수 있게).
  - **서버**: 체력이 0이 되면 `CombatSystem`이 죽음 사건을 내고 개체에 죽음 표시를 합니다. 죽은 개체의 요청은 `Revive`, `Ping`, 채팅, `Logout`만 받습니다. 플레이어는 `Revive`를 보내면 `Zones`의 부활 지점으로 옮기고 체력을 일부 채웁니다. 서버가 플레이어를 옮길 때(부활, 귀환, 개발 명령)는 보는 쪽에는 순간 이동 표시가 있는 움직임으로, 본인에게는 `PositionReset`으로 알립니다(내 개체는 `EntityMoves`에 들어가지 않습니다). `Revived`는 그 개체가 보이는 연결에 보내 죽음 표시를 내리게 하고, 본인의 체력과 마나는 `SelfVitals`(22)로 갑니다. 몬스터는 죽음 표시로 3초 동안 남았다가 `Scheduler`가 빼고(`EntitiesLeave`), `SpawnSystem`이 리스폰을 예약합니다. 죽는 틱에 바로 빼면 클라이언트가 이미 없는 개체의 `Damaged`와 `Died`를 받습니다. 무법자가 따로 부활하는 지점은 44에서 넣습니다.
  - **모델**: 죽음 표시와 `Revived`를 개체에 반영합니다. 순간 이동 표시가 있는 움직임은 위치 기록을 비우고 그 자리에 바로 놓습니다. 내가 죽었는지를 `FSelfState`가 가집니다.
  - **화면**: 죽음 애니메이션, 내가 죽으면 조작을 막고 사망 화면(부활 버튼)을 엽니다. 부활하면 사망 화면을 닫고 `PositionReset`의 위치로 옮깁니다(12).
  - **확인**: 서버 테스트로 죽은 동안의 `Move`·공격이 버려지는 것, 부활 위치와 체력, 부활한 본인이 `PositionReset`과 `SelfVitals`를 받는 것, 보는 쪽이 순간 이동 표시가 있는 움직임과 `Revived`를 받는 것, 죽은 몬스터가 3초 뒤에 빠지는 것, 몬스터의 리스폰 시간(23에서 미룬 것), 죽은 개체가 시야에 새로 들어올 때의 표시를 봅니다. 엔진 없는 테스트로 순간 이동한 개체가 미끄러지지 않는 것을 봅니다.

- [ ] **26. 스킬과 효과** `M3` — 스킬을 쓰고 효과를 겁니다. [설계: 전투](design.md#전투)
  - **계약·데이터**: `Skills`, `Effects` 테이블. `UseSkill`(스킬, 대상), `SkillCast`(시전자, 스킬, 끝나는 틱), `SkillCancelled`(시전자), `SkillUsed`(시전자, 스킬, 대상), `SkillFailed`(이유. 24의 `FailReason`), `EffectApplied`(개체, 효과, 끝나는 틱), `EffectRemoved`(개체, 효과), `Cooldowns`(스킬마다 끝나는 틱. 32부터 물약도). 200번대. `EntityEnter`에 걸려 있는 효과(번호, 끝나는 틱)를 실어, 나중에 시야에 들어온 쪽이 알게 합니다.
  - **서버**: `SkillSystem`이 합니다. M3에서는 모든 스킬을 배운 것으로 두고 퀵슬롯은 정해진 차례이며, 배우기와 배치는 36에서 넣습니다.
    - 요청: 입력 차례에서 차례대로 확인합니다: 배웠는지, 쿨다운의 끝나는 틱, 마나, 대상과 사거리, 상태. 어긋나면 `SkillFailed`로 답합니다. 시전 시간이 없는 스킬은 통과하면 그 자리에서 마나를 빼고 쿨다운을 겁니다. 시전 시간이 있는 스킬은 발동할 때 마나를 빼고 쿨다운을 걸어, 취소되면 잃는 것이 없습니다(발동할 때 마나가 모자라면 `SkillFailed`로 답합니다). 시전하는 동안의 다른 `UseSkill`은 실패로 답합니다. 입력 차례에서는 여기까지만 합니다(17).
    - 발동: 전투 차례에서 합니다. 시전 시간이 없으면 그 틱에, 있으면 `Scheduler`에 예약한 틱에 발동합니다. 시전하는 사이에 시작한 자리에서 벗어나거나 기절하면 취소합니다. `Move`가 왔는지가 아니라 위치가 달라졌는지를 봅니다(방향만 바꾼 `Move`와 멈출 때의 마지막 `Move`는 취소하지 않습니다). 발동하면 종류에 따라 단일 피해, 범위 피해, 효과 붙이기, 회복을 적용합니다. 범위 피해의 대상은 `Grid.Query`로 찾아 `CombatSystem.CanAttack`(24)으로 거릅니다.
    - 효과: 개체의 작은 배열(효과 번호, 끝나는 틱)입니다. 붙을 때 `Scheduler`에 끝을 예약하고, 같은 효과가 다시 붙어 시간이 새로 되면 세대 번호로 옛 예약을 가립니다(20). 붙은 틱과 끝나는 틱에 `StatSystem.Recalculate`를 부릅니다. 감속은 이동 예산에 곱하고, 기절 중의 `Move`는 `PositionReset`으로 되돌립니다.
    - 보내는 곳: `SkillCast`와 `SkillCancelled`는 시전자가 보이는 연결에, `SkillUsed`와 `EffectApplied`는 대상(없으면 시전자)이 보이는 연결에 보냅니다. `EffectRemoved`는 시간이 다 되기 전에 떼일 때만 보냅니다(클라이언트는 끝나는 틱을 압니다). `Cooldowns`는 로그인 때 전체를, 그 뒤에는 바뀐 것을 본인에게 보냅니다.
  - **모델**: `FCooldowns`가 스킬마다 끝나는 틱을 가지고 "지금 쓸 수 있는지"와 남은 비율을 답합니다. `UseSkill`을 보낼 때 쿨다운을 미리 돌리고, `SkillFailed`가 오면 되돌리고, `Cooldowns`가 오면 서버의 값으로 맞춥니다. 효과 목록을 개체에 두고, 끝나는 틱이 지난 효과는 `EffectRemoved` 없이 뺍니다. 내게 감속이나 기절이 걸려 있는지를 답합니다.
  - **화면**: 퀵슬롯 버튼과 쿨다운 가림, 시전 바, 효과 아이콘과 남은 시간, 스킬 몽타주, 범위 스킬의 바닥 표시를 둡니다. 모바일은 스킬 버튼입니다. 내게 걸린 감속은 이동 컴포넌트의 최대 속도에, 기절은 입력을 막는 데 반영합니다(반영하지 않으면 걸릴 때마다 `PositionReset`이 납니다).
  - **확인**: 서버 테스트로 쿨다운 중의 요청, 마나 부족, 시전 취소(마나와 쿨다운이 그대로인 것), 시전을 마칠 때 마나가 모자라면 실패하는 것, 시전하는 동안의 다른 `UseSkill`이 실패로 답해지는 것, 시전 중에 방향만 바꾼 `Move`가 취소하지 않는 것, 범위의 경계, 범위 스킬이 다른 플레이어를 맞히지 않는 것, 효과가 끝나는 틱에 능력치가 돌아오는 것, 다시 붙은 효과가 옛 끝나는 틱에 떨어지지 않는 것, 시간이 다 된 효과에는 `EffectRemoved`가 가지 않는 것, 감속과 기절 중의 이동, 기절한 개체가 시야에 새로 들어올 때 효과가 실려 가는 것, 쿨다운이 바뀔 때 본인이 `Cooldowns`를 받는 것을 봅니다. 서버가 만든 쿨다운 비교 벡터로 `FCooldowns`를 검사합니다(5). 엔진 없는 테스트로 끝나는 틱이 지난 효과가 빠지는 것을 봅니다.

  - **서버**: 요청을 처리하는 함수가 결과(`Ok`, `Ignored(이유)`, `Malformed`)를 돌려주고, 끊을지는 한 곳(`World.Receive`)에서 정합니다. 지연 때문에 정상 클라이언트도 보낼 수 있는 것은 `Ignored`로 실패만 알리고(`ActionFailed`, `SkillFailed`), 보낼 수 없는 것만 `Malformed`로 끊습니다. `Session`에 토큰 버킷(초당 채우는 수, 최대)을 두고 입력 차례에서 패킷마다 하나씩 씁니다. 토큰은 지난 틱 수만큼 채웁니다(17). 다 쓰면 그 틱의 나머지 패킷을 버리고, 계속되면 `KICK_REASON_RATE_LIMITED`로 끊습니다(이 이유로 끊긴 클라이언트는 다시 붙지 않습니다. 64). `Move`는 따로 세어, 망이 1초 치를 몰아 전해도 다른 요청의 몫을 쓰지 않게 합니다. 요청 번호를 실은 요청을 버릴 때의 답은 요청 번호가 생기는 32에서 넣습니다. 연결을 받는 쪽에는 IP마다 연결 시도의 빈도 제한을 두어, 로그인하지 않은 연결이 쌓이지 않게 합니다. 부하 봇은 한 IP에서 수천 개를 붙이므로 서버 옵션으로 끌 수 있게 합니다.
  - **클라이언트**: 실패 이유를 받아 HUD에 짧게 알립니다("너무 멉니다", "마나가 부족합니다").
  - **확인**: 서버 테스트로 방금 죽은 대상을 공격해도 끊기지 않는 것, 없는 스킬 번호는 끊기는 것, 패킷을 쏟아붓는 연결의 나머지 패킷이 버려지고 계속되면 `KICK_REASON_RATE_LIMITED`로 끊기는 것, 틱을 건너뛴 뒤 토큰이 지난 틱 수만큼 차는 것, 몰려온 `Move` 20개 뒤의 요청이 버려지지 않는 것, 한 IP에서 짧은 시간에 몰린 연결 시도가 거절되는 것을 봅니다.

- [ ] **32. 인벤토리와 아이템 사용** `M4` — 아이템을 가지고 씁니다.
  - **계약·데이터**: `Items` 테이블(종류, 등급). `Inventory`(로그인할 때 전체), `InventoryChanged`(바뀐 칸들, 골드), `UseItem`(칸, 요청 번호), `RequestResult`(요청 번호, 결과). 300번대. `RequestResult`는 성공과 실패만 알리고, 바뀐 내용은 `InventoryChanged` 같은 다른 패킷이 싣습니다.
  - **서버**: `Inventory`는 60칸 배열이고 칸마다 아이템 번호, 수량, (장비면) 강화 수치입니다. 넣기는 겹칠 수 있는 칸을 먼저 채우고 남으면 빈 칸에 넣으며, 다 들어가지 않으면 아무것도 넣지 않습니다. 바뀐 칸을 표시해 두었다가 시야 차례에 `InventoryChanged` 하나로 보냅니다. 인벤토리를 바꾸는 요청은 연결마다 1씩 느는 요청 번호를 싣고 답(`RequestResult`)은 그 번호로 짝을 짓습니다. `Session`이 마지막 번호를 기억하고, 마지막 번호 + 1이 아닌 요청 번호는 정상 클라이언트가 보낼 수 없으므로 `Malformed`로 끊습니다. 빈도 제한(28)으로 버리는 요청도 번호를 기록하고 `RequestResult`(실패)로 답합니다(답이 없으면 클라이언트가 계속 기다립니다). 번호는 저장하지 않습니다(다시 연결하면 0부터 세고 인벤토리를 처음부터 다시 받습니다). 물약은 체력을 채우고 쿨다운을 걸어 `Cooldowns`(26)로 알립니다. 귀환 주문서는 부활 지점으로 옮기고 25의 방식으로 알립니다.
  - **모델**: `FInventory`가 칸과 골드를 가지고 `Inventory`와 `InventoryChanged`를 반영합니다. 요청 번호를 1씩 올려 붙이고, 답이 올 때까지 그 칸을 "기다리는 중"으로 둡니다.
  - **화면**: 인벤토리 창(칸 그리드, 아이콘, 등급에 따른 이름 색, 겹친 수, 골드), 칸을 눌러 쓰기.
  - **확인**: 서버 테스트로 겹치기와 빈 칸 채우기, 가득 찼을 때 아무것도 들어가지 않는 것, 같은 요청 번호나 건너뛴 요청 번호가 `Malformed`로 끊기는 것, 빈도 제한으로 버려진 요청에 실패 답이 가고 다음 번호가 받아들여지는 것, 물약의 회복과 쿨다운, 귀환 주문서를 봅니다.

- [ ] **33. 드롭과 바닥 아이템** `M4` — 몬스터가 떨어뜨린 것을 줍습니다.
  - **계약·데이터**: `DropGroups` 테이블. 바닥 아이템은 개체(종류 = 바닥 아이템, 템플릿 = 아이템 번호)로 보이고, `EntityEnter`에 수량, 강화 수치, 주인(개체나 파티), 주인만 줍는 시간이 끝나는 틱, 플레이어가 떨어뜨렸는지를 싣습니다. 골드는 `Items`의 골드 줄을 가리킵니다. `PickUp`(개체, 요청 번호), `DropItem`(칸, 수량, 요청 번호).
  - **서버**: `LootSystem`이 죽음 사건을 받아 `DropGroups`의 줄마다 확률을 굴려 `Drop` 개체를 죽은 자리 둘레에 놓습니다. `Drop`은 아이템, 수량, 강화 수치, 주인(플레이어나 파티), 주인만 줍는 시간이 끝나는 틱, 플레이어가 떨어뜨렸는지를 가지고, `Scheduler`에 사라짐을 예약합니다. `PickUp`은 입력 차례에서 온 순서대로 처리하므로 같은 틱의 두 요청 중 먼저 온 것만 성공합니다. 거리, 주인, 인벤토리의 빈 자리를 확인해 인벤토리에 넣고, 남의 것을 고치는 일(바닥 개체 지우기)을 마지막에 합니다(17). `DropItem`은 인벤토리에서 뺀 뒤 바닥 개체를 놓습니다(38이 그 사이에 사본을 저장 큐에 넣는 것을 더합니다). 골드는 떨어뜨릴 수 없습니다. 플레이어가 떨어뜨린 `Drop`은 주인이 떨어뜨린 사람의 파티이고 주인만 줍는 시간이 10초입니다(떨어뜨린 본인도 줍습니다). 파티가 없으면 주인이 없어 바로 누구나 줍습니다. 파티는 42에서 생기므로 그때까지는 늘 주인이 없습니다.
  - **모델**: 바닥 아이템은 개체로 들어오므로 따로 둘 것이 없습니다. 줍기와 떨어뜨리기의 답으로 인벤토리가 바뀝니다.
  - **화면**: 바닥 아이템의 메시와 이름표(아이템 이름, 등급의 색), 가까이에서 줍기 버튼이나 누르기, 얻은 아이템 알림. 인벤토리 창(32)의 칸에서 수량을 골라 떨어뜨리기.
  - **확인**: 서버 테스트로 고정한 씨앗의 드롭, 주인만 줍는 시간, 같은 틱의 두 줍기, 인벤토리가 가득 찼을 때, 시간이 지나 사라지는 것, 강화한 장비를 떨어뜨렸다 주워도 수치가 남는 것, 골드를 주우면 수로 더해지는 것, 골드는 떨어뜨릴 수 없는 것, 플레이어가 떨어뜨린 아이템의 `EntityEnter`에 그 표시가 실리는 것을 봅니다.

  - **서버**: `Equipment`는 6칸 배열입니다. 입을 때 종류와 필요 레벨을 확인하고, 그 칸에 있던 것은 인벤토리의 같은 자리로 바꿔 넣습니다. 끝에 `StatSystem.Recalculate`를 부릅니다.
  - **모델**: `FEquipment`와, 입었을 때 능력치가 얼마나 바뀌는지 미리 보여 주는 비교 함수(테이블의 수치만 더함).
  - **화면**: 장비 창(6칸), 인벤토리에서 끌거나 눌러 입기, 능력치 비교 표시, 무기 메시를 캐릭터의 소켓에 붙이기.
  - **확인**: 서버 테스트로 레벨 미달, 칸이 맞지 않는 아이템, 바꿔 입기, 벗을 자리가 없을 때를 봅니다. 입고 벗을 때 능력치가 바뀌는 것, 다른 연결이 바뀐 무기를 보는 것도 봅니다.

- [ ] **35. 강화** `M4` — 주문서로 장비를 강화합니다.
  - **계약·데이터**: `Enchants` 테이블(단계, 성공 확률, 능력치). `Enchant`(장비의 칸, 주문서의 칸, 요청 번호), `EnchantResult`(성공, 새 수치 또는 파괴).
  - **서버**: `EnchantSystem`이 주문서 하나를 빼고, 안전 수치 아래면 성공, 위면 `Random`으로 굴립니다. 성공하면 수치를 올리고 실패하면 장비를 지웁니다. 주문서 소모와 결과는 한 요청 안에서 정해지므로, 38 뒤에는 같은 사본에 실려 한 트랜잭션으로 쓰입니다. 입고 있는 장비면 능력치를 다시 구합니다. `RequestResult`는 요청이 처리됐는지만 알리고, 강화의 성공과 실패는 `EnchantResult`가 알립니다.
  - **모델**: 단계별 확률을 테이블에서 읽어 화면에 줍니다.
  - **화면**: 강화 창(장비와 주문서 올리기, 성공 확률, 실패하면 사라진다는 경고), 성공과 실패의 연출.
  - **확인**: 서버 테스트로 안전 수치까지의 성공, 고정한 씨앗의 성공과 실패, 실패 뒤 장비가 없는 것, 최대 단계를 봅니다. 10만 번 굴려 확률이 테이블과 맞는지 봅니다.

- [ ] **36. 스킬 배우기** `M4` — 스킬북으로 스킬을 배우고 퀵슬롯에 올립니다.
  - **계약**: `SkillLearned`(스킬), `LearnedSkills`(로그인할 때 배운 것 전체. 데이터 테이블 `Skills`와 이름이 겹치지 않게), `SetQuickslot`(자리, 스킬이나 아이템), `Quickslots`(로그인할 때 전체).
  - **서버**: 스킬북은 32의 아이템 사용으로 처리합니다. 필요 레벨과 이미 배웠는지를 확인하고 배운 스킬 집합에 더한 뒤, `RequestResult`와 함께 `SkillLearned`로 배운 스킬을 알립니다. 26에서 모든 스킬을 배운 것으로 두던 것을 없애고 `UseSkill`이 배운 스킬 집합을 보게 합니다. 퀵슬롯은 자리 → (종류, 번호)의 배열이고 서버는 값을 기억만 합니다.
  - **모델**: 배운 스킬 집합과 퀵슬롯 배열.
  - **화면**: 스킬 창(배운 스킬과 설명), 스킬을 퀵슬롯으로 끌어 올리기, 인벤토리의 물약을 퀵슬롯에 올리기.
  - **확인**: 서버 테스트로 레벨 미달, 이미 배운 스킬(스킬북을 쓰지 않음), 배우지 않은 스킬의 `UseSkill`이 거절되는 것을 봅니다. 퀵슬롯이 다시 들어와도 남는 것은 38에서 봅니다.

- [ ] **37. NPC와 상점** `M4` — 마을의 NPC에게서 사고팝니다.
  - **계약·데이터**: `Npcs`(자리, 역할), `Shops`(상점, 아이템, 가격). NPC는 개체로 보입니다. `Buy`(NPC, 아이템, 수량, 요청 번호), `Sell`(NPC, 칸, 수량, 요청 번호).
  - **서버**: `NpcSystem`이 뜰 때 `Npcs`대로 개체를 둡니다. `ShopSystem`은 NPC와의 거리(`Grid`의 거리 확인), 그 상점이 파는 물건인지, 골드와 빈 자리를 확인합니다. 파는 값은 `Items`의 값입니다. 골드와 아이템은 같은 틱에 함께 바뀝니다.
  - **모델**: 상점의 물건 목록은 테이블에서 읽으므로 패킷으로 받지 않습니다.
  - **화면**: NPC를 누르면 역할에 맞는 창을 엽니다. 상점 창(사기 목록, 내 인벤토리에서 팔기, 수량 고르기).
  - **확인**: 서버 테스트로 멀리서 사기, 골드 부족, 자리 부족, 그 상점에 없는 물건을 봅니다.

- [ ] **38. 캐릭터 저장** `M4` — 캐릭터를 데이터베이스에 남깁니다. [설계: 저장의 흐름](design.md#저장의-흐름)
  - **서버**: 메모리가 원본이고, 데이터베이스를 쓰고 읽는 일은 저장 스레드가 합니다(데이터베이스 일을 시뮬레이션 스레드 밖에 두는 것이 MMO 서버의 일반적인 방식입니다). 지금 있는 위치 저장도 이 경로로 옮깁니다.
    - 저장 스레드와 큐: 틱은 플레이어의 사본을 묶음(사본 목록)으로 `Channel`에 넣기만 하고, 저장 스레드가 들어온 순서대로 묶음 하나를 한 트랜잭션으로 씁니다. 순서가 지켜지므로 내놓은 쪽이 받은 쪽보다 먼저 쓰입니다. 큐가 정한 길이를 넘으면 경고를 남깁니다.
    - 언제 넣나: 플레이어마다 바뀜 표시를 둘 둡니다. 5초 표시(아이템, 골드, 스킬, 퀵슬롯)와 60초 표시(위치, 체력, 경험치)입니다. 저장 차례는 5초마다 5초 표시가 된 플레이어를, 60초마다 60초 표시가 된 플레이어를 묶음 하나로 넣습니다. 아이템을 내놓는 일(`DropItem`. 45부터는 무법자가 죽어서 떨어뜨림도)은 표시가 아니라 처리하는 그 자리에서 사본 하나짜리 묶음을 넣습니다. 순서는 "인벤토리에서 빼기 → 사본을 큐에 넣기 → 바닥 개체 놓기"입니다(도중에 실패하면 잃을 뿐 복사되지 않습니다). 바로 넣는 까닭은, 다른 플레이어가 그것을 주운 뒤 서버가 죽었을 때 아이템이 두 곳에 남지 않게 하려는 것입니다. 플레이어가 월드에서 빠질 때(끊김)도 그 사본을 넣습니다.
    - 무엇을 쓰나: 표시는 언제 쓸지만 정합니다. 사본에는 까닭이 무엇이든 그 플레이어의 바뀐 것 전부(캐릭터의 줄, 아이템, 골드, 스킬, 퀵슬롯, 남은 시간)를 담고 두 표시를 내립니다. 아이템은 바뀐 칸만 씁니다(지우기와 넣기). 쿨다운과 효과는 쓸 때마다 남은 틱 수로 `timers`를 고쳐 쓰고(끝난 것은 지움) 들어올 때 지금 틱에 더합니다(틱 번호는 서버가 다시 뜨면 0부터라 저장하지 않습니다).
    - 저장 형식: `players`에 열을 더하고 `items`, `skills`, `quickslots`, `timers` 테이블을 만듭니다. `PRAGMA user_version`으로 저장 형식의 버전을 두고, 뜰 때 버전이 낮으면 차례로 옮깁니다. 뒤의 항목(44, 47, 48, 50)이 자기 열과 단계를 더합니다.
    - 실패: 쓰기가 실패한 묶음은 건너뛰지 않고 간격을 늘려 가며(최대 1초) 그 자리에서 다시 쓰고, 뒤의 묶음은 그동안 기다립니다(건너뛰면 받은 쪽이 내놓은 쪽보다 먼저 쓰여 복사됩니다). 가장 오래된 묶음이 큐에 들어온 지 10초가 되면 그만두고 서버를 내립니다.
    - 내려가기: 경로는 넷이고, 다시 띄우는 것은 systemd입니다(10).
      - SIGTERM: 접속한 모두의 사본을 넣고 큐를 다 쓰되 10초까지 기다립니다. 넘으면 쓰지 못한 묶음 수를 로그에 남기고 끝냅니다.
      - 큐가 10초 넘게 밀림(위의 실패): 새 사본 없이 끝냅니다. 앞에서부터 쓴 만큼만 남으므로 복사는 없습니다.
      - 틱 차례의 예외(39에서 만듭니다): 틱 루프가 잡아 틱을 멈추고, 새 사본은 만들지 않은 채 큐에 든 것만 쓰고(10초 한도) 0이 아닌 코드로 끝냅니다.
      - 멈춤 감시(39에서 만듭니다. 틱이 10초 넘게 멈춤): `Environment.FailFast`로 끝내고 큐는 버립니다.
    - 로그인: 읽기도 같은 큐에 넣어 저장 스레드가 캐릭터 전체를 읽고, 결과를 틱의 입력 큐로 돌려줍니다. 같은 큐라 그 플레이어의 남은 사본이 다 쓰인 뒤에 읽히고, 틱은 디스크를 기다리지 않습니다. 틱은 "불러오는 중인 ID → 기다리는 연결" 표를 가집니다. 같은 ID의 `Login`이 또 오면 읽기를 다시 넣지 않고 기다리는 연결만 바꿉니다(앞 연결은 `DUPLICATE_LOGIN`으로 끊습니다). 결과가 왔을 때 기다리는 연결이 끊겼으면 결과를 버립니다. 불러오는 중인 연결도 동접 상한에 셉니다. 한 틱에 읽기를 넣는 로그인은 정한 수까지이고 나머지는 다음 틱으로 넘깁니다(서버가 다시 뜬 직후 몰리는 로그인이 틱을 넘기지 않게). 로그인 시간 제한(10초)은 `Login`을 보내기 전까지만 세어, 읽기를 기다리는 연결이 끊기지 않게 합니다. 처음 로그인한 계정에는 처음 상태(`Constants`의 기본 무기, 물약, 첫 스킬)를 줍니다. 죽은 채 빠진 캐릭터는 다음 로그인 때 부활 지점(44 뒤에는 무법자는 무법자의 부활 지점)에서 부활한 상태(체력 일부)로 시작합니다.
    - 넘겨받기: 그 ID의 캐릭터가 이미 메모리에 있으면 읽지 않고, `Player`를 그대로 둔 채 `Session`만 갈아 끼웁니다(지금 코드는 새 개체를 만들고 위치만 옮깁니다). 데이터베이스에서 다시 읽으면 아직 쓰지 않은 변화가 되돌아가기 때문입니다. 개체 번호는 그대로이고, `Ack`와 요청 번호는 0으로 되돌리며, 넘겨받은 연결에 처음 로그인한 것처럼 모든 상태를 다시 보냅니다.
  - **클라이언트**: 없음.
  - **확인**: 서버 테스트로 아래를 봅니다. 사냥하는 봇으로는 저장 차례의 시간(사본을 만드는 시간)과 저장 스레드가 묶음 하나를 쓰는 시간을 잽니다.
    - 남는 것: 다시 들어왔을 때 아이템, 골드, 배운 스킬, 퀵슬롯, 쿨다운의 남은 시간이 모두 남아 있는 것, 옛 버전의 데이터베이스가 옮겨지는 것, 처음 로그인한 계정이 처음 상태를 한 번만 받는 것, 죽은 채 나간 캐릭터가 다음 로그인에 부활 지점에서 부활한 상태로 시작하는 것.
    - 한 트랜잭션: 트랜잭션 도중 실패하면 아무것도 쓰이지 않는 것, 물약 90개를 사고 곧 1개를 떨어뜨린 뒤 서버가 죽어도 산 물약과 낸 골드가 함께 저장되어 있는 것.
    - 순서: 내놓은 아이템을 다른 플레이어가 주운 뒤 주운 쪽이 저장되기 전에 서버가 죽어도 아이템이 두 곳에 있지 않은 것, 쓰기가 한 번 실패했을 때 뒤의 묶음이 먼저 쓰이지 않는 것.
    - 내려가기: SIGTERM을 받으면 큐에 남은 묶음이 모두 쓰이는 것, 쓰기가 계속 실패하면 10초 뒤에 프로세스가 끝나는 것(SIGTERM 뒤에도).
    - 로그인: 접속한 채 다시 로그인해도 방금 얻은 아이템이 남고 이동이 되는 것, 불러오는 중에 같은 ID가 또 로그인해도 캐릭터가 하나이고 앞 연결이 끊기는 것, 불러오는 중에 끊긴 연결의 결과가 버려지는 것, 한 틱의 상한을 넘은 로그인이 다음 틱에 되는 것.
    - 틱 시간: 저장 스레드의 쓰기와 읽기를 일부러 늦춰도 틱 시간이 그대로인 것.

- [ ] **39. 오류 격리** `M4` — 예외 하나가 서버 전체를 깨지 않게 합니다. [설계: 오류와 내려가기](design.md#오류와-내려가기)
  - **계약**: `KickReason`에 `SERVER_ERROR`를 더합니다.
  - **서버**: 예외가 난 곳에 따라 다르게 다룹니다. 프로세스가 끝나면 systemd가 다시 띄웁니다(10).
    - 요청 하나의 예외: 입력 차례에서 요청 하나를 처리하다 난 예외는 잡아 로그를 남기고, 그 플레이어만 버린 뒤 `KICK_REASON_SERVER_ERROR`로 끊습니다. 버릴 때는 메모리 상태를 저장하지 않고(반쯤 적용된 상태일 수 있습니다) 월드에서 바로 빼며, 몬스터의 피해 표와 남의 대상에서 지웁니다(42 뒤에는 파티에서도 지우고, 46 뒤에도 전투 중이라고 남기지 않습니다). 요청 처리는 자기 플레이어의 상태만 고치고 남의 것을 고치는 일은 전투 차례로 넘기거나 마지막에 하므로(17, 33), 다른 개체가 반쯤 고쳐진 채 남지 않습니다. 아이템을 내놓은 요청은 사본이 이미 큐에 들어 있어(38), 같은 틱의 뒤 요청이 예외를 내도 바닥의 아이템과 어긋나지 않습니다.
    - 틱 차례의 예외: 그 밖의 차례에서 난 예외는 월드가 깨졌을 수 있으므로 틱 루프가 잡아 틱을 멈추고, 38의 목록대로 새 사본 없이 큐에 든 묶음만 쓴 뒤 0이 아닌 코드로 끝냅니다. 큐에 든 묶음은 예외 전의 일관된 상태입니다.
    - 멈춤 감시: 틱이 10초 넘게 끝나지 않으면 감시 스레드가 `Environment.FailFast`로 프로세스를 끝내고 덤프를 남깁니다(`DOTNET_DbgEnableMiniDump`). 큐는 버립니다.
  - **클라이언트**: 끊김 알림(16)에 `SERVER_ERROR`의 글("서버 오류로 마지막 저장 상태로 되돌려졌습니다")을 더합니다. 다시 붙는 것은 64에서 합니다.
  - **확인**: 서버 테스트로 요청 처리 중 예외가 나도 다른 연결의 틱이 이어지는 것, 그 연결이 `KICK_REASON_SERVER_ERROR`를 받는 것, 그 플레이어가 다시 들어오면 마지막으로 큐에 넣은 상태인 것, 아이템을 떨어뜨린 틱에 같은 플레이어의 다음 요청이 예외를 내도 다시 들어온 그 플레이어에게 그 아이템이 없는 것, 틱 차례에서 예외가 난 뒤 다시 뜬 서버에 예외 전에 큐에 든 묶음이 쓰여 있는 것, 틱을 일부러 멈췄을 때 감시 스레드가 프로세스를 끝내는 것을 봅니다.

- [ ] **40. 자동 사냥** `M4` — 클라이언트가 사냥을 대신 합니다. [설계: 자동 사냥](design.md#자동-사냥)
  - **서버**: 없음. 손으로 한 것과 같은 패킷이 옵니다.
  - **모델**: `FAutoHunt.Decide(월드 모델, 내 상태)`가 다음에 할 일 하나를 돌려줍니다: 대상 고르기, 다가가기, 스킬 쓰기, 줍기, 물약 쓰기, 기다리기. 대상은 가장 가까운 살아 있는 몬스터이고, 체력이 정한 비율 아래면 물약이 먼저입니다. 바닥 아이템은 플레이어가 떨어뜨린 것(33의 표시)을 빼고, 내가 주울 수 있는 것(주인이 없거나 나이거나, 주인만 줍는 시간이 지난 것)만 고릅니다. 주인이 내 파티인 것은 42에서 더합니다. 상태를 거의 가지지 않는 함수라 월드 모델을 꾸며 테스트합니다.

  - **확인**: 엔진 없는 테스트로 대상이 없을 때, 체력이 낮을 때, 바닥 아이템이 있을 때, 플레이어가 떨어뜨린 아이템은 줍지 않는 것, 남이 주인인 아이템은 시간이 지나야 줍는 것, 인벤토리가 가득 찼을 때의 선택을 봅니다. 자동 사냥으로 10분 돌려 서버에서 끊기지 않는지 봅니다.

  - **서버**: 24의 `CombatSystem.CanAttack`을 플레이어 사이로 넓힙니다. 플레이어가 플레이어를 칠 수 있는 조건은 둘 다 레벨 10 이상이고, 같은 파티가 아니고, 강제 공격 표시가 있고, 대상이 표시 없는 일반 플레이어면 둘 다 안전 지대 밖인 것입니다. 대상에게 선공 표시가 있거나 대상이 무법자면 안전 지대 안에서도 칠 수 있습니다. 기본 공격과 스킬(범위 스킬 포함)이 모두 이 함수를 거칩니다. 선공 표시와 성향은 `PkSystem`이 맡습니다. 일반 플레이어를 먼저 치면 "선공 표시가 끝나는 틱"을 30초 뒤로 두고 `Scheduler`에 끝을 예약합니다(다시 치면 세대 번호로 옛 예약을 가립니다. 20). 끝나는 틱에 표시 상태를 바꿔 이름 색이 돌아온 것을 알립니다. 죽음 사건에서 죽은 쪽이 선공도 무법자도 아니면 죽인 쪽의 성향을 내리고, 몬스터를 잡으면 올립니다. 성향이 0 아래가 되거나 0으로 돌아오면 표시 상태를 바꿉니다. `Karma`는 성향이 바뀔 때와 로그인 때 본인에게 보냅니다. 경비병은 `Monster`와 같은 AI를 쓰되 대상이 "인식 범위의 무법자와 선공 표시"이고, 몬스터와 달리 안전 지대 안으로도 쫓아갑니다. 무법자는 `Zones`의 무법자 부활 지점(마을 밖)에서 부활합니다. 성향, 죽인 수, 선공 표시의 남은 시간(`timers`)을 저장해 다시 들어와도 남게 하고, 그 열과 저장 형식의 단계(`user_version`)를 더합니다(38).
  - **모델**: 개체의 표시 상태로 이름 색을 정하는 함수, 내 성향.
  - **화면**: HUD의 강제 공격 버튼(켜야 플레이어가 대상이 됨), 이름표의 색(흰색, 보라색, 빨간색), 안전 지대 안에서는 버튼이 꺼지는 표시.
  - **확인**: 서버 테스트로 안전 지대, 레벨 10 미만, 파티원, 강제 공격 표시가 없을 때, 범위 스킬이 칠 수 없는 플레이어를 빼는 것, 선공 표시의 시간, 선공자를 죽였을 때 성향이 그대로인 것, 일반 플레이어를 죽였을 때 내려가는 것, 성향이 바뀔 때 본인이 `Karma`를 받는 것, 경비병의 대상, 선공 표시가 있는 채 안전 지대에 들어가도 맞는 것, 무법자의 부활 지점, 서버가 다시 뜬 뒤에도 선공 표시와 성향이 남는 것을 봅니다. 끊긴 캐릭터를 표시가 끝날 때까지 월드에 남기는 것은 46에서 합니다.

- [ ] **47. 채집** `M6` — 필드의 재료를 캡니다.

- [ ] **48. 제작** `M6` — 재료로 물건을 만듭니다.
  - **계약·데이터**: `Recipes` 테이블(결과, 재료와 수량, 골드, 제작 시간, 필요 숙련도. 장비 제작법은 결과의 등급별 확률). 1단계 장비는 제작법 없이 사냥터 1의 드롭(`DropGroups`)으로 둡니다. `Craft`(NPC, 제작법, 요청 번호), `Crafting`(만드는 중인 제작법, 끝나는 틱), `CraftDone`(결과). `Inventory`와 `InventoryChanged`의 칸에 "제작 결과용" 표시를 더합니다.
  - **서버**: `CraftSystem`이 제작 NPC와의 거리(시작할 때만 봅니다), 숙련도, 재료와 골드, 빈 칸 하나를 확인합니다. 제작은 한 번에 하나라, 만드는 중에 `Craft`가 또 오면 실패로 답합니다. 시작할 때 재료와 골드를 빼고, 빈 칸 하나를 "제작 결과용"으로 표시하고(결과가 있던 묶음에 겹칠 수 있어도 빈 칸을 씁니다), "만드는 중인 제작"을 기록하고, `Scheduler`에 완료를 예약하고, `Crafting`을 보냅니다. 표시한 칸은 `Inventory`에 실려 가고, 다른 넣기(줍기, 구매, 벗기, 창고에서 찾기, 퀘스트 보상)는 이 칸을 빈 칸으로 세지 않습니다. 완료할 때 기록과 표시를 지우고 결과를 그 칸에 넣고, 숙련도를 올리고, `CraftDone`과 `Proficiency`(47)를 보냅니다. 장비 제작법은 결과의 등급을 `Recipes`의 확률로 정합니다. 만드는 도중에 나갔거나 서버가 꺼졌으면 다음에 로그인할 때 남은 시간부터 이어서 끝내고, 로그인한 연결에 `Crafting`을 보내 진행 바가 이어지게 합니다. 시작과 완료는 5초 표시입니다(38). 표시한 칸, 만드는 중인 제작(남은 틱 수), 제작 숙련도를 저장하는 열과 저장 형식의 단계를 더합니다. 플레이어를 쓸 때 전부를 한 트랜잭션에 쓰므로 재료와 결과가 갈리지 않습니다.
  - **모델**: 제작법 목록은 테이블에서 읽습니다. 가진 재료로 만들 수 있는지를 답하는 함수, 만드는 중인 제작과 끝나는 틱. `FInventory`가 "제작 결과용" 칸을 빈 칸으로 세지 않습니다(자동 사냥의 "가득 참" 판단도 이것을 씁니다).
  - **화면**: 제작 창(제작법 목록, 필요한 재료와 가진 수, 만들기 버튼, 진행 바).
  - **확인**: 서버 테스트로 재료 부족, 빈 칸이 없을 때, 숙련도, 멀리서의 `Craft`, 만드는 중의 `Craft`가 실패로 답해지는 것, 시작한 뒤 NPC에서 멀어져도 끝나는 것, 제작 중에 인벤토리를 가득 채워도 결과가 들어가는 것, 장비 결과의 등급(고정한 씨앗), 만드는 도중 서버가 다시 떴을 때 다음 로그인에서 결과를 한 번만 받는 것, 만드는 중에 서버가 죽어도 재료와 결과를 둘 다 받지 않는 것을 봅니다.

### M7 최적화와 완성도

끝나면: 한 화면 200명, 송신량 절반, 장애물, 다시 연결이 되고 Unreal 클라이언트가 끝납니다. 최적화(51–57, 59–62, 78–79, 81)는 30으로 잰 수치에서 큰 것부터 하고, 항목마다 전과 후를 `docs/performance.md`에 적습니다. 재 보니 문제가 아닌 항목은 수치만 남기고 하지 않습니다. 다만 52와 79는 다른 항목이 기대므로(55와 78이 52에, 17과 29가 79에) 늘 합니다. 서버 쪽(51–57, 78–81)은 MMO 서버의 일반적인 기술에서 골랐습니다([설계: MMO 서버 기술과 적용 여부](design.md#mmo-서버-기술과-적용-여부)). [설계: 최적화](design.md#최적화)

- [ ] **51. 직렬화 한 번만** `M7` — 같은 개체의 움직임을 보는 사람 수만큼 다시 인코딩하지 않습니다(지금 2,000명에 7.1 ms).
  - **서버**: 움직인 개체마다 `EntityMove`를 그 틱에 한 번만 바이트로 만들어 개체에 둡니다. `ViewSystem`은 연결마다 `EntityMoves`의 머리(틱 번호)를 쓰고 보이는 개체의 바이트를 이어 붙인 뒤 길이를 채웁니다. Protobuf의 반복 필드는 원소를 이어 붙인 것과 같은 바이트라 클라이언트는 바뀌지 않습니다.
  - **클라이언트**: 없음.
  - **확인**: `Contract.Tests`에 이어 붙인 바이트가 원래 방식의 바이트와 같은지를 더합니다. 차례별 측정(29)으로 전과 후를 잽니다.

- [ ] **52. 시야 비교** `M7` — 플레이어마다 집합 전체를 비교하지 않습니다(지금 2,000명에 7.0 ms).
  - **서버**: `Grid`가 칸마다 그 틱에 들어온 개체와 나간 개체의 목록을 가집니다. 칸을 옮기지 않은 연결은 둘레 9칸의 그 목록만 보고 들어옴과 나감을 정하고, 칸을 옮긴 연결만 새로 보이는 칸과 안 보이게 된 칸을 통째로 봅니다. 개체마다 "나를 받은 연결" 목록을 두고 `EntitiesEnter`와 `EntitiesLeave`를 보낼 때 함께 고칩니다. 움직임, 사건, `EntityVitals`, `EntityState`는 칸을 돌지 않고 이 목록으로 보냅니다(사건은 24대로 본인의 연결에도 갑니다). 연결 → 받은 개체의 집합도 남깁니다. 연결이 끊길 때 목록에서 빼는 데 쓰고, 55와 78도 씁니다. 없애는 것은 틱마다 그 집합을 처음부터 다시 모아 비교하는 일입니다.
  - **클라이언트**: 없음.
  - **확인**: 지금 있는 시야 테스트가 그대로 통과합니다. 무작위로 움직인 뒤 옛 방식과 새 방식이 보낸 패킷이 같은지 비교하는 테스트를 더하고, 그 테스트에서 "나를 받은 연결" 목록과 연결이 받은 개체의 집합이 서로 맞는지도 봅니다. 전과 후를 잽니다.

- [ ] **53. 할당과 GC** `M7` — 틱마다 버리는 메모리를 줄입니다(지금 131 MB/s).
  - **서버**: 틱 버퍼를 `ArrayPool<byte>`에서 빌려 보낸 뒤 돌려주고, 틱 안에서 쓰는 목록(질의 결과, 사건)을 틱마다 비워 다시 씁니다. 틱 최대값에서 GC가 차지하는 시간을 `GC.GetTotalPauseDuration`으로 재고, 서버 GC와 워크스테이션 GC, 동시 GC를 켜고 끈 값을 비교합니다. 자료마다 권하는 설정이 달라(작은 프로세스는 워크스테이션 GC가 낫다는 쪽도 있습니다) 이 서버의 부하로 재서 고릅니다. 받기 버퍼도 `ArrayPool`에서 빌립니다.
  - **클라이언트**: 없음.
  - **확인**: 할당량(MB/s), 틱 최대값, GC 멈춤 시간의 전과 후를 적습니다.

- [ ] **54. 이동을 바뀔 때만 알리기** `M7` — 움직이는 개체를 매 틱 보내지 않습니다(지금 클라이언트당 15,354 B/s, 목표는 절반 아래). VPS에서는 CPU가 아니라 송신량이 동접을 정합니다. 일반적인 MMORPG의 방식입니다. 몬스터는 목적지와 속도를 한 번 알리고(WoW의 `SMSG_MONSTER_MOVE`), 플레이어는 출발, 방향 바뀜, 멈춤과 주기적인 확인만 알립니다(WoW의 `MSG_MOVE_START_FORWARD`, `MSG_MOVE_STOP`, `MSG_MOVE_HEARTBEAT`). M2에서는 지금 서버의 방식(매 틱 위치, 13의 보간)으로 만들고 여기서 바꿉니다(2026-11-10 정함). 전과 후의 송신량을 남기려는 것이고, 클라이언트에서 고치는 곳은 엔진 없는 `FEntityTrack`과 `MoveSender`입니다.
  - **계약**: `EntityMove`에 속도(방향의 `yaw` 칸과 빠르기, 0은 멈춤)와 목적지(몬스터용)를 싣는 필드를 더합니다. `EntityEnter`에도 지금의 속도와 목적지를 싣습니다. 클라이언트가 보내는 `Move`에 움직이는 중인지를 싣습니다. 서버가 "이번 틱에 `Move`가 없음"으로 멈춤을 알 수는 없기 때문입니다(TCP가 몰아 전하거나 프레임이 낮으면 걷는 중에도 빕니다). 패킷의 뜻이 바뀌므로 `PROTOCOL_VERSION_CURRENT`를 올립니다. `Move`를 보내는 주기(초당 20번)는 그대로 둡니다. 서버가 그 위치로 사거리를 판정합니다.
  - **서버**: 플레이어의 `Move`는 지금처럼 매번 받아 검증합니다(서버의 위치는 늘 정확합니다). 보는 쪽에는 아래의 틱에만 알립니다. 알릴지의 기준이 연결이 아니라 개체라 51의 "한 번만 인코딩"과 함께 되고, 시야에 새로 들어온 연결은 `EntityEnter`로 지금의 위치와 속도를 받습니다.
    - 플레이어: 출발한 틱, 방향이 8칸(약 11도) 넘게 바뀐 틱, 멈춘 틱에 알리고, 움직이는 동안은 10틱마다 확인을 보냅니다. 속도의 방향은 `Move.yaw`이고 빠르기는 최대 속도 × 감속입니다. 출발과 멈춤은 `Move`의 움직이는 중 표시로 압니다. 움직이는 중인 플레이어에게서 `Move`가 10틱 넘게 없거나 `Session`이 떨어지면(46) 멈춘 것으로 알립니다. 방향이 바뀐 알림은 개체마다 4틱에 한 번까지입니다.
    - 몬스터: `AiSystem`이 이동을 시작한 틱, 목적지가 바뀐 틱(10틱에 한 번까지), 사거리에 들거나 대상을 잃어 멈춘 틱에 "지금 위치, 목적지, 속도"를 알립니다. 추적의 목적지는 대상의 위치가 아니라 대상에서 사거리만큼 앞의 점입니다.
    - 서버가 속도나 위치를 바꾼 틱: 늘 알립니다. 기절과 감속이 붙은 틱과 끝난 틱(26의 예약), 죽은 틱, `PositionReset`으로 되돌린 틱, 순간 이동한 틱(25의 표시)입니다.
  - **모델**: `FEntityTrack`이 기록 사이는 보간하고, 마지막 기록 뒤로는 그 속도로 이어 그립니다. 몬스터는 목적지에서 멈춥니다. 새 기록이 오면 이어 그린 위치에서 새 위치로 몇 틱에 걸쳐 섞어 튀지 않게 합니다. 움직이는 개체의 확인이 1초 넘게 오지 않으면 이어 그리기를 멈춥니다. 13의 "기록 사이가 벌어지면 옛 위치를 끼워 넣는" 규칙과 "앞질러 그리지 않는다"는 규칙을 없애고, 멈춤은 빠르기 0으로 압니다. 순간 이동 표시가 있는 기록은 섞지 않고 바로 옮깁니다. `MoveSender`는 움직이는 중인지를 싣고, 그 표시가 바뀌면 위치가 같아도 보냅니다(12의 "같은 값이면 보내지 않는다"가 멈춤을 막지 않게).
  - **화면**: 없음.
  - **확인**: 서버 테스트로 곧게 걷는 플레이어가 출발과 10틱마다의 확인만 가는 것, 방향을 바꾸거나 멈춘 틱에 가는 것, 매 틱 방향을 바꿔도 4틱에 한 번만 가는 것, 움직이는 중에 `Move`가 10틱 넘게 끊기거나 `Session`이 떨어지면 멈춤이 가는 것, 몬스터가 이동을 시작할 때와 목적지를 바꿀 때(10틱에 한 번까지)와 사거리에 들거나 대상을 잃어 멈출 때 가는 것, 추적의 목적지가 대상에서 사거리만큼 앞인 것, 기절이나 감속이 걸린 틱과 끝난 틱, 되돌려진 틱에 가는 것, 나중에 들어온 연결이 속도를 받는 것을 봅니다. 엔진 없는 테스트로 이어 그린 위치가 다음 확인의 위치와 가까운 것, 새 기록이 왔을 때 튀지 않는 것, 서버가 조용할 때 멈추는 것, 표시만 바뀐 멈춤 `Move`를 `MoveSender`가 보내는 것을 봅니다. 곧게 걷는 봇, 방향을 자주 바꾸는 봇, 사냥하는 봇마다 클라이언트당 송신량의 전과 후, 월 GB, VPS의 동접을 적습니다.

- [ ] **55. 시야 인원 상한** `M7` — 사람이 몰려도 연결 하나에 보내는 양에 끝이 있게 합니다. 사람이 몰리는 게임이 쓰는 표시 캐릭터 수 제한입니다.
  - **계약**: 사건 패킷(`Damaged`, `SkillUsed`, `Died` 같은 것)의 개체 번호 0이 "이 연결이 받지 않은 개체"를 뜻하게 됩니다. 패킷의 뜻이 바뀌므로 `PROTOCOL_VERSION_CURRENT`를 올립니다.
  - **서버**: 연결마다 보낼 다른 플레이어 수의 상한을 둡니다. 상한은 200 이상입니다(59의 목표가 한 화면 200명입니다). 넘으면 파티원, 나를 공격하는 캐릭터, 내 대상을 먼저 넣고 나머지는 가까운 순으로 채웁니다. 가까운 순은 정렬하지 않고 칸을 가까운 것부터 돌아 근사합니다. 이미 보이는 캐릭터를 새로 온 캐릭터보다 먼저 두어 상한의 경계에서 들어옴과 나감이 되풀이되지 않게 합니다. 빠진 캐릭터는 `EntitiesLeave`로 알리고, 자리가 나면 `EntitiesEnter`로 다시 보냅니다. 78을 했으면 여유 목록에 있는 캐릭터도 상한에 셉니다. 몬스터와 바닥 아이템에는 상한을 두지 않습니다. 상한이 걸린 연결만 누구를 보낼지 다시 고릅니다. 사건(피해, 스킬, 효과, 죽음)은 대상(맞은 쪽, 효과가 붙은 쪽, 죽은 쪽. 대상이 없으면 행위자)을 받은 연결에 보내고(52의 목록), 그 연결이 받지 않은 다른 쪽의 번호는 0으로 싣습니다.
  - **모델**: 사건의 번호가 0이면 개체를 찾지 않고 대상 쪽의 결과(체력, 피해 숫자, 피격 반응)만 반영합니다.
  - **화면**: 설정(77)의 "표시할 캐릭터 수"로 서버가 보낸 것 가운데 가까운 순으로 그릴 수를 더 줄일 수 있습니다(59).
  - **확인**: 서버 테스트로 상한을 넘을 때 파티원과 공격자가 남는 것, 상한의 경계에서 같은 캐릭터가 들어옴과 나감을 되풀이하지 않는 것, 내가 받지 않은 캐릭터가 내가 받은 캐릭터를 쳤을 때 `Damaged`가 공격자 번호 0으로 오는 것, 내가 받지 않은 캐릭터가 맞은 사건은 오지 않는 것, 빠진 캐릭터의 주변 채팅(41)이 오는 것을 봅니다. 엔진 없는 테스트로 번호 0인 사건이 대상 쪽의 결과만 바꾸는 것을 봅니다. 봇 500명을 한 칸에 모아 틱 시간과 송신량을 전과 후로 잽니다. 상한에서의 최악 송신량, 월 GB, VPS의 동접을 재서 남깁니다.

- [ ] **56. 몬스터 재우기** `M7` — 아무도 없는 곳의 몬스터는 계산하지 않습니다.
  - **서버**: `Grid`가 칸마다 "둘레 9칸의 플레이어 수"를 가지고 플레이어가 칸을 옮길 때만 고칩니다. 끊긴 채 남은 캐릭터(46)도 이 수에 셉니다. `AiSystem`은 그 수가 0인 칸의 몬스터를 건너뜁니다. 잠드는 몬스터가 움직이는 중이었으면 멈춤을 알려(54) 보는 쪽이 이어 그리지 않게 합니다. 자는 동안 복귀 중이던 몬스터는 깨어날 때 자리로 옮기고 체력을 채웁니다. 깨어난 몬스터의 "다음 인식 틱"은 17의 방식대로 `다음 += 주기`를 지금 틱을 넘을 때까지 되풀이해 맞춥니다. 그래야 함께 깨어난 몬스터의 인식이 한 틱에 몰리지 않습니다.
  - **클라이언트**: 없음.
  - **확인**: 서버 테스트로 플레이어가 다가오면 깨어나는 것, 자는 동안 리스폰이 예약대로 되는 것, 함께 깨어난 몬스터들의 인식 틱이 엇갈려 있는 것을 봅니다. 몬스터 5,000마리에 플레이어 100명일 때 몬스터 차례의 시간을 전과 후로 잽니다.

- [ ] **57. 저장 다듬기** `M7` — 저장 스레드(38)가 쓰는 양과 시간을 줄입니다.
  - **서버**: 저장 스레드의 큐 길이, 가장 오래된 묶음이 기다린 시간, 묶음 하나를 쓰는 시간을 10초 로그에 찍습니다. WAL 체크포인트가 저장 스레드에서 돌게 하고 걸리는 시간을 잽니다. 바뀐 칸만 쓰는 것은 38에서, 준비한 문장을 다시 쓰는 것은 지금 코드(`PlayerStore`)에서 이미 합니다.
  - **클라이언트**: 없음.
  - **확인**: 사본을 만드는 시간, 묶음 하나를 쓰는 시간, 큐의 가장 긴 길이, 체크포인트에 걸리는 시간을 전과 후로 잽니다. 38의 저장 테스트가 그대로 통과합니다.

- **58. 시야 차례를 여러 코어로** — 넣지 않습니다(2026-11-10). 같은 방식을 쓰는 MMO 서버를 찾지 못했습니다. 51과 52 뒤에도 틱 시간이 모자라면 [규모를 넘으면](design.md#규모를-넘으면)의 차례를 따릅니다.

- [ ] **78. 시야 경계의 흔들림** `M7` — 칸의 경계를 오가는 개체가 들어옴과 나감을 되풀이하지 않게 합니다. 29의 패킷 종류별 수에서 들어옴과 나감의 몫이 작으면 수치만 남기고 하지 않습니다.
  - **서버**: 지금은 둘레 3×3칸에 들어오면 보이고 벗어나는 틱에 사라집니다. 경계선 위를 걷는 개체는 틱마다 `EntitiesEnter`(이름과 상태를 다 실은 큰 패킷)와 `EntitiesLeave`를 번갈아 냅니다. 나가는 기준을 들어오는 기준보다 넓게 둡니다. 3×3칸을 벗어난 개체는 연결의 "여유 목록"으로 옮기고, 3×3칸의 바깥 테두리에서 8 m 넘게 멀어졌을 때 `EntitiesLeave`를 보냅니다. 그 전에 되돌아오면 아무것도 보내지 않습니다. 틱마다 거리를 재는 것은 여유 목록의 개체뿐입니다. 52의 "칸에 들어오고 나간 목록" 방식 위에 얹습니다. 여유 목록의 개체는 "나를 받은 연결" 목록(52)에 남아 있으므로 움직임, 사건, 상태(피해, 죽음, 효과, 체력)가 계속 갑니다. 보는 쪽이 칸을 넘을 때 생기는 들어옴과 나감도 같은 봇 측정에서 재고, 크면 "보는 쪽의 중심 칸도 새 칸으로 8 m 넘게 들어갔을 때 바꾼다"를 넣습니다(재서 정함).
  - **클라이언트**: 없음.
  - **확인**: 서버 테스트로 여유 안에서 되돌아오면 들어옴이 다시 가지 않는 것, 여유를 넘으면 나가는 것, 여유에 있는 개체의 움직임이 계속 오는 것, 여유에 있는 동안 맞은 개체가 돌아왔을 때 체력이 맞는 것을 봅니다. 경계선을 따라 오가는 봇과 칸을 넘나드는 봇으로 `EntitiesEnter`와 `EntitiesLeave`의 수와 바이트를 전과 후로 잽니다.

- [ ] **79. 틱이 밀릴 때** `M7` — 틱이 50 ms를 넘어도 게임 시간이 실제 시간을 따라가게 합니다. [설계: 과부하 때](design.md#과부하-때)
  - **계약**: `EntityMoves`의 틱 번호가 1씩 오르지 않게 됩니다. `packets.proto`의 "틱마다 1씩 오른다"는 주석을 고치고, 패킷의 뜻이 바뀌므로 `PROTOCOL_VERSION_CURRENT`를 올립니다.
  - **서버**: 밀린 틱을 몰아서 돌리지 않고, 틱 루프가 틱 번호를 지난 시간만큼 건너뜁니다(100 ms가 걸렸으면 2). 시스템은 17에서부터 (지금 틱, 지난 틱 수)를 받으므로 고치지 않습니다. 지난 틱 수만큼 진행하는 계산(몬스터 이동, 이동 예산, 28의 토큰 채우기)은 그만큼 진행하고, 주기로 하는 일(회복, 인식, 저장, 로그)은 밀려도 한 번만 하며, "끝나는 틱"으로 둔 것(쿨다운, 효과, 예약한 일)은 지금 틱과 비교하므로 그대로 맞습니다. 지난 시간만큼 진행하는 MMORPG 서버의 루프와 같은 동작이고, 게임 시간을 늦추지 않습니다. 건너뛴 틱 수는 29의 10초 로그에 찍힙니다.
  - **모델**: `FServerClock`은 받은 틱 번호로 서버의 지금 틱을 어림하므로 번호가 건너뛰어도 실제 시간과 맞습니다. 13의 멈춤 기준(4틱)보다 크게 건너뛰면 끊겨 보일 수 있고, 54 뒤에는 멈춤을 속도로 알므로 없어집니다.
  - **화면**: 없음.
  - **확인**: 서버 테스트(건너뛴 수를 주입)로 두 틱을 건너뛴 틱에서 몬스터가 두 틱 치를 가는 것, 쿨다운이 실제 시간에 끝나는 것, 제 속도로 걷는 플레이어가 되돌려지지 않는 것, 건너뛴 틱 뒤에 1초마다의 회복, 5틱마다의 인식, 60초 저장이 한 번씩 돌고 다음 차례가 제때 오는 것을 봅니다. 봇을 한도 넘게 붙여 틱이 60 ms가 되게 한 뒤 되돌림(`PositionReset`)의 수가 늘지 않는지 봅니다.

- [ ] **80. 접속 대기열** `M7` — 동접 상한을 넘은 로그인을 거절하지 않고 줄을 세웁니다.
  - **계약**: `LoginResultCode`에 대기 중을 더하고, 순번을 알리는 `QueuePosition`(세션 범위)을 둡니다. `LoginResult`가 두 번 올 수 있고(대기 중, 그 뒤 OK) OK가 아닌 결과 뒤에도 연결이 이어지게 되므로 `PROTOCOL_VERSION_CURRENT`를 올립니다.
  - **서버**: 상한을 넘으면 연결을 끊지 않고 `LoginResult`(대기 중)를 보내 대기열에 넣습니다. 자리가 나면 줄 선 순서대로 `LoginResult`(OK)를 보내 로그인을 이어 가고(38의 틱당 로그인 상한 안에서), 순번은 5초마다 `QueuePosition`으로 알립니다. 대기 중인 연결도 `Ping`에 답하고 무응답이면 끊습니다. 로그인 시간 제한(10초)은 `Login`을 보내기 전까지만 세므로(38) 줄 선 연결은 끊기지 않습니다. 대기열의 길이에도 상한을 두어 넘으면 지금처럼 `SERVER_FULL`로 거절합니다. 같은 ID의 재로그인(넘겨받기)과 끊긴 채 남은 캐릭터(46)의 주인은 줄을 서지 않고 바로 들어갑니다(그 캐릭터는 이미 상한에 세어 있습니다). 같은 ID가 줄에 두 번 서면 38의 불러오는 중과 같이 앞의 연결을 `DUPLICATE_LOGIN`으로 끊고 새 연결이 그 자리를 잇습니다.
  - **모델**: 대기 중 상태와 순번은 `World/`의 엔진 없는 코드가 가지고, `LoginResult`(OK)가 오면 평소의 로그인 뒤처럼 이어 갑니다. `UMmoSession`은 패킷을 전달만 합니다.
  - **화면**: 로그인 화면에 순번을 보이고 취소 버튼을 둡니다.
  - **확인**: 서버 테스트로 자리가 날 때 줄 선 순서대로 들어가는 것, 대기 중에 끊긴 연결이 줄에서 빠지는 것, 대기열이 가득 찼을 때의 거절, 가득 찬 서버에서 같은 ID의 재로그인이 바로 들어가는 것, 같은 ID가 줄에 두 번 섰을 때 앞 연결이 끊기는 것, 줄 선 연결이 10초 뒤에 끊기지 않는 것을 봅니다. 엔진 없는 테스트로 대기 중에서 OK로 넘어가는 것을 봅니다.

- [ ] **81. 큰 패킷 압축** `M7` — 큰 버퍼만 압축해 보냅니다. 29의 패킷 종류별 바이트에서 큰 버퍼의 몫이 작으면 수치만 남기고 하지 않습니다.
  - **계약**: 압축한 프레임들을 싣는 `Compressed`(세션 범위)를 둡니다. 풀린 크기를 싣고 그 크기에 상한을 둡니다. `Compressed` 안의 `Compressed`는 받지 않습니다. 옛 클라이언트는 모르는 패킷을 건너뛰므로 `PROTOCOL_VERSION_CURRENT`를 올립니다.
  - **서버**: 한 틱에 한 연결로 가는 버퍼가 정한 크기(처음 값 1,024바이트, 재서 정함)를 넘을 때만 zlib 형식(`ZLibStream`, 가장 빠른 단계. Unreal의 zlib 풀기가 머리를 요구합니다)으로 보내기 작업에서 압축해 `Compressed` 하나로 보냅니다. 작은 버퍼는 압축해도 줄지 않아 그대로 보냅니다. 대상은 로그인할 때의 인벤토리와 한꺼번에 들어오는 개체 목록입니다.
  - **모델**: `Compressed`를 풀어 안의 프레임들을 차례로 처리합니다(Unreal은 엔진의 zlib, 엔진 없는 테스트는 시스템의 zlib).
  - **화면**: 없음.
  - **확인**: 압축했다 푼 프레임이 원래와 같은지, 문턱보다 작은 버퍼는 압축하지 않는지, 풀린 크기가 상한을 넘거나 겹친 `Compressed`를 받지 않는지 봅니다. 로그인할 때와 사람이 몰린 곳에 들어설 때의 바이트, 보내기 작업의 CPU를 전과 후로 잽니다.

- [ ] **64. 다시 연결** `M7` — 끊겨도 이어서 합니다. [설계: 세션](design.md#세션)
  - **서버**: 넘겨받기와 모든 상태를 다시 보내는 것은 38에서, 남아 있는 캐릭터는 46에서 이미 만듭니다. 여기서는 그 뒤에 더한 상태가 다시 보내는 목록에 빠지지 않았는지 확인합니다: 입은 장비, 경험치, 죽음, 효과와 쿨다운, 파티, 성향, 숙련도, 만드는 중인 제작, 퀘스트.
  - **모델**: 다시 붙을지와 간격은 엔진 없는 코드(`World/ReconnectPolicy`)가 정하고 `UMmoSession`은 그 답대로 연결만 합니다. 뜻하지 않게 끊겼을 때 다시 붙습니다. 내가 닫았거나 `Kicked`의 이유가 중복 로그인, 잘못된 패킷, `RATE_LIMITED`(28)면 다시 붙지 않습니다. 서버가 내려갈 때, 무응답으로 끊길 때, `SERVER_ERROR`(39)일 때는 `Kicked`가 와도 다시 붙습니다. 간격은 1초부터 두 배씩 늘려 30초까지이고 2분 동안 시도합니다(배포로 서버가 다시 뜨는 시간보다 길어야 합니다). 다시 붙으면 월드 모델을 비우고 새로 받습니다. 답을 기다리던 요청은 버립니다(결과는 새로 받은 인벤토리에 있습니다). 다시 붙다 대기열(80)에 서면 2분 한도를 세지 않고 순번을 보입니다.
  - **화면**: 다시 붙는 동안 "다시 연결하는 중" 알림을 띄우고 조작을 막습니다. `SERVER_ERROR`로 끊겼으면 39의 알림도 함께 띄웁니다. 2분 동안 붙지 못하면 로그인 화면으로 갑니다.
  - **확인**: 엔진 없는 테스트로 간격의 계산과 `Kicked`의 이유마다 다시 붙는지를 봅니다. 서버를 잠깐 멈추거나 Wi-Fi를 껐다 켜서 이어지는지 봅니다. 중복 로그인이나 `RATE_LIMITED`로 끊겼을 때는 다시 붙지 않는 것, `SERVER_ERROR`로 끊겼을 때 알림과 함께 다시 붙는 것, 죽은 채 남아 있는 캐릭터를 넘겨받으면 사망 화면이 뜨는 것을 봅니다.

- [ ] **65. 맵 원본과 장애물** `M7` — 필드에 벽과 바위를 둡니다. [설계: 공간](design.md#공간)
  - **계약·데이터**: 맵 원본을 `data/`의 한 파일로 둡니다(1 m 칸마다 걸을 수 있는지). 서버와 두 클라이언트가 같은 생성물을 읽습니다.
  - **서버**: `MovementSystem`이 지난 위치에서 새 위치까지의 선이 막힌 칸을 지나면 `PositionReset`으로 되돌립니다. 공격과 스킬도 같은 선 검사로 벽 너머의 대상을 막고, 범위 스킬은 중심에서 선이 막힌 대상을 뺍니다. `AiSystem`은 대상까지 곧은 선이 막혔을 때만 그 격자에서 A*로 길을 찾고, 그 몬스터가 찾은 자기 길을 몇 틱 동안 따라갑니다(몬스터 사이에 경로를 나눠 쓰는 캐시는 두지 않습니다). 찾는 길이에 상한을 두어(추적 한계 안의 칸 수) 한 번의 길찾기가 틱을 오래 잡지 않게 하고, 상한 안에 길이 없으면 추적을 그만둡니다.
  - **모델**: 같은 격자로 "갈 수 있는가"를 답해 내 캐릭터가 막힌 칸으로 들어가지 않게 합니다.
  - **화면**: 맵 원본에서 장애물의 충돌 상자와 보이는 메시를 놓는 에디터 도구를 둡니다. 맵을 손으로 따로 놓지 않습니다.
  - **확인**: 서버 테스트로 벽을 지나는 이동이 되돌려지는 것, 몬스터가 벽을 돌아가는 것, 상한 안에 길이 없으면 복귀하는 것, 벽 너머의 대상을 칠 수 없는 것을 봅니다. 서버와 모델이 같은 좌표에 같은 답을 내는지 비교 벡터로 봅니다(5).

  - **계약**: `GuildCreate`, `GuildInvite`, `GuildAnswer`, `GuildLeave`, `GuildState`, `GuildWarDeclare`. 표시 상태에 길드 번호를 더합니다. 400번대.
  - **서버**: `GuildSystem`과 `guilds`, `guild_members`, `guild_wars` 테이블. 길드는 접속하지 않은 길드원도 있으므로 데이터베이스가 원본이고, 접속한 길드원만 메모리에 올립니다. 두 길드가 서로 선언하면 전쟁 상태이고, `PkSystem`이 죽음 사건에서 두 쪽이 전쟁 중인 길드면 성향을 내리지 않습니다. 길드 채팅은 `ChatSystem`의 채널 하나입니다.
  - **모델**: 내 길드, 길드원, 전쟁 중인 길드의 목록.
  - **화면**: 길드 창(만들기, 길드원, 초대, 전쟁 선언), 이름표의 길드 이름, 전쟁 중인 길드원의 이름 색.
  - **확인**: 서버 테스트로 한쪽만 선언했을 때(전쟁 아님), 전쟁 중의 죽음과 성향, 길드장이 나갈 때를 봅니다. Unreal에서 만든 뒤 Unity로 옮깁니다.

## 마일스톤

마일스톤 하나가 끝나면 그때까지를 시연할 수 있습니다.

| 단계 | 끝나면 되는 것 | 항목 |
| --- | --- | --- |
| M1 기반 | 서버에 로그인한다 (끝남) | 1–3, 6, 8–9 |
| M2 함께 걷기 | 휴대폰과 PC의 Unreal 클라이언트가 Live 서버의 같은 필드에서 서로 걷는 것을 본다 | 10–16, 71 |
| M3 사냥 | 몬스터를 스킬로 잡고, 죽고, 부활한다. 성능을 재기 시작한다 | 4–5, 17–30, 72–74 |
| M4 성장과 아이템 | 드롭을 줍고, 장비를 입고 강화하고, 상점을 쓰고, 다시 들어와도 남아 있다. 자동 사냥이 된다 | 31–40, 75–77 |
| M5 함께 하고 겨루기 | 파티로 보스를 잡고, 다른 플레이어와 싸우고, 죽으면 잃는다 | 41–46 |
| M6 생활 | 채집해서 만들고, 퀘스트의 안내를 따라간다 | 47–48, 50 |
| M7 최적화와 완성도 | 한 화면 200명, 송신량 절반, 장애물, 다시 연결. Unreal 클라이언트가 끝난다 | 51–57, 59–68, 78–81 |
| M8 Unity | Unity 클라이언트가 같은 서버에서 Unreal 클라이언트와 함께 논다. 시연 자료를 만든다 | 7, 69 |
| M9 나중 | 길드와 길드전(두 클라이언트 모두) | 70 |

- 항목 하나는 계약·데이터 → 서버 → 모델 → 화면 → 확인 순서로 합니다. 서버와 모델은 worktree 세션에서 병렬로 할 수 있고, 화면은 메인 체크아웃에서 한 번에 하나씩 합니다.
- M2의 순서는 71 → 11 → 12 → 16 → 13 → 10 → 15이고, 14는 12 뒤 어느 때든 합니다. 13이 16의 이름표 층을 씁니다. 15의 확인이 Live 서버를 쓰므로 배포(10)가 먼저입니다.
- M3은 서버의 구조(17)를 먼저 나누고 데이터(4)를 붙인 뒤 번호 순서로 갑니다. 29는 17 뒤 어느 때든 하고, 30의 사냥하는 봇은 24와 26 뒤에 합니다. 72(콘텐츠의 양과 수치)는 23 앞에, 73(에셋 목록)은 18의 화면과 함께, 74(문자열)는 4 바로 뒤에 합니다.
- M4는 번호 순서이고 75–77은 38 뒤에 합니다(76은 37 뒤 어느 때든).
- M7의 서버 최적화는 51 → 52 → 78 → 54 → 55 → 53 → 56 → 57 → 81 → 79 → 80을 기본 순서로 하되, 30으로 잰 수치에서 큰 것부터 합니다. 52와 79는 건너뛰지 않습니다.
- Unity 클라이언트(7)는 Unreal 클라이언트가 M7까지 다 끝난 뒤에 시작합니다.
- 65(장애물)는 이동 검증과 몬스터 이동을 다시 건드리므로 평지로 M6까지 간 뒤에 합니다.
- 쓰는 기술과 고른 이유는 [설계의 기술 선택](design.md#기술-선택)에 있습니다. 만들면서 다른 것을 고르면 그 표와 이 목록을 함께 고칩니다.
