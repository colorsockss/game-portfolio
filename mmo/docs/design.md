# MMORPG 게임 설계

MMORPG 포트폴리오(`mmo/`)가 어떤 게임이고 각 시스템을 어떻게 만들지 적은 문서입니다. 무엇을 언제 만드는지는 [backlog.md](backlog.md)에, 이미 만든 것의 실제 구조와 규칙은 [MANUAL](../MANUAL.md)에 있습니다. 만들면서 이 문서와 달라지면 이 문서를 고칩니다.

## 방향

**리니지 라이크에 생활 콘텐츠 한 줄기를 더한 MMORPG**입니다(2026-11-10 정함).

**클라이언트 포트폴리오입니다**(2026-11-10 정함). 서버는 프로세스 하나로 두고, 화면보다 서버의 일이 큰 콘텐츠(거래소)는 넣지 않습니다. 서버에서는 MMO라서 꼭 해야 하는 것(서버 판정, 시야, 저장)과 그 최적화(틱 시간, 송신량, 사람이 몰린 곳)까지 합니다.

- 열린 필드에서 대상을 정해 몬스터를 잡고, 장비를 얻고 강화해 강해집니다.
- 마을 밖에서는 다른 플레이어를 공격할 수 있고(PK), 그 대가로 성향과 사망 페널티가 있습니다.
- 채집한 재료로 물약과 장비를 만듭니다.

조준형 액션(검은사막 방식)은 고르지 않았습니다. 그 난이도는 애니메이션에 맞춘 판정과 큰 월드에 있고 둘 다 에셋에 달려 있는데, 이 저장소는 직접 만든 것이나 CC0만 넣습니다. TCP와 20Hz 틱, 서버 판정, 많은 인원이 한 필드에 있는 구조는 대상 지정 전투와 맞습니다.

### 흐름

```
사냥 → 경험치·골드·아이템 → 레벨·장비·강화 → 더 센 사냥터·필드 보스
                     ↑                               ↓
채집 → 제작 ──────────┘                    PK(사냥터와 보스의 경쟁)
```

### 넣는 것

| 영역 | 콘텐츠 |
| --- | --- |
| 월드 | 걸어서 이어지는 필드 하나(마을, 사냥터 3곳, 채집지, 보스 자리), 안전 지대 |
| 전투 | 대상 지정 기본 공격, 스킬(피해, 범위, 강화, 상태 이상, 회복), 자동 사냥 |
| 몬스터 | 일반 몬스터(선공·비선공), 필드 보스 |
| 성장 | 레벨, 장비 6칸, 강화(확률과 파괴), 스킬 배우기 |
| 아이템 | 등급, 인벤토리와 창고, 소모품, 바닥에 떨어지는 드롭, NPC 상점 |
| 함께 | 채팅, 파티 |
| 겨루기 | PK, 성향, 사망 페널티, 경비병 |
| 생활 | 채집, 제작 |
| 안내 | 퀘스트(잡기, 모으기, 만들기, 레벨, 장비) |
| 나중(우선순위 가장 낮음) | 길드와 길드전 |

### 범위 밖

- 운영과 이벤트: 우편, 공지, 출석, 이벤트, 랭킹, 쿠폰, 운영자 도구
- 결제, 광고, 외부 SDK. 로그인은 텍스트 ID입니다.
- 서버 선택, 채널, 인스턴스 던전, 서버 프로세스 여러 개(로그인 서버나 채팅 서버를 따로 두는 것 포함)
- 캐릭터 생성과 꾸미기, 직업 여러 개
- 원거리 직업과 발사체, 명중·회피·치명타, 무게
- 친구 목록, 변신, 인형, 컬렉션
- 거래소와 개인 거래. 화면은 목록 하나인데 서버의 일(매물, 정산, 무결성)이 커서 뺐습니다. 아이템은 바닥에 떨어뜨려 건넬 수 있습니다
- 공성전, 탈것, 펫
- 낚시, 하우징, 무역
- 조준형 액션 전투, 높이가 있는 지형
- 월드를 여러 존으로 나눠 따로 계산하기(포털로 잇는 존, 경계에 개체의 사본을 두는 심리스 존). 필드 하나를 한 스레드가 계산합니다

## 구조 원칙

- **서버가 판정합니다.** 전투, 성장, 아이템은 서버만 계산하고 클라이언트는 입력을 보내고 결과를 보여 줍니다. 이동만 클라이언트가 위치를 정하고 서버가 속도와 범위를 검증합니다(되돌림은 `PositionReset`).
- **월드는 틱 스레드 하나만 읽고 고칩니다.** 잠금이 없고, 한 틱 안의 확인과 쓰기는 늘 한 동기 구간입니다. 소켓 쪽은 큐에 넣고 꺼내기만 합니다. 줍기처럼 여럿이 같은 것을 노리는 요청도 틱 안에서 들어온 순서대로 처리해 한 명만 성공합니다.
- **시간은 틱 번호로 셉니다.** 쿨다운, 시전, 버프, 리스폰, 선공 표시는 모두 "끝나는 틱"으로 가지고, 데이터의 밀리초는 읽을 때 틱 수(올림)로 바꿉니다. 시스템은 시계를 읽지 않고 틱 번호만 받으므로 틱을 손으로 돌리는 테스트가 됩니다.
  - **틱이 밀리면** 틱 루프가 번호를 건너뛰어 실제 시간을 따라갑니다([과부하 때](#과부하-때)). 번호를 올리는 것은 틱 루프뿐이고, 시스템은 처음부터 (지금 틱, 지난 틱 수)를 받습니다.
  - **지난 틱 수만큼 진행하는 계산**은 몬스터 이동, 이동 예산, 요청 빈도 제한의 토큰 채우기입니다.
  - **주기로 하는 일**(1초마다의 회복, 5틱마다의 인식, 5초와 60초의 저장)은 나머지 연산이 아니라 "다음에 할 틱 ≤ 지금 틱"으로 봅니다. 나머지 연산은 번호가 배수를 건너뛰면 그 주기를 통째로 놓칩니다. 밀려도 한 번만 하고, `다음 += 주기`를 지금 틱을 넘을 때까지 되풀이해 위상을 지킵니다. 엇갈림은 처음의 `다음 = 번호 % 주기`로 주고, 잠들었다 깨어난 몬스터도 같은 식으로 맞춥니다.
  - **저장할 때**: 틱 번호는 서버가 다시 뜨면 0부터라 저장하지 않습니다. 남은 틱 수로 바꿔 쓰고 읽을 때 지금 틱에 더합니다(쿨다운, 효과, 선공 표시, 만드는 중인 제작). 접속을 끊어도 남은 시간이 줄지 않습니다.
- **난수는 서버만 굴립니다.** 피해, 드롭, 강화의 난수는 서버가 주입받은 `Random`에서 나오고, 테스트는 씨앗을 고정합니다.
- **기능 하나를 세로로 끝냅니다.** 계약(`packets.proto`) → 데이터 테이블 → 서버와 서버 테스트 → Unreal의 엔진 없는 코드와 테스트 → Unreal 화면 순서입니다. 서버와 엔진 없는 코드는 엔진 없이 테스트합니다.
- **계약은 `packets.proto` 하나입니다.** 패킷 번호는 기능마다 범위 하나를 쓰고([패킷 범위](#패킷-범위)), 서버와 두 클라이언트가 맞춰야 하는 수는 `Constant` enum 값입니다. 값이 같은 상수를 더할 때는 enum에 `allow_alias`를 켭니다.
- **필드 위의 것은 모두 같은 개체입니다.** 플레이어, 몬스터, NPC, 채집물, 바닥 아이템이 개체 번호 공간, 시야 칸, `EntitiesEnter`·`EntitiesLeave`·`EntityMoves`를 함께 씁니다.
- **수치는 데이터에 둡니다.** 몬스터, 스킬, 아이템, 레벨, 확률, 시간은 `data/`의 xlsx가 원본이고 서버와 두 클라이언트가 같은 생성물을 읽습니다. 코드에는 틱 수 같은 구조의 상수만 둡니다. 이 문서의 수치는 처음 넣을 값이고 테이블에서 고칩니다. data-tool이 생성물 전체의 해시를 내고 클라이언트가 `Login`에 실어 보내, 서버의 것과 다르면 로그인을 거절합니다. 프로토콜 버전은 패킷만 보므로, 데이터만 바뀐 배포에서 옛 클라이언트가 틀린 상점과 쿨다운을 보이는 것을 막습니다.
- **클라이언트는 연결 → 세션과 월드 모델 → 화면으로 나눕니다.** 패킷은 월드 모델에 먼저 반영하고, 화면(액터, 위젯)은 그것을 읽기만 합니다. 월드 모델과 판단 코드(보간, 쿨다운, 자동 사냥)는 엔진 타입 없는 코드라 엔진 없이 테스트하고, Unity로 옮길 때 그대로 C#이 됩니다.
- **다른 개체는 서버 틱 번호로 보간합니다.** TCP가 패킷을 몰아서 전해도 `EntityMoves.tick`의 간격으로 다시 펴고, 두 틱(100 ms) 늦게 그립니다(M2부터의 방식이고, M7에서 이동을 바뀔 때만 알리게 바꾸면 기록 뒤를 속도로 이어 그립니다). 클라이언트는 `LoginResult`, `Pong`, `EntityMoves`에 실린 틱 번호와 받은 때로 서버의 지금 틱을 어림하고, 쿨다운과 시전의 남은 시간도 그것으로 그립니다. 순간 이동(귀환, 부활)은 표시를 달아 보내, 보간하지 않고 바로 옮깁니다. 옮겨진 본인에게는 `PositionReset`을 보냅니다(내 개체는 `EntityMoves`에 들어가지 않습니다).
- **저장은 틱 밖의 저장 스레드가 합니다.** 틱은 플레이어의 사본을 묶어 큐에 넣기만 하고, 저장 스레드가 들어온 순서대로 묶음 하나를 한 트랜잭션으로 씁니다. 규칙은 [저장의 흐름](#저장의-흐름)에 있습니다.

## 기술 선택

무엇을 쓰고 왜 쓰는지, 무엇을 고르지 않았는지입니다. **상태**가 "있음"인 것은 이미 만들어져 있고 근거 수치는 [MANUAL](../MANUAL.md)에 있습니다. "계획"은 만들 때 확인하고, 달라지면 이 표를 고칩니다.

### 서버

| 무엇에 | 쓰는 것 | 이유 | 고르지 않은 것 | 상태 |
| --- | --- | --- | --- | --- |
| 언어 | C#(.NET 10) | Unity 클라이언트와 같은 생성 코드(`Packets.cs`)를 씁니다. 봇 2,000명의 틱이 15.4 ms라 예산(50 ms) 안입니다 | UnrealSharp로 Unreal까지 C#으로 맞추기(접음, Unreal은 C++) | 있음 |
| 동시성 | 틱 스레드 하나 + 연결마다 받기·보내기 작업, `ConcurrentQueue`로 넘김 | 월드를 한 스레드만 고쳐 잠금과 경쟁 상태가 구조에서 없습니다. 틱 계산은 한 코어로 충분하고 소켓만 여러 코어를 씁니다 | 존마다 스레드(걸어서 이어지는 필드를 나누면 경계 근처 개체의 사본과 넘겨주기가 필요함. 잰 한도가 목표보다 커서 나눌 까닭이 없음) | 있음 |
| 틱 | 20Hz 고정(`PeriodicTimer`) | 대상 지정 전투는 50 ms 판정이면 충분하고, 송신량은 틱 수에 비례합니다 | 30·60Hz(송신량 1.5–3배) | 있음 |
| 전송 | TCP(`NoDelay`), 한 틱의 패킷을 한 버퍼로 | 순서와 재전송을 만들지 않아도 됩니다. TCP/IP 머리(52바이트)가 패킷마다가 아니라 틱마다 붙습니다 | UDP와 직접 만든 신뢰 계층(손실 있는 망에서 낫지만 만들고 검증할 것이 많음. 패킷 형식이 전송과 따로라 나중에 바꿀 수 있음) | 있음 |
| 직렬화 | Protobuf 36.2(길이 구분 형식) | 정의 하나에서 protoc가 C#과 C++을 만들고, 필드를 더해도 옛 쪽이 건너뜁니다. 대가는 개체 하나 15바이트(고정 크기 9바이트보다 송신 +58%) | 직접 만든 고정 크기 형식(9바이트, 생성기를 유지해야 해서 지움), MessagePack(12바이트) | 있음 |
| 좌표 | 1/32 m 정수(zigzag varint), 방향 256칸 | 실수 대신 정수라 작고, 서버와 두 클라이언트의 값이 비트까지 같습니다 | `float` 좌표 | 있음 |
| 시야 | 32 m 격자, 둘레 3×3칸, 지난 틱과 비교해 들어옴·나감·움직임만 보냄 | 모든 쌍을 비교하지 않고 칸 안만 봅니다. 움직이지 않은 개체는 보내지 않습니다 | 쿼드트리(매 틱 움직이는 개체는 쪼개고 합치는 비용이 듦. 읽은 서버는 모두 격자나 정렬 리스트를 쓰고, 트리는 움직이지 않는 지형에 씀) | 있음 |
| 느린 연결 | 연결마다 상한 있는 `Channel`(40틱) | 따라오지 못하는 클라이언트가 서버 메모리를 끝없이 쓰지 않게 2초 넘게 밀리면 끊습니다 | 상한 없는 큐 | 있음 |
| 끊김 감지 | `Ping`/`Pong` 5초, 15초 무응답이면 끊음 | TCP는 망이 바뀐 휴대폰의 끊김을 몇 분 동안 알려 주지 않습니다. 비용은 연결 하나에 약 11 B/s | TCP keepalive(시간이 OS마다 다름) | 있음 |
| 저장 | SQLite(WAL). 틱은 사본의 묶음을 큐에 넣고 저장 스레드가 묶음 하나를 한 트랜잭션으로 씀 | 같은 VPS에서 프로세스와 비용을 더하지 않습니다. 데이터베이스 일을 시뮬레이션 스레드 밖에 두는 것이 MMO 서버의 일반적인 방식입니다(TrinityCore, Albion, Photon) | PostgreSQL·Redis(서버 프로세스 여러 개가 데이터를 나눠 써야 하면 다시 고름), 틱 스레드에서 쓰기(지금 코드. 2,000명의 위치 저장이 4.8 ms이지만 디스크가 느린 순간에 틱이 멈춤) | 틱 스레드에서 쓰는 것만 있음 |
| 시간과 난수 | 틱 번호, 주입한 `Random` | 시계를 읽지 않아 쿨다운·리스폰·확률을 틱을 손으로 돌려 테스트합니다 | 벽시계 타이머 | 계획 |
| 코드 구조 | 월드(개체와 격자) 하나와, 그것을 고치는 시스템 클래스들을 정해진 차례로 부름 | 기능마다 파일이 나뉘고, 차례가 고정이라 같은 입력에 같은 결과가 납니다 | ECS(개체 종류가 다섯뿐이고 고정이라 클래스 계층이 더 단순함), 기능을 `World` 하나에 모두 넣기 | 계획 |
| 예약한 일 | 쓸 때만 보면 되는 것(쿨다운, 전투 상태)은 개체의 "끝나는 틱" 필드, 끝나는 틱에 할 일이 있는 것(효과와 선공 표시의 끝, 리스폰, 드롭 사라짐)은 틱 번호의 우선순위 큐 | 쓸 때만 확인하는 것은 틱마다 드는 비용이 없고, 큐에서는 때가 된 것만 꺼냅니다 | 일마다 `Task.Delay`나 타이머(틱 스레드 밖에서 월드를 건드리게 됨) | 계획 |

## 서버 구조

MMORPG 서버가 해야 하는 일과 그것을 이 서버가 어떻게 하는지입니다. 지금 있는 뼈대(연결, 틱, 이동, 시야, 저장)의 실제 규칙은 [MANUAL의 서버](../MANUAL.md#서버)에 있고, 여기에는 콘텐츠가 들어가며 넓어질 구조를 적습니다.

### MMO 서버 기술과 적용 여부

MMO 서버에서 흔히 쓰는 최적화 기술을 조사해(2026-11-10) 넣을 것과 넣지 않을 것을 갈랐습니다. 오픈소스 MMO 서버(TrinityCore, L2J, rAthena, KBEngine)의 소스와 설정, 커뮤니티가 정리한 패킷 정의(테라), 엔진 문서(Unreal, Photon, BigWorld), Microsoft 문서, 책(ithare, Game AI Pro)을 읽은 결과입니다. "흔한 정도"는 몇 개의 자료가 쓰는지로 매겼습니다. GDC와 NDC의 발표는 읽지 못했습니다.

| 실행 | 동접 상한과 접속 대기열, 연결 시도 빈도 제한 | 핵심 | 상한은 있음. 대기열과 빈도 제한은 할 것 |
| 실행 | 요청 빈도 제한(토큰 버킷) | 핵심 | 할 것 |
| 실행 | 실행 중 지표와 멈춤 감시 | 흔함 | 지표는 있음(넓힘). 멈춤 감시는 할 것 |
| 실행 | 맵마다 스레드 | 흔함 | 넣지 않음. 필드가 하나 |
| 저장 | 메모리가 원본, 주기와 사건으로 저장 | 핵심 | 있음(위치만). 캐릭터 저장에서 넓힘 |
| 저장 | 저장을 시뮬레이션 스레드 밖에서 | 핵심 | 할 것(캐릭터 저장을 만들 때부터) |
| 저장 | 아이템 복사 방지(내놓은 쪽을 먼저 씀) | 흔함 | 할 것 |
| 측정 | 봇 부하 측정 | 핵심 | 있음(넓힘) |

### 프로세스와 스레드

프로세스 하나가 월드 하나를 가집니다.

```
받기 작업(연결마다) ──┐                         ┌── 보내기 작업(연결마다)
받기 작업            ─┼→ 큐 → [ 틱 스레드 ] → ─┼── 보내기 작업
연결 받기            ─┘      월드를 혼자 고침    └── 저장 스레드
```

- **받기**: 연결마다 비동기 작업이 프레임을 읽어 패킷으로 만들고 큐에 넣기만 합니다. 월드는 건드리지 않습니다.
- **틱 스레드**: 20Hz로 돌며 월드를 혼자 읽고 고칩니다. 게임의 모든 판정이 여기서 납니다.
- **보내기**: 틱이 만든 버퍼를 연결마다 비동기 작업이 보냅니다. 느린 연결은 그 연결의 큐만 밀립니다.
- 받기와 보내기는 여러 코어를 쓰고(2,000명에 1.7코어), 틱 계산은 한 코어입니다(2,000명에 15.4 ms).

프로세스를 나누지 않는 이유는 둘입니다. 필드가 하나이고 잰 한도(이동만으로 약 6,000명)가 목표(시연 서버의 동접 수백 명)보다 큽니다. 그리고 클라이언트 포트폴리오라 서버 사이의 일을 만들지 않습니다. 넘으면 어떻게 나누는지는 [규모를 넘으면](#규모를-넘으면)에 있습니다.

실제 MMORPG는 서버를 나눕니다(2026-11-10 조사). 여기서는 그 일들이 한 프로세스 안에 있습니다.

| 본 것 | 나눈 서버 | 여기서는 |
| --- | --- | --- |
| 리니지2 공식 서버([커뮤니티의 설정 자료](https://www.cnblogs.com/kt007/p/10308435.html)) | 인증, 게임, 데이터베이스 캐시, 몬스터 AI, 로그 | 로그인은 게임 서버의 첫 패킷, 저장은 저장 스레드(틱은 사본을 큐에 넣음), 몬스터는 틱의 한 차례 |
| Albion Online([2016년 발표](https://www.slideshare.net/slideshow/albion-online-software-architecture-of-an-mmo-talk-at-quo-vadis-2016-berlin/62724504)) | 로그인, 게임(구역마다), 월드(길드·파티), 거래소, 채팅 | 게임 서버가 하나라 파티와 채팅이 같은 프로세스에 있고, 거래소는 없음 |

### 틱의 차례

한 틱은 늘 같은 차례로 돕니다. 차례가 고정이라 같은 입력이면 같은 결과가 나고, 테스트가 틱을 손으로 돌릴 수 있습니다.

| 차례 | 하는 일 |
| --- | --- |
| 1. 입력 | 큐의 일(연결, 패킷, 끊김, 저장 스레드가 돌려준 불러오기 결과)을 들어온 순서대로 꺼내 검증하고 처리합니다. 이동, 대상 정하기, 인벤토리 요청이 여기서 반영됩니다. 스킬 요청은 검증과 비용까지만 처리합니다 |
| 2. 예약한 일 | 때가 된 일을 꺼냅니다: 시전이 끝난 스킬(발동은 전투 차례로 넘김), 끝난 효과, 다시 나올 몬스터와 채집물, 사라질 바닥 아이템 |
| 3. 몬스터 | 몬스터의 상태(대기, 추적, 공격, 복귀)를 진행합니다. 둘레에 플레이어가 없는 몬스터를 재우는 것은 M7에서 넣습니다 |
| 4. 전투 | 공격 간격이 된 기본 공격을 치고, 앞의 차례가 넘긴 스킬을 발동하고, 피해를 적용하고, 죽음을 처리합니다(경험치, 드롭, 성향, 퀘스트) |
| 5. 회복과 효과 | 체력과 마나를 채웁니다(1초마다). 효과는 여기서 떼지 않고, 끝을 예약해 2번 차례에서 뗍니다([예약한 일](#예약한-일)) |
| 6. 시야 | 플레이어마다 지난 틱과 비교해 들어옴·나감·움직임을 보내고, 이번 틱의 사건(스킬 사용, 피해, 효과, 죽음)을 사건의 대상을 받은 연결에 넣습니다([전투](#전투)의 결과) |
| 7. 저장 | 5초와 60초의 표시가 된 플레이어의 사본을 묶어 저장 스레드의 큐에 넣습니다(내놓는 요청은 입력 차례에서, 무법자가 죽어서 떨어뜨린 것은 전투 차례에서 이미 넣음. [저장의 흐름](#저장의-흐름)) |
| 8. 보내기 | 연결마다 이번 틱의 패킷을 한 버퍼로 만들어 보내기 큐에 넣습니다 |

입력 차례의 요청은 자기 플레이어의 상태만 고칩니다. 다른 개체를 고치는 결과(피해, 죽음, 효과 붙이기)는 전투 차례로 넘깁니다. 줍기처럼 입력 차례에서 남의 것을 고쳐야 하는 요청은 그 일을 마지막에 합니다(줍기: 인벤토리에 넣기 → 바닥 개체 지우기). 요청을 처리하다 난 예외가 그 플레이어만 버리고 끝날 수 있는 까닭입니다([오류와 내려가기](#오류와-내려가기)).

### 코드의 구조

- **월드**: 개체(번호 → 개체)와 격자(칸 → 개체 목록)를 가집니다. 플레이어의 번호는 다시 쓰지 않습니다. 몬스터와 채집물은 놓인 자리마다 번호가 정해져 있어 다시 나올 때 같은 번호를 쓰고, 바닥 아이템은 사라진 지 10초가 지난 번호를 다시 씁니다. 번호가 작아야 varint가 짧습니다(200만을 넘으면 개체 하나가 2바이트 늘어 송신량이 약 13% 늡니다).
- **개체**: `Entity`(번호, 위치, 칸) → `Creature`(체력, 능력치, 효과, 전투 상태) → `Player`, `Monster`, `Npc`. 채집물과 바닥 아이템은 `Entity`에서 바로 갈립니다.
- **시스템**: 이동, 전투, 몬스터, 드롭, 인벤토리, 파티, PK, 채집, 제작, 채팅, 퀘스트가 각각 클래스 하나입니다. 월드의 데이터를 고치는 코드만 있고 자기 상태는 거의 없습니다.
- **시스템 사이**: 묻는 것(칠 수 있는가, 구역이 어디인가)과 자기 개체의 능력치 재계산은 직접 부릅니다. 다른 시스템의 상태를 바꾸는 결과만 틱 안의 사건으로 잇습니다. 전투가 "죽음"을 내면 성장(경험치), 드롭, PK(성향), 퀘스트가 그것을 받습니다. 사건은 그 틱 안에서 차례대로 처리하고 다음 틱으로 넘기지 않습니다.
- **데이터**: 테이블은 서버가 뜰 때 읽어 바꾸지 않는 객체로 둡니다. 데이터를 바꾸려면 서버를 다시 띄웁니다.

### 예약한 일

- 개체에 붙은 것(쿨다운, 효과, 선공 표시, 전투 상태)은 "끝나는 틱"을 필드로 가집니다. 쿨다운과 전투 상태는 쓸 때만 비교하므로 틱마다 드는 비용이 없습니다.
- 효과는 끝나는 틱에 할 일이 있어(능력치를 다시 구하고, 이동을 바뀔 때만 알리게 된 뒤에는 바뀐 속도도 알림) 끝을 아래의 큐에도 예약합니다. 같은 효과를 다시 걸어 끝나는 틱이 바뀌면 효과의 세대 번호를 올리고, 꺼낸 예약의 번호가 지금 것과 다르면 버립니다. 선공 표시도 끝나는 틱에 이름 색이 바뀐 것을 알려야 하므로 같은 방식으로 예약합니다.
- 월드의 일(리스폰, 바닥 아이템 사라짐)은 끝나는 틱이 키인 우선순위 큐에 넣고, 틱마다 때가 된 것만 꺼냅니다.
- 같은 틱의 일은 넣은 순서대로 꺼냅니다. .NET의 `PriorityQueue`는 그 순서를 지키지 않으므로 (틱, 넣은 순번)을 키로 씁니다.

### 공간

- 32 m 격자 하나를 시야, 범위 스킬의 대상 찾기, 몬스터의 인식, 줍기와 NPC의 거리 확인에 함께 씁니다.
- 원 안의 개체를 찾을 때는 원이 걸친 칸만 보고, 칸 안에서 거리를 잽니다.
- 장애물이 생기면 걸을 수 있는지를 적은 1 m 격자를 더합니다. 이동 검증은 지난 위치에서 새 위치까지의 선이 막힌 칸을 지나는지 보고, 몬스터는 그 격자에서 A*로 길을 찾습니다. 공격과 스킬도 공격자에서 대상까지의 선이 막힌 칸을 지나면 되지 않고, 범위 스킬은 중심에서 선이 막힌 대상을 뺍니다.

### 요청 검증

클라이언트가 보내는 것은 "하고 싶은 것"뿐이고, 되는지는 서버가 봅니다.

| 확인하는 것 | 예 |
| --- | --- |
| 순서와 상태 | 로그인 전의 요청, 죽었거나 기절한 동안의 요청 |
| 거리 | 스킬의 사거리, 줍기, NPC, 채집물 |
| 가진 것 | 아이템과 수량, 골드, 배운 스킬, 마나 |
| 시간 | 쿨다운, 공격 간격, 물약 쿨다운, 이동 속도 예산 |
| 관계와 구역 | 안전 지대, 레벨 10 미만, 파티원, 드롭의 주인 |
| 빈도와 크기 | 초당 패킷 수(토큰 버킷), 채팅 간격, 패킷 256바이트 |

어긋난 요청은 셋으로 나눕니다.

- **무시**: 지연 때문에 정상 클라이언트도 보낼 수 있는 것(방금 죽은 대상을 공격, 이미 주운 아이템을 줍기)은 실패를 알리고 넘어갑니다.
- **되돌림**: 이동이 어긋나면 `PositionReset`으로 서버의 위치를 알립니다.
- **끊기**: 정상 클라이언트가 보낼 수 없는 것(읽을 수 없는 패킷, 서버가 보내는 패킷, 없는 스킬 번호)은 `KICK_REASON_MALFORMED_PACKET`으로 끊습니다. 빈도 제한을 계속 넘는 연결은 `KICK_REASON_RATE_LIMITED`로 끊고, 클라이언트는 다시 붙지 않습니다.

요청 번호를 실은 요청은 버릴 때도 실패라는 답을 보냅니다. 답이 없으면 클라이언트가 그 칸을 계속 기다립니다. `Move`는 빈도 제한에서 따로 세어, 망이 몰아서 전한 `Move`가 다른 요청의 몫을 쓰지 않게 합니다.

### 세션

- **로그인**: 텍스트 ID입니다. 실제 서비스라면 인증 서버가 준 토큰을 여기서 검증하지만 범위 밖입니다. 그래서 시연 서버에서는 남의 ID를 아는 사람이 그 캐릭터로 들어올 수 있습니다. 알고 두는 대가이고 README에 적습니다.
- **같은 ID**: 새 연결이 예전 연결을 끊습니다(`KICK_REASON_DUPLICATE_LOGIN`). 지금은 새 개체를 만들고 위치만 옮깁니다(있음). 캐릭터 저장이 들어가면 메모리의 캐릭터를 그대로 두고 연결만 갈아 끼웁니다(넘겨받기). 끊긴 뒤 월드에 남아 있는 캐릭터도 같은 ID로 로그인하면 넘겨받습니다. 데이터베이스에서 다시 읽으면 아직 쓰지 않은 변화가 되돌아가기 때문입니다. 개체 번호가 그대로라 몬스터의 대상, 파티, 남이 정한 대상이 이어지고, `ack`와 요청 번호는 새 연결에 맞춰 0부터 시작합니다. 넘겨받은 연결에는 처음 로그인한 것처럼 인벤토리와 주변 개체를 비롯한 모든 상태를 다시 보냅니다. 캐릭터를 불러오는 중에 같은 ID가 또 로그인하는 경우는 [저장의 흐름](#저장의-흐름)의 읽기에 있습니다.
- **대기열을 건너뛰는 로그인**: 넘겨받는 로그인(같은 ID의 재로그인, 끊긴 채 남은 캐릭터의 주인)은 [대기열](#과부하-때)에 서지 않고 바로 들어갑니다. 남아 있는 캐릭터는 동접 상한에 셉니다.
- **끊김**: 15초 동안 아무것도 오지 않으면 끊습니다(있음). 전투 상태이거나 선공 표시가 남은 채 끊긴 캐릭터는 그것이 끝날 때까지 월드에 남아 맞습니다. 끊어서 죽음을 피하지 못하게 하려는 것입니다. 남아 있는 동안 기본 공격은 멈춥니다.
- **로그아웃**: 클라이언트가 나가겠다고 보내면 전투 상태가 아니고 선공 표시도 없을 때 바로 저장하고 닫습니다. 둘 중 하나라도 남아 있으면 끊긴 것과 같이 그것이 끝날 때까지 캐릭터가 남습니다.
- **죽은 채 빠진 캐릭터**: 다음 로그인 때 부활 지점(무법자는 무법자의 부활 지점)에서 부활한 상태(체력의 일부)로 시작합니다. 페널티는 죽을 때 이미 적용됐습니다.
- **몰리는 로그인**: 한 틱에 처리하는 로그인 수에 상한을 두고 나머지는 다음 틱으로 넘깁니다. 상한은 불러오기를 저장 큐에 넣을 때 셉니다. 로그인 시간 제한(10초)은 `Login`을 보내기 전까지만 셉니다(미뤄진 로그인과 대기열의 연결이 끊기지 않게).
- **다시 들어와도 남는 것**: 쿨다운, 효과, 선공 표시, 성향은 저장되어 남습니다. 접속을 끊어 표시나 쿨다운을 지울 수 없습니다.

### 저장의 흐름

- **메모리가 원본입니다.** 로그인할 때 캐릭터를 읽어 메모리에 두고, 틱은 메모리만 읽고 고칩니다. 데이터베이스는 서버가 죽어도 남기려는 것입니다.
- **큐와 저장 스레드**: 틱은 플레이어의 사본을 큐에 넣기만 하고 디스크를 기다리지 않습니다. 큐의 단위는 묶음(사본의 목록)이고, 저장 스레드가 들어온 순서대로 묶음 하나를 한 트랜잭션으로 씁니다. 지금 코드는 틱 스레드에서 쓰고, 캐릭터 저장을 만들 때 옮깁니다.
- **언제 넣나**: 플레이어마다 바뀜 표시를 둘(5초, 60초) 둡니다. 표시를 기다리지 않고 그 자리에서 넣는 경우가 둘 있습니다.

| 바뀐 것 | 큐에 넣는 때 |
| --- | --- |
| 아이템, 골드, 스킬, 퀵슬롯, 퀘스트, 제작(줍기, 사용, 강화, 상점, 창고에 맡기기와 찾기, 제작의 시작과 완료, 퀘스트 보상) | 5초 표시. 저장 차례가 5초마다 표시된 플레이어들의 사본을 한 묶음으로 넣음 |
| 위치, 체력, 경험치 | 60초 표시. 저장 차례가 60초마다 표시된 플레이어들의 사본을 한 묶음으로 넣음 |
| 아이템을 내놓는 일(떨어뜨리기, 무법자가 죽어서 떨어뜨림) | 처리하는 그 자리에서 사본 하나짜리 묶음으로 넣음 |
| 나갈 때(로그아웃, 끊긴 캐릭터가 월드에서 빠질 때) | 그 자리에서 사본 하나짜리 묶음으로 넣음 |

- **내놓는 순서**: 인벤토리에서 빼기 → 사본을 큐에 넣기 → 바닥 개체 놓기입니다. 도중에 실패하면 아이템을 잃을 뿐 복사되지 않습니다.
- **무엇을 쓰나**: 플레이어를 쓸 때는 까닭이 무엇이든 그 플레이어의 바뀐 것 전부(캐릭터의 줄, 아이템, 골드, 스킬, 퀵슬롯, 퀘스트, 남은 시간)를 쓰고, 사본을 넣을 때 두 표시를 내립니다. 칸마다 따로 쓰면 "물약 90개를 사고 1초 뒤 1개를 떨어뜨린 틱"에 물약 칸만 저장되어, 그때 서버가 죽으면 물약은 남고 골드는 깎이지 않습니다.
- **내놓는 일만 바로 넣는 까닭**: 아이템이 복사되는 것은 내놓은 쪽이 저장되지 않은 채 주운 쪽만 저장되고 서버가 죽을 때뿐입니다. 내놓은 쪽의 사본이 먼저 큐에 들어가고 큐는 들어온 순서대로 쓰이므로, 주운 쪽이 먼저 저장되는 일이 없습니다. 혼자 얻고 쓰는 변화는 늦게 써도 서버가 죽으면 잃을 뿐 복사되지 않습니다. 그래서 5초로 모아 사냥 중에 매 틱 트랜잭션이 돌지 않게 합니다.
- **쓰기가 실패하면**: 실패한 묶음은 건너뛰지 않고 간격을 늘려 가며(최대 1초) 그 자리에서 다시 쓰고, 뒤의 묶음은 기다립니다. 건너뛰면 내놓은 쪽보다 주운 쪽이 먼저 쓰여 아이템이 복사됩니다. 가장 오래된 묶음이 큐에 들어온 지 10초가 되면 그만두고 서버를 내립니다. 저장하지 못하는 서버가 계속 도는 것보다 낫습니다. 큐의 길이는 10초마다의 로그에 찍고, 정한 길이를 넘으면 경고합니다.
- **읽기**: 로그인의 불러오기도 같은 큐에 넣어 저장 스레드가 읽고, 결과를 틱의 입력 큐로 돌려줍니다. 같은 큐라 그 플레이어의 남은 사본이 다 쓰인 뒤에 읽히고, 틱은 디스크를 기다리지 않습니다.
  - 틱은 "불러오는 중인 ID → 기다리는 연결" 표를 가집니다. 같은 ID의 `Login`이 또 오면 읽기를 다시 넣지 않고 기다리는 연결만 바꿉니다(앞 연결은 `KICK_REASON_DUPLICATE_LOGIN`으로 끊음).
  - 결과가 왔을 때 기다리던 연결이 끊겼으면 결과를 버립니다.
  - 그 ID의 캐릭터가 이미 메모리에 있으면 읽지 않고 넘겨받습니다([세션](#세션)).
  - 불러오는 중인 연결도 동접 상한에 셉니다.
- **내려갈 때**: 경로는 넷이고 경로마다 큐를 다르게 다룹니다. 까닭은 [오류와 내려가기](#오류와-내려가기)에 있습니다.

| 경로 | 새 사본 | 큐에 든 묶음 |
| --- | --- | --- |
| SIGTERM | 모두의 사본을 넣음 | 다 쓰되 10초까지 기다림. 넘으면 쓰지 못한 묶음 수를 로그에 남기고 끝냄 |
| 틱 차례의 예외 | 만들지 않음 | 든 것만 쓰고(10초 한도) 0이 아닌 코드로 끝냄 |
| 큐가 10초 넘게 밀림(쓰기 실패) | 만들지 않음 | 쓰기를 그만두고 끝냄. 앞에서부터 쓴 만큼만 남으므로 복사는 없음 |
| 멈춤 감시(틱이 10초 넘게 멈춤) | 만들지 않음 | 버림(`Environment.FailFast`) |

- **서버가 죽으면** 마지막으로 커밋한 묶음까지의 상태로 돌아갑니다. 아이템과 골드는 보통 5초 치, 위치·체력·경험치는 60초 치까지 잃습니다. 바닥을 거친 아이템은 사라질 수는 있어도 두 곳에 남지 않습니다.

### 오류와 내려가기

- **요청 하나의 예외**: 그 플레이어만 버리고 `KICK_REASON_SERVER_ERROR`로 끊고 로그를 남깁니다. 클라이언트는 다시 붙되 되돌려졌다고 알립니다. 그 플레이어의 메모리 상태는 저장하지 않습니다. 반쯤 적용된 상태일 수 있기 때문이고, 다음 로그인은 마지막으로 큐에 넣은 사본에서 시작합니다. 버린 캐릭터는 전투 중이어도 월드에 남기지 않고, 몬스터의 피해 표, 파티, 남의 대상에서 지웁니다. 입력 차례의 요청은 자기 플레이어의 상태만 고치므로([틱의 차례](#틱의-차례)) 다른 플레이어에게 번지지 않습니다. 떨어뜨린 아이템은 사본이 이미 큐에 들어 있어 바닥의 아이템과 어긋나지 않습니다.
- **틱 차례의 예외**: 요청 처리 밖(예약한 일부터 보내기까지의 차례)에서 난 예외는 틱 루프가 잡아 틱을 멈추고 서버를 내립니다. 월드가 깨졌을 수 있기 때문입니다. 골드는 뺐고 아이템은 아직 주지 않은 중간일 수 있어, 새 사본을 만들어 저장하면 깨진 상태가 굳습니다. 큐에 이미 든 묶음은 일관된 상태이므로 그것까지는 씁니다. 깨진 상태로 계속 도는 것보다 낫습니다.
- **멈춤 감시**: 틱이 10초 넘게 끝나지 않으면 감시 스레드가 프로세스를 끝내고(`Environment.FailFast`) 덤프를 남깁니다. 멈춘 채 연결만 붙들고 있는 것보다 다시 뜨는 것이 낫습니다.
- **내려가기**: SIGTERM을 받으면 모두에게 `KICK_REASON_SERVER_SHUTDOWN`을 보내고, 저장하고, 내려갑니다(있음).
- 경로마다 큐를 어떻게 하는지는 [저장의 흐름](#저장의-흐름)의 표에 있습니다. 예외, 밀린 큐, 감시로 끝난 프로세스는 프로세스 관리자(systemd)가 다시 띄웁니다.

### 재는 것

- 10초마다 찍는 로그(틱 평균과 최대, CPU, 송신량, 할당, GC, 있음)에 틱의 차례별 시간, 패킷 종류별 수와 바이트, 보내기 큐의 길이를 더합니다.
- 50 ms를 넘은 틱은 차례별 시간과 함께 따로 남깁니다. 틱이 예정보다 늦게 시작한 시간(타이머의 흔들림)과 건너뛴 틱 수도 찍습니다.
- 어느 함수에 시간이 드는지는 `dotnet-trace`로, 할당과 GC는 `dotnet-counters`로 봅니다.
- 최적화는 이 수치에서 큰 것부터 합니다([최적화](#최적화)).

### 과부하 때

일반적인 MMORPG처럼 한도를 미리 정해 두고, 넘어도 게임 시간은 실제 시간을 따라가게 합니다.

- **동접 상한과 대기열**: 정한 수를 넘는 로그인은 거절합니다(있음). 거절하는 대신 대기열에 두고 순번을 알리며 자리가 나면 들여보내게 바꿉니다. 줄을 서지 않는 로그인은 [세션](#세션)에 있습니다. 연결 시도는 IP마다 빈도를 제한합니다.
- **시야 인원 상한**: 한곳에 사람이 몰려도 연결 하나에 보내는 캐릭터 수에 끝이 있습니다([개체](#개체)).
- **틱이 밀릴 때**: 틱이 50 ms를 넘으면 밀린 틱을 몰아서 돌리지 않고, 틱 번호를 지난 시간만큼 건너뜁니다. 100 ms가 걸린 틱 다음은 번호가 2 오릅니다. 건너뛴 틱에서 계산을 맞추는 법은 [구조 원칙](#구조-원칙)에 있습니다. 쿨다운, 공격 간격, 이동 예산이 실제 시간 그대로라 플레이어는 느려지지 않고, 주변의 갱신만 뜸해집니다.
- **넣지 않은 것**: 게임 시간을 늦추는 것과 부하에 따라 갱신 빈도를 단계별로 줄이는 것입니다. 까닭은 [서버에서 할 것](#서버에서-할-것)의 "넣지 않은 것" 표에 있습니다.

### 규모를 넘으면

만들지는 않고, 한도와 나누는 차례만 적습니다.

| 차례 | 방법 | 풀리는 한도 |
| --- | --- | --- |
| 1 | 저장 스레드를 데이터베이스 캐시 서버(프로세스)로 | 게임 서버 여러 개가 같은 저장 경로를 씀 |
| 2 | 채널: 같은 필드를 도는 프로세스를 여럿 띄우고 로그인할 때 나눔 | 한 프로세스의 동접. 대신 채널이 다른 플레이어는 서로 보이지 않음 |
| 3 | 존 서버: 필드를 존으로 나눠 프로세스마다 맡기고, 앞에 연결을 쥐는 게이트웨이를 둠 | 한 필드의 동접. 존을 넘는 이동(넘겨주기)과 경계 너머의 시야(개체의 사본)가 필요함 |
| 4 | 로그인 서버를 따로 두고, 채팅과 파티를 월드 서버로 떼고, 데이터베이스를 PostgreSQL로 | 여러 게임 서버가 같은 계정과 캐릭터 데이터를 봄 |

## 월드

- **필드**: 하나이고 걸어서 이어집니다(심리스). 로딩이나 포털이 없고, 필드 전체를 틱 스레드 하나가 계산합니다. 처음에는 장애물 없는 평지입니다. 좌표와 방향의 규약은 `packets.proto`에 있습니다(1 m = 32칸, `+z`가 앞, `yaw`는 시계 방향 256칸). 쓰는 넓이는 한 변 600 m(±300 m)로 시작합니다. 끝에서 끝까지 걸어서 100초이고, 패킷의 한도(±1,024 m)보다 작습니다. 서버의 이동 검증도 패킷의 한도가 아니라 이 넓이(`Zones`의 필드 범위)를 씁니다.
- **구역**: `Zones` 테이블의 사각형입니다. 구역마다 종류(마을, 사냥터, 채집지, 보스 자리)와 안전 지대 여부, 권장 레벨이 있습니다. 서버는 개체의 위치로 구역을 구합니다. 구역은 규칙을 가르는 이름표이고, 계산을 나누는 단위가 아닙니다.

| 구역 | 내용 |
| --- | --- |
| 마을 | 안전 지대. 부활 지점, 상점·창고·제작·퀘스트 NPC, 경비병 |
| 사냥터 1–3 | 레벨대가 다른 몬스터. 뒤로 갈수록 선공 몬스터 |
| 채집지 | 나무, 광석, 약초. 약한 몬스터가 섞여 있음 |
| 보스 자리 | 필드 보스. 사냥터 3 안쪽 |

- **안전 지대**: 몬스터가 들어오지 않고 플레이어끼리의 공격을 막습니다. 누구를 지키고 누구를 지키지 않는지는 [PK](#pk)에 있습니다.
- **장애물**: 서버(이동 검증, 몬스터 이동)와 두 엔진이 함께 읽을 맵 원본이 생긴 뒤에 넣습니다. 엔진마다 맵을 따로 만들면 한쪽에서 벽인 곳을 다른 쪽 플레이어가 지나갑니다.

## 개체

| 종류 | 움직임 | 체력 | 고를 수 있는 행동 |
| --- | --- | --- | --- |
| 플레이어 | 클라이언트가 보냄 | 있음 | 공격(PK), 파티 초대, 귓속말 |
| 몬스터 | 서버가 계산 | 있음 | 공격 |
| NPC | 없음(경비병은 서버가 계산) | 경비병만 | 상점, 창고, 제작, 퀘스트 |
| 채집물 | 없음 | 없음(남은 횟수) | 채집 |
| 바닥 아이템 | 없음 | 없음 | 줍기 |

- `EntityEnter`에 종류, 템플릿 번호(몬스터·NPC·채집물·아이템의 테이블 행), 체력과 최대 체력, 레벨, 표시 상태(죽음, 성향 색, 길드)를 더합니다. 필드를 더하는 것이라 프로토콜 버전은 올리지 않습니다.
- 서버는 `Player`에서 공통 부분(번호, 위치, 시야 칸)을 `Entity`로 떼고, 체력이 있는 것은 그 위에 전투 상태를 얹습니다.
- 시야에 다른 플레이어가 너무 많으면(대규모 PK, 보스) 정한 수까지만 보냅니다. 파티원, 나를 공격하는 캐릭터, 내 대상을 먼저 넣고 나머지는 가까운 순입니다. 몬스터와 바닥 아이템에는 상한을 두지 않습니다. 상한은 200 이상이고(한 화면 200명이 클라이언트의 목표입니다), 상한에서의 최악 송신량을 재서 정합니다. 상한으로 빠진 캐릭터가 낸 사건을 어떻게 보내는지는 [전투](#전투)의 결과에, 그 캐릭터의 주변 채팅은 [사회](#사회)에 있습니다.

## 캐릭터와 능력치

- 로그인 ID 하나에 캐릭터 하나, 직업은 하나(근접)입니다.
- 능력치는 넷입니다: **최대 체력, 최대 마나, 공격력, 방어력**. 이동 속도는 모두 같고(6 m/s, `Constant`의 값) 감속 효과만 줄입니다.
- 능력치 = 레벨의 기본값(`Levels`) + 입은 장비와 강화 + 걸린 효과. 서버가 바뀔 때마다 다시 더하고, 클라이언트에는 결과를 보냅니다.
- 체력과 마나는 시간이 지나면 차오릅니다. 전투 중(마지막 공격·피격 뒤 5초)에는 느리게 찹니다. 물약은 바로 채우고 쿨다운이 있습니다.

## 전투

- **대상**: 개체 하나를 대상으로 정합니다. 다른 플레이어는 강제 공격을 켜야 공격 대상이 됩니다(실수로 치지 않게).
- **기본 공격**: 클라이언트는 공격 시작(대상)과 멈춤만 보냅니다. 서버가 공격 간격마다 대상이 사거리 안에 있고 살아 있으면 한 번씩 칩니다. 대상에게 다가가는 것은 클라이언트의 이동입니다. 패킷이 줄고, 공격 속도를 속일 수 없습니다.
- **스킬**: 클라이언트는 스킬 번호와 대상(또는 자기)을 보냅니다. 서버는 요청을 받은 입력 차례에 배웠는지, 쿨다운, 마나, 사거리, 상태(살아 있음, 기절 아님)를 확인합니다. 발동은 전투 차례에서 합니다([틱의 차례](#틱의-차례)). 시전 시간이 없는 스킬은 확인한 자리에서 비용(마나, 쿨다운)을 빼고 같은 틱에 발동합니다. 시전 시간이 있는 스킬은 그 틱 수 뒤에 발동하고 비용도 그때 뺍니다(그때 마나가 모자라면 실패합니다). 시전하는 사이에 시작한 자리에서 벗어나거나 기절하면 취소되고, 잃는 것이 없습니다(방향만 바꾼 것은 취소하지 않습니다). 시전하는 동안에는 다른 스킬을 쓸 수 없습니다.

| 스킬 종류 | 내용 |
| --- | --- |
| 단일 피해 | 대상 하나에 공격력 × 계수 |
| 범위 피해 | 대상이나 자기를 중심으로 한 원 안의 적 모두 |
| 강화 | 자기의 공격력이나 방어력을 일정 시간 올림 |
| 상태 이상 | 기절(이동·공격·스킬 불가), 감속(이동 속도) |
| 회복 | 자기 체력을 채움 |

- **효과**: 강화와 상태 이상은 `Effects`의 행 하나이고, 개체에 "효과 번호, 끝나는 틱"으로 붙습니다. 같은 효과는 시간만 새로 합니다. 끝나는 틱에 서버가 효과를 떼고 능력치를 다시 구합니다([예약한 일](#예약한-일)). 감속이 걸리면 서버의 이동 예산도 그만큼 줄고, 기절한 동안의 `Move`는 되돌립니다. 클라이언트도 내게 걸린 감속과 기절을 이동과 입력에 반영해 되돌려지지 않게 합니다.
- **피해**: `(공격력 × 스킬 계수 − 방어력의 몫) × 난수(±10%)`이고 최소 1입니다. 공식은 formula-tool로 만들어 서버가 계산합니다. 명중·회피·치명타는 넣지 않습니다.
- **결과**: 서버는 스킬 사용(누가, 무엇을, 누구에게), 피해(누가 얼마, 남은 체력), 효과가 붙음, 죽음을 사건으로 보냅니다.
  - **누구에게**: 사건의 대상(맞은 쪽, 효과가 붙은 쪽, 죽은 쪽. 대상이 없으면 행위자)을 받은 연결 모두와 대상 자신입니다. 개체를 "받은 연결"은 그 개체의 `EntitiesEnter`를 받고 아직 `EntitiesLeave`를 받지 않은 연결입니다.
  - **번호 0**: 그 연결이 받지 않은 다른 쪽(시야 인원 상한으로 빠진 공격자나 시전자)의 번호는 0으로 싣습니다. 클라이언트는 번호가 0이면 개체를 찾지 않고 대상 쪽의 결과(체력, 피해 숫자, 피격 반응)만 반영합니다.
  - **효과가 떨어짐**: 붙을 때 끝나는 틱을 함께 알리므로, 시간이 다 되기 전에 떼일 때만 알립니다.
  - **나에게만**: 내 체력과 마나는 바뀐 틱에 보냅니다. 쿨다운은 로그인 때 전체를, 그 뒤에는 바뀐 것을 보냅니다(물약 포함).
  - **1초마다**: 피해가 아닌 까닭으로 체력이 바뀐 개체(자연 회복, 물약, 회복 스킬, 복귀 중인 몬스터)는 1초마다 모아 체력과 최대 체력을 보냅니다.
  - **새로 들어온 개체**: 시야에 새로 들어온 개체에는 걸려 있는 효과를 함께 알립니다.
- **클라이언트의 예측**: 쿨다운 표시와 공격 동작의 시작만 미리 보여 줍니다. 맞았는지와 피해는 서버의 결과로만 보여 줍니다. 쿨다운 규칙은 서버가 만든 비교 벡터로 두 클라이언트를 검사합니다.

## 몬스터

- **테이블**: `Monsters`(레벨, 체력, 공격력, 방어력, 이동 속도, 인식 범위, 추적 한계, 공격 사거리와 간격, 선공 여부, 경험치, 드롭 묶음)와 `Spawns`(구역, 몬스터, 수, 다시 나오는 시간, 배회 반경).
- **상태**: 대기(자리 근처를 배회) → 추적 → 공격 → 복귀. 선공 몬스터는 인식 범위에 플레이어가 들어오면, 비선공은 맞으면 추적합니다. 자리에서 추적 한계보다 멀어지면 복귀하고, 복귀하는 동안은 피해를 받지 않고 체력이 찹니다.
- **누구를 칠지**: 자기에게 준 피해의 합이 가장 큰 플레이어입니다.
- **누가 잡았는지**: 피해를 가장 많이 준 플레이어(파티면 파티)가 경험치와 드롭의 주인입니다.
- **죽은 뒤**: 죽은 몬스터는 죽음 표시로 3초 동안 남아 쓰러지는 모습을 보인 뒤 사라집니다. 죽는 틱에 바로 빼면 클라이언트가 이미 없는 개체의 피해와 죽음을 받습니다.
- **이동**: 평지라 길찾기 없이 대상 쪽으로 곧게 갑니다. 움직인 틱에는 플레이어처럼 `EntityMoves`에 들어갑니다(M7에서 목적지와 속도를 한 번 알리는 것으로 바꿉니다).
- **필드 보스**: `Spawns`의 다시 나오는 시간이 긴 몬스터입니다. 일정 간격으로 범위 공격을 하는데, 바닥에 범위를 먼저 알리고 몇 틱 뒤에 피해를 주어 걸어서 피할 수 있습니다. 보상은 피해를 준 순서로 여러 플레이어(파티)에게 나눕니다.

## 성장

- **경험치와 레벨**: 몬스터를 잡으면 `Monsters`의 경험치를 얻고, `Levels`(레벨, 필요 경험치, 기본 능력치)에 따라 레벨이 오릅니다. 레벨 차이가 크면 경험치가 줄어듭니다.
- **스킬 배우기**: 스킬북 아이템을 쓰면 그 스킬을 배웁니다. 스킬마다 필요 레벨이 있습니다. 배운 스킬은 퀵슬롯에 올려 씁니다(퀵슬롯 배치는 서버에 저장).
- **처음 상태**: 새 캐릭터는 레벨 1, 기본 무기, 물약 몇 개, 첫 스킬 하나로 시작합니다(`Constants`).
- **스킬북을 얻는 곳**: 기본 스킬은 상점에서 사고, 뒤의 스킬은 몬스터와 보스가 떨어뜨립니다.
- **사망**: 죽으면 그 자리에 쓰러지고, 부활을 누르면 마을의 부활 지점에서 체력의 일부로 다시 시작합니다. 페널티는 [PK](#pk)에, 죽은 채 접속을 끊은 경우는 [세션](#세션)에 있습니다.

## 아이템

- **종류**

| 종류 | 예 | 겹침 |
| --- | --- | --- |
| 장비 | 무기, 투구, 갑옷, 장갑, 신발, 장신구 | 겹치지 않음. 칸 하나에 하나이고 강화 수치를 가짐 |
| 소모품 | 체력·마나 물약, 귀환 주문서, 강화 주문서, 스킬북 | 겹침 |
| 재료 | 나무, 광석, 약초, 몬스터 부산물 | 겹침 |

- **골드**: 아이템이 아니라 캐릭터의 수입니다. 바닥에 떨어질 때만 `Items`의 골드 줄을 가리키는 바닥 아이템이 되고, 주우면 수로 더해집니다.
- **등급**: 일반, 고급, 희귀, 영웅 네 단계입니다. 이름의 색과 드롭 확률의 기준이고, 같은 칸의 장비라도 등급이 높으면 능력치가 높습니다.
- **인벤토리**: 칸 수가 정해져 있고(60칸), 가득 차면 줍거나 사지 못합니다.
- **창고**: 마을의 창고 NPC에게 아이템을 맡기고 찾습니다(120칸). 창고의 아이템은 죽어도 떨어뜨리지 않습니다.
- **장비**: 6칸(무기, 투구, 갑옷, 장갑, 신발, 장신구)이고 필요 레벨이 있습니다. 입고 벗으면 능력치를 다시 더합니다.
- **강화**: 강화 주문서를 장비에 씁니다. 안전 수치(+3)까지는 늘 성공하고, 그 위로는 `Enchants`의 확률로 성공합니다. 실패하면 장비가 사라집니다. 주문서 소모, 난수, 결과는 한 틱에서 정해지고 한 트랜잭션으로 저장합니다.
- **드롭**: 몬스터가 죽으면 `DropGroups`(묶음, 아이템, 확률, 수량)와 서버의 난수로 골드와 아이템을 정해 그 자리에 **바닥 아이템** 개체로 둡니다. 일정 시간(10초)은 잡은 플레이어(파티)만 주울 수 있고, 그 뒤에는 누구나 줍고, 더 지나면(60초) 사라집니다.
- **떨어뜨리기**: 인벤토리의 아이템을 바닥에 내려놓습니다. 10초 동안은 떨어뜨린 본인과 파티원만 줍고 그 뒤에는 누구나 줍습니다. 파티가 없으면 바로 누구나 줍습니다. 골드는 떨어뜨릴 수 없고, 안전 지대에서도 됩니다. 플레이어끼리 아이템을 건네는 방법입니다. 처리하는 순서와 저장은 [저장의 흐름](#저장의-흐름)에 있습니다.
- **줍기**: 가까이에서 줍기를 보내면 서버가 그 틱에 먼저 온 요청 하나만 받아 줍니다. 바닥 아이템은 수량, 강화 수치, 주인, 주인만 줍는 시간이 끝나는 틱, 플레이어가 떨어뜨렸는지를 함께 알립니다. 강화한 장비를 떨어뜨려도 수치가 남고, 자동 사냥이 무엇을 주울지를 이것으로 정합니다([자동 사냥](#자동-사냥)).
- **요청 번호**: 인벤토리를 바꾸는 요청(사용, 입기와 벗기, 강화, 떨어뜨리기와 줍기, 구매와 판매, 창고에 맡기기와 찾기, 제작, 퀘스트 받기와 완료)은 연결마다 1씩 느는 요청 번호를 싣고, 답은 그 번호로 짝을 짓습니다. 마지막 번호 + 1이 아닌 번호는 정상 클라이언트가 보낼 수 없으므로 `KICK_REASON_MALFORMED_PACKET`으로 끊습니다. 빈도 제한으로 버린 요청도 번호는 기록합니다(실패라는 답은 [요청 검증](#요청-검증)). 번호를 저장하지는 않습니다. TCP는 한 연결 안에서 같은 요청을 두 번 전하지 않고, 다시 연결하면 클라이언트가 인벤토리를 처음부터 다시 받아 기다리던 요청을 다시 보내지 않기 때문입니다.

## 파티

- 초대 → 수락으로 만들고, 떠나기와 내보내기가 있습니다. 최대 5명이고 파티장이 나가면 다음 사람이 파티장입니다.
- 끊긴 파티원은 2분 동안 "끊김"으로 남고, 그 안에 다시 들어오면 그대로 이어 갑니다. 지나면 파티에서 빠집니다. 파티장이 끊기면 바로 다음 사람이 파티장이 됩니다.
- 파티원의 체력과 위치는 시야 밖이어도 보입니다(파티 전용 패킷, 1초마다).
- 경험치는 잡은 자리의 둘레 9칸에 있는 파티원이 고르게 나누고, 인원이 많을수록 합이 조금 늡니다.
- 드롭은 파티원 모두가 주울 수 있습니다.
- 파티원끼리는 피해를 주지 못합니다. 파티 채팅이 있습니다.

## PK

- **어디서**: 안전 지대 밖이면 어디서나 다른 플레이어를 공격할 수 있습니다. 레벨 10 미만은 공격하지도 받지도 않습니다.
- **안전 지대가 지키는 것**: 표시가 없는 일반 플레이어만 지킵니다. 선공 표시가 있거나 무법자인 플레이어는 안전 지대 안에서도 맞고, 경비병도 안으로 쫓아 들어옵니다. 경계에서 치고 한 걸음 들어가 숨을 수 없습니다.
- **선공 표시**: 일반 플레이어를 먼저 공격하면 30초 동안 이름이 보라색이 됩니다. 보라색인 플레이어는 누가 죽여도 죽인 쪽에 대가가 없습니다(정당방위).
- **성향**: 보라색이 아닌 일반 플레이어를 죽이면 성향이 내려가고, 0 아래면 이름이 빨간색(무법자)이 됩니다. 몬스터를 잡으면 조금씩 올라 0으로 돌아옵니다.

| 상태 | 이름 색 | 죽었을 때 | 그 밖 |
| --- | --- | --- | --- |
| 일반 | 흰색 | 경험치 조금 잃음. 아이템은 떨어뜨리지 않음 | |
| 선공 | 보라색 | 일반과 같음 | 경비병이 공격함. 죽여도 대가 없음 |
| 무법자 | 빨간색 | 경험치를 더 잃고, 인벤토리와 입은 장비에서 확률로 떨어뜨림 | 경비병이 공격함. 죽여도 대가 없음 |

- **떨어뜨린 아이템**: 무법자가 죽어서 떨어뜨린 것은 바닥 아이템이 되어 누구나 주울 수 있습니다. 몬스터의 드롭과 같은 전리품이라 자동 사냥도 줍습니다("플레이어가 떨어뜨림" 표시를 붙이지 않습니다). 아이템을 내놓는 일이라 [저장의 흐름](#저장의-흐름)의 내놓는 순서를 따릅니다.
- **경비병**: 마을 둘레의 NPC이고, 인식 범위의 무법자와 선공 표시가 있는 플레이어를 공격합니다.
- **무법자의 부활**: 마을이 아니라 마을 밖에 따로 둔 지점에서 부활합니다. 부활하자마자 경비병에게 다시 죽지 않습니다.
- **끊어서 피하기**: 할 수 없습니다. 전투 상태나 선공 표시가 남은 캐릭터는 [세션](#세션)의 규칙대로 월드에 남습니다.
- **서버가 확인하는 것**: 대상의 구역과 레벨, 파티(와 길드) 관계, 표시의 끝나는 틱. 성향과 죽인 수는 저장합니다.

## 생활

- **채집**: `GatherNodes`(종류, 주는 재료와 수량, 채집 시간, 횟수, 다시 나오는 시간, 필요 숙련도)의 채집물이 `Spawns`대로 필드에 있습니다. 가까이에서 채집을 시작하면 시간(3초)이 지난 뒤 재료를 얻습니다. 그 사이에 피해를 받거나 시작한 자리에서 벗어나면 취소됩니다. 완료할 때 인벤토리가 가득이면 실패를 알리고 채집물의 횟수는 줄지 않습니다. 채집물은 횟수를 다 쓰면 사라졌다가 다시 나오고, 그때 같은 채집물을 채집하던 다른 플레이어에게는 취소를 알립니다.
- **제작**: 마을의 제작 NPC 가까이에서 `Recipes`(결과, 재료와 수량, 골드, 제작 시간, 필요 숙련도, 장비면 등급의 확률)의 제작법을 고릅니다. 재료와 골드를 내고 시간이 지나면 결과를 얻습니다.
  - 한 번에 하나만 만듭니다. 만드는 중에 온 제작 요청은 실패로 답합니다. NPC와의 거리는 시작할 때만 봅니다.
  - 시작할 때 빈 칸 하나를 "제작 결과용"으로 표시합니다. 결과가 겹칠 수 있는 아이템이어도 빈 칸을 씁니다. 표시한 칸은 인벤토리와 함께 클라이언트에 가고 만드는 중인 제작과 함께 저장되며, 다른 넣기(줍기, 구매, 벗기, 창고에서 찾기, 퀘스트 보상)는 이 칸을 빈 칸으로 세지 않습니다.
  - 장비 제작법은 결과의 등급을 `Recipes`의 확률로 정합니다.
- **얻는 곳**: 1단계 물약은 상점에서 사고, 2단계 물약은 제작으로만 얻습니다. 1단계 장비는 사냥터 1의 드롭으로, 2단계 장비는 드롭과 제작 둘 다로, 3단계 장비는 제작으로만 얻습니다.
- **숙련도**: 채집과 제작에 하나씩 있습니다. 할 때마다 오르고, 높은 채집물과 제작법을 엽니다.

## 경제

- **골드가 생기는 곳**: 몬스터 드롭, NPC 상점에 팔기, 퀘스트 보상.
- **골드가 사라지는 곳**: NPC 상점 구매(물약, 주문서, 스킬북), 제작비.
- **NPC 상점**: `Shops`(상점, 아이템, 가격). 사고, 가진 것을 정해진 값에 팝니다.
- **플레이어 사이**: 거래소와 개인 거래는 없습니다([범위 밖](#범위-밖)). 아이템은 바닥에 [떨어뜨려](#아이템) 건넵니다.

## 사회

- **채팅**: 주변(둘레 9칸), 파티, 전체, 귓속말입니다. 주변 채팅은 보낸 사람의 둘레 9칸에 있는 플레이어에게 가고, 받는 쪽이 보낸 사람의 개체를 받았는지와 상관없습니다. 그래서 보낸 사람의 이름을 함께 싣고, 말풍선은 그 캐릭터가 화면에 있을 때만 띄웁니다. 길이와 보내는 빈도는 서버가 제한합니다.
- **길드와 길드전(나중)**: 길드를 만들고 가입·탈퇴하며, 이름표에 길드 이름이 보이고 길드 채팅이 있습니다. 두 길드가 서로 전쟁을 선언하면 그 길드원끼리는 죽여도 성향이 내려가지 않습니다. 공성전은 만들지 않습니다.

## 퀘스트

- `Quests`(차례, 조건, 수, 보상)의 퀘스트를 마을 NPC에게서 받아 차례로 합니다. 조건은 몬스터 잡기, 재료 모으기, 제작하기, 레벨 달성, 장비 입기입니다.
- 진행은 서버가 세고 저장합니다. 파티원이 잡은 몬스터도 잡은 자리의 둘레 9칸에 있으면 셉니다. 모으기의 재료는 완료할 때 뺍니다.
- 처음 들어온 플레이어를 사냥 → 장비 → 채집 → 제작 순으로 안내하는 것이 목적입니다.

## 자동 사냥

- 클라이언트가 합니다. 서버에는 손으로 한 것과 같은 패킷이 갑니다.
- 차례: 가까운 몬스터를 대상으로 → 사거리까지 이동 → 기본 공격과 쿨다운이 돈 스킬 → 죽으면 바닥 아이템 줍기 → 체력이 낮으면 물약 → 다음 대상.
- 줍는 것은 주인이 나나 내 파티이거나 주인만 줍는 시간이 지난 바닥 아이템입니다. 남의 드롭으로 걸어가지 않습니다. 플레이어가 떨어뜨린 아이템은 줍지 않습니다. 가방을 비우려고 떨어뜨린 것을 다시 줍거나, 남에게 건네려고 떨어뜨린 것을 가로채지 않게 하려는 것입니다.
- 무엇을 할지 고르는 판단은 엔진 없는 코드로 만들어 테스트하고, 이동과 입력만 엔진 쪽에서 합니다.

## 콘텐츠의 양

처음 넣을 양입니다. 구조를 보이는 데 필요한 만큼만 두고, 늘리는 것은 데이터의 줄을 더하는 일입니다.

| 무엇 | 양 |
| --- | --- |
| 최대 레벨 | 30 |
| 사냥터 | 3곳(레벨 1–10, 10–20, 20–30) |
| 몬스터 | 사냥터마다 3종(비선공 2, 선공 1)으로 9종, 필드 보스 1 |
| 스킬 | 6개: 단일 피해 2(하나는 감속을 겁니다), 범위 피해 1, 강화 1, 기절 1, 회복 1 |
| 장비 | 6칸 × 3단계(레벨 1, 10, 20)로 18종. 종마다 등급 넷이라 `Items`에는 72줄. 얻는 곳은 [생활](#생활) |
| 강화 | +0에서 +9 |
| 소모품 | 체력·마나 물약 2단계씩, 귀환 주문서, 강화 주문서, 스킬북 5(첫 스킬은 가지고 시작) |
| 채집물과 재료 | 나무, 광석, 약초를 2단계씩. 몬스터 부산물 |
| 제작법 | 14개(2단계 물약 2, 2·3단계 장비 12). 장비 제작법은 종마다 하나이고 등급은 확률로 정함 |
| NPC | 상점, 창고, 제작, 퀘스트, 경비병 |
| 퀘스트 | 10개 안팎 |

- **수치를 잡는 기준**: 1레벨에서 30레벨까지 자동 사냥으로 2시간쯤 걸리게 합니다. 시연에서 성장이 보여야 하기 때문입니다. 레벨마다 필요한 경험치는 이 시간에서 거꾸로 구하고, 몬스터의 체력은 같은 레벨의 캐릭터가 스킬 몇 번에 잡는지로 정합니다.
- **그림**: 필요한 메시, 아이콘, 소리의 목록과 출처는 `docs/art.md`에 둡니다. 직접 만든 것이나 CC0만 넣으므로, 그림이 없을 때 쓰는 자리 표시(색 도형, 글자 아이콘)를 먼저 둡니다.

## 데이터 테이블

`data/`의 xlsx가 원본이고 data-tool이 테이블마다 `.proto`와 Protobuf 바이너리를 냅니다. 서버(C#), Unity(C#), Unreal(C++)은 protoc가 만든 코드로 읽습니다. 이름과 문장은 `Strings`의 키로 가리킵니다.

| 테이블 | 내용 |
| --- | --- |
| `Constants` | 인벤토리 칸 수, 전투 상태 시간, 드롭이 남는 시간, 사망 페널티 등 |
| `Zones` | 구역의 사각형, 종류, 안전 지대, 권장 레벨, 부활 지점 |
| `Levels` | 필요 경험치, 기본 능력치 |
| `Monsters`, `Spawns` | 몬스터의 수치와 놓을 자리 |
| `Skills`, `Effects` | 스킬(종류, 계수, 사거리, 범위, 쿨다운, 시전 시간, 마나, 필요 레벨)과 효과 |
| `Items` | 종류, 등급, 칸, 능력치, 필요 레벨, 겹침, 상점에 파는 값 |

| `DropGroups` | 묶음마다 아이템, 확률, 수량, 골드 |
| `Npcs`, `Shops` | NPC의 자리와 역할, 상점의 물건 |
| `GatherNodes`, `Recipes` | 채집물과 제작법 |
| `Quests` | 조건과 보상 |
| `Strings` | 화면에 보이는 이름과 문장 |

| --- | --- | --- |
| 1–99 | 세션 | 로그인, 끊기, 연결 확인 (있음), 로그아웃, 실패 알림, 대기 순번, 압축한 프레임, 개발 명령 |

| `players` | 위치(있음), 레벨, 경험치, 체력, 마나, 골드, 성향, 죽인 수, 숙련도, 만드는 중인 제작(결과용으로 표시한 칸 포함) |
| `items` | 주인, 있는 곳(인벤토리, 장비, 창고)과 칸, 아이템 번호, 수량, 강화 수치 |
| `timers` | 주인, 종류(쿨다운, 효과, 선공 표시), 번호, 남은 틱 수. 플레이어를 쓸 때마다 고쳐 쓰고(끝난 것은 지움) 들어올 때 지금 틱에 더함 |
| `skills`, `quickslots`, `quests` | 배운 스킬, 퀵슬롯, 퀘스트 진행 |
| `guilds`, `guild_members`, `guild_wars` | 길드와 길드전(나중) |

저장 형식에 버전을 두고, 올릴 때 옮기는 코드(마이그레이션)를 함께 둡니다.

## 최적화

리니지 라이크의 기술 과제는 한 화면과 한 서버에 사람이 많은 것입니다. 클라이언트 포트폴리오라 서버의 콘텐츠는 줄였지만, 사람이 많을 때 서버가 해야 하는 최적화는 합니다. 그것이 없으면 클라이언트가 200명을 그릴 일도 없기 때문입니다. 최적화는 **먼저 재고, 가장 큰 것부터 고치고, 같은 방법으로 다시 재서 전과 후의 수치를 남기는** 순서로 합니다. 재지 않은 것은 고치지 않습니다. 수치는 `docs/performance.md`에 잰 날, 커밋, 환경과 함께 남깁니다(키우기와 같은 방식).

### 한 것

| 무엇 | 방법 | 수치 |
| --- | --- | --- |
| Mac 패키지 크기 | Shipping, 셰이더 한 벌(SM5), 쓰지 않는 렌더러 기능 끔, 실행 파일의 심볼 지움, 엔진 플러그인 끔 | 872 → 212 MB |
| Android 라이브러리 | libprotobuf의 디버그 정보 지움 | 145 → 11 MB |
| 송신량 | 좌표를 정수로 줄이고, 움직인 개체만 보내고, 한 틱을 한 버퍼로 보냄 | 개체 하나 15바이트, 시야 55명에 클라이언트당 15,354 B/s |
| 틱 시간 | 격자 시야, 잠금 없는 틱 스레드 하나 | 봇 2,000명에 평균 15.4 ms(최대 23.5 ms) |
| 저장 | 한 트랜잭션에 모아 씀(WAL) | 2,000명에 4.8 ms |

### 서버에서 할 것

지금 수치는 봇 2,000명(시야 평균 55명)을 잰 값입니다. 몬스터와 전투가 들어가면 다시 잽니다.

| 대상 | 지금 | 방법 |
| --- | --- | --- |
| 직렬화 | 틱의 7.1 ms | 개체의 움직임을 틱마다 한 번만 인코딩해 두고, 보는 연결마다 그 바이트를 이어 붙입니다. 지금은 보는 사람 수만큼 다시 인코딩하고 크기 계산도 여러 번 돕니다 |
| 시야 비교 | 틱의 7.0 ms | 플레이어마다 `HashSet` 전체를 비교하지 않고, 칸에 들어오고 나간 개체의 목록만 봅니다. 칸을 옮긴 플레이어만 전체를 다시 봅니다. 개체마다 "나를 받은 연결"의 목록을 두고, 움직임, 사건, 상태를 그 목록으로 보냅니다 |
| 할당 | 131 MB/s | 틱 버퍼와 패킷 객체를 풀에서 꺼내 씁니다. 틱 최대값(23.5 ms)에서 GC가 차지하는 몫을 재고 GC 설정을 비교합니다 |
| 송신량 | 클라이언트당 15,354 B/s(한 달 43 GB). VPS에서는 CPU가 아니라 이것이 동접을 정함 | 이동을 바뀔 때만 알립니다. 몬스터는 목적지와 속도를 한 번, 플레이어는 출발·방향 바뀜·멈춤과 0.5초마다의 확인만 보내고 클라이언트가 그 사이를 이어 그립니다. 목표는 절반 아래입니다 |
| 시야의 경계 | 칸의 경계를 오가는 개체가 틱마다 들어옴과 나감을 냄 | 나가는 기준을 들어오는 기준보다 넓게 둡니다(여유 8 m). 들어옴은 이름과 상태를 다 실은 큰 패킷입니다. 여유 안에 남은 개체는 "나를 받은 연결"의 목록에 그대로 있어 사건과 상태가 계속 갑니다. 보는 쪽이 칸을 넘을 때 생기는 들어옴·나감도 같은 봇 측정에서 재고, 크면 보는 쪽의 중심 칸도 새 칸으로 8 m 넘게 들어갔을 때 바꿉니다 |
| 사람이 몰린 곳 | 시야 개체 수에 상한 없음 | 보낼 캐릭터 수에 상한을 둡니다(200 이상. 누구를 먼저 넣는지는 [개체](#개체)). 상한에서의 최악 송신량, 월 GB, VPS의 동접을 재서 남깁니다. 클라이언트에도 표시할 캐릭터 수 설정을 둡니다 |
| 틱이 밀릴 때 | 틱 번호가 실제 시간보다 늦어짐 | 틱 번호를 지난 시간만큼 건너뜁니다([과부하 때](#과부하-때)). 건너뛴 틱에서 계산을 맞추는 법은 [구조 원칙](#구조-원칙)에 있습니다 |
| 몬스터 AI | 아직 없음 | 둘레 칸에 플레이어가 없는 몬스터는 계산하지 않습니다 |
| 저장 | 2,000명 4.8 ms를 틱 스레드에서 씀 | 저장 스레드로 옮기고 바뀐 플레이어만 씁니다(캐릭터 저장을 만들 때부터. [저장의 흐름](#저장의-흐름)). 그 뒤에 큐의 길이와 한 번 쓰는 시간을 재고, WAL 체크포인트가 저장 스레드에서 돌게 합니다 |
| 큰 패킷 | 압축하지 않음 | 한 틱의 버퍼가 정한 크기(재서 정함)를 넘을 때만 보내기 작업에서 압축합니다(로그인 때의 인벤토리, 한꺼번에 들어오는 개체 목록). 작은 패킷은 압축해도 줄지 않습니다 |
| OS의 한도 | 확인하지 않음 | VPS에서 열 수 있는 파일 수와 소켓 버퍼를 확인해, 연결 수가 서버보다 OS에서 먼저 막히지 않게 합니다 |

무엇이 MMO 서버의 일반적인 기술인지와 각각을 넣는지는 [MMO 서버 기술과 적용 여부](#mmo-서버-기술과-적용-여부)에 있습니다.

**넣지 않은 것**. 처음에 넣었다가 이 기준에서 벗어나 뺐습니다.

### 클라이언트에서 할 것

목표는 한 화면에 캐릭터 200명입니다. 프레임 목표(휴대폰 30, PC 60)는 기기에서 처음 잰 뒤에 정합니다.

| 대상 | 방법 |
| --- | --- |
| 게임 스레드 | 다른 캐릭터는 액터의 틱을 끄고 관리자 하나가 한 번에 위치를 넣습니다. 이동 컴포넌트를 두지 않습니다 |
| 애니메이션 | Animation Budget Allocator로 먼 캐릭터의 갱신을 줄이고, 화면 밖은 갱신하지 않습니다 |
| 그리기 | 메시 LOD, 먼 캐릭터의 그림자 끔, 그릴 캐릭터 수의 상한(가까운 순) |
| UI | 이름표와 피해 숫자를 한 층에서 풀로 그리고, 인벤토리와 창고의 목록은 보이는 줄만 만듭니다 |
| 끊김과 메모리 | 액터(몬스터, 바닥 아이템, 이펙트)를 풀에서 쓰고, 에셋을 비동기로 불러오고, 패킷을 Protobuf Arena에 풀어 프레임마다의 할당을 없앱니다 |
| 크기와 시작 시간 | Android 셰이더를 한 벌로 줄이고, 시작부터 로그인 화면까지의 시간을 잽니다 |
| 발열 | 프레임 상한을 설정에 둡니다 |

### 재는 방법

- **서버**: 10초마다 찍는 로그(틱 평균과 최대, CPU, 송신량, 할당, GC)와 `server/tools/load-test`의 봇입니다. 봇에 전투, 줍기, 한곳에 모이기를 더합니다.
- **클라이언트**: Unreal Insights(CPU와 메모리 기록), `stat unit`, 실제 휴대폰의 Development 빌드입니다. 봇 200명을 한 화면에 모아 잽니다.
- **비용**: 송신량을 월 GB와 VPS의 동접으로 바꿔 적습니다.
