# 키우기 기반 구현 목록

방치형 RPG 포트폴리오(`idle/`)를 만들기 위해 구현할 기반 시스템 목록입니다. 결제, 광고, 외부 SDK 연동은 범위에 넣지 않습니다.

## 현재 있는 것

- PuerTS 런타임 부트스트랩, Development/Release 전환, 스크립트 환경 재시작
- Excel → MessagePack 테이블 파이프라인(`tools/data-tool`, 스키마 시트의 검사 열로 참조·범위·Enum 검사), 공식 툴(`tools/formula-tool`, 입력과 결정적인 거듭제곱, `idle/balance`로 돌리는 N초 전투 미리보기)
- M1 뼈대: 로그인해서 서버의 플레이어 상태를 화면에 표시하는 전체 경로. 클라이언트(층 구조, 상태 신호, 예측과 확정, 재연결, UI 스택, 뷰 바인딩, 리소스 로더)에서 WebSocket을 거쳐 서버(SQLite, 세션 토큰, 한 번만 처리하는 커맨드)와 공용 규칙(`game-core`)까지 닿습니다.
- M2 1단계 전투: 로그인하면 메인 화면 뒤에서 영웅이 몬스터 웨이브(여럿이 함께, 56)를 스킬과 버프·디버프(57), 발사체(58), 소환수(59)로 자동으로 잡고, 웨이브 수가 차면 보스에 도전해 이기면 다음 스테이지로 넘어갑니다. 서버가 체크포인트부터 같은 시뮬레이션을 다시 돌려 확정하고(`BattleSettle`), 클라이언트는 같은 코드로 예측해 보여 줍니다. 게임 내용은 커맨드 열세 개(`StageSelect`, `BattleSettle`, `BossChallenge`, `ItemEquip`, `ItemUnequip`, `ItemEnhance`, `ItemMerge`, `StatUpgrade`, `SkillLearn`, `SkillEquip`, `SkillUnequip`, `SkillLevelUp`, `Rebirth`), 테이블 열한 개(`Items`, `Skills`, 효과의 `Effects`, 발사체의 `Projectiles`, 소환수의 `Summons`, `Monsters`, `Stages`, `Heroes`, `HeroLevels`, 소리의 `Sounds`, 규칙 상수의 `Constants`)와 Enum 정의(`Enums`), 공식 열일곱 개(피해, 소환수 능력치 셋, 효과의 지속 피해·회복·보호막·능력치 비율, 속성 상성, 강화 비용, 스킬 레벨 배율·피해 배율·레벨업 비용, 장비 강화의 비용과 스탯, 환생 포인트와 배율. `Big`으로 계산하고 거듭제곱과 조건식을 씀, 59–60, 67–69)입니다. 처치·클리어 보상은 보유량 `items`에 들어가고 메인 화면의 재화 바와 가방(`ScrollList` 그리드)에 보입니다(14). 경험치가 차면 전투 경계에서 영웅 레벨이 자동으로 오릅니다(51). 접속하지 않은 동안의 보상은 접속 뒤 첫 정산이 떠날 때 레벨의 사냥 기대치로 지급하고, 그 경험치로 바로 레벨을 올립니다(12, 24). 받은 오프라인 보상은 이벤트 버스(29)로 알려 보상 팝업에 보이고, 메인 화면 위쪽에 재화 바(굴러가는 수량)와 경험치 막대, 로그아웃 확인 팝업, 거절된 커맨드의 토스트, 서버를 기다리는 동안의 로딩 표시가 있습니다(38). 스테이지는 테이블의 해금 조건(선행 클리어, 영웅 레벨)을 채워야 고르거나 클리어 뒤 옮겨 갑니다(15). 메인 화면에는 전투 BGM이, 전투에는 효과음이 있고(44), 볼륨·뮤트와 초당 프레임은 메인의 설정 팝업에서 바꾸고 기기에 저장하며(31), 누를 때마다 버튼 소리가 납니다(44). 서버 시계는 왕복 지연을 보정하고 백그라운드에서 돌아오면 다시 맞춥니다(30). 클리어와 보스 보상으로 받은 장비(개별 인스턴스)를 장비 화면에서 입고 벗으면 영웅의 능력치에 더해지고, 입은 것보다 좋은 장비가 있으면 장비 버튼과 슬롯 탭에 알림 뱃지가 뜹니다(52, 41). 장비는 골드로 강화하고 같은 장비 셋을 다음 등급으로 합성합니다(68, 화면은 아직 없음). 30레벨부터 환생하면 레벨·스테이지·골드 강화·골드·경험치가 처음으로 돌아가고, 쌓은 포인트의 영구 배율이 능력치와 골드에 곱해집니다(69, 화면은 아직 없음).
- M3 개발 도구: 개발과 릴리즈를 클라이언트(번들의 빌드 모드 `BUILD_MODE`)와 서버(`SERVER_MODE`)에서 하나씩 정하고, 채널과 레벨이 있는 로그(46, 릴리즈는 debug를 버림), 처리되지 않은 오류의 재시작 팝업(6), 개발 모드 서버만 받는 치트(25), 개발 빌드의 디버그 오버레이(47)가 그것을 씁니다.
- M3 화면 대응: UI는 노치와 홈 인디케이터를 피하고, 세로 비율이 다른 기기에서도 1080×1920 이상의 영역에 놓이며, 전투 월드는 같은 가로 폭을 보입니다(40).
- M3 씬과 업데이트: 앱 흐름의 상태가 바뀔 때 전환 화면이 페이드로 가리고, 앞 상태가 놓은 에셋을 내린 뒤 걷습니다(5, 씬은 하나). Update 상태는 올린 번들의 매니페스트와 비교해 바뀐 TS 번들·테이블만 받고 검증한 뒤 슬롯을 바꿔 재시작합니다(35).
- M3 튜토리얼: 새 계정은 `TutorialSteps` 테이블의 스텝(대사, 비출 UI, 해금 조건과 같은 구조의 조건)을 차례로 마치고, 진행은 서버에 저장한 지금 스텝입니다(45).
- M3 로컬라이징: 화면의 문장은 모두 `Strings` 테이블의 키이고, 한국어(기본)와 영어 중 설정의 언어로 보이며, 설정 화면에서 바꾸면 열린 화면이 그 자리에서 다시 그려집니다(18).
- M3 테스트: 저장소 규칙의 동시성과 데이터 무결성(재연결 전후 두 연결의 동시 커맨드, 같은 요청 id, 한 번만 지급, 부분 쓰기, 저장 형식 1→최신)을 서버 테스트가 지키고, 클라이언트와 서버를 붙여야 보이는 흐름은 `integration/`이 실제 WebSocket 서버까지 붙여 봅니다. `npm run coverage`가 워크스페이스별 커버리지를 냅니다(48).

## 설계 원칙

- **공용(`shared/`)에는 클라이언트와 서버가 반드시 같아야 하는 것만 둡니다.** 통신 계약, 게임 규칙, 큰 수, 테이블이 여기에 해당합니다. 한쪽만 쓰는 것(저장 데이터 생성·마이그레이션, 시계, 표기)은 그쪽에서 구현합니다. 클라이언트와 서버는 서로를 의존하지 않으며, 둘을 함께 돌리는 테스트는 `integration/`에 둡니다.
- **클라이언트는 층으로 나눕니다.** `domain` → `application` → `adapters`·`presentation` → `composition.ts` → `unity` 순서로, 안쪽 층은 바깥을 모릅니다(`scripts/check-boundaries.mjs`가 검사). Unity와 서버는 안쪽이 정한 포트로만 닿으므로 앱 전체가 Node에서 돕니다. 전역 서비스 로케이터는 없습니다. `startApp`이 데이터를 읽고 서비스를 의존 순서대로 조립해 `App`(`data`, `state`, `events`, `clock`, `account`, `settings`, `progress`, `battle`, `ui`, `resources`)을 돌려주고, 필요한 곳에 인자로 넘깁니다.
- **게임 규칙은 `game-core`에 한 벌만 둡니다.** `(상태, 커맨드) → 새 상태`인 순수 함수로 만들고, 클라이언트는 결과를 바로 반영하며 서버는 같은 코드로 검증합니다. 클라이언트와 서버의 규칙이 어긋나지 않습니다.
- **재시작은 스크립트 환경을 통째로 새로 만듭니다.** 서비스마다 초기화 코드를 두지 않으므로 재시작 후 상태가 남는 버그가 생기지 않습니다.
- **클라이언트 상태는 슬라이스마다 신호 하나로 모읍니다.** 슬라이스마다 쓰는 컨텍스트는 하나이고, 화면은 필요한 신호만 따라가며 파생 값은 `computed`로 계산합니다. 알림 뱃지와 해금 표시도 상태에서 계산해 별도 등록 코드를 두지 않습니다.
- **규칙은 시간을 인자(`now`)로 받습니다.** 시계는 각 측이 가장자리에서 읽어 넘기므로 오프라인 보상과 일일 리셋을 단위 테스트로 검증할 수 있습니다.
- **프로토콜은 TS 타입 하나를 클라이언트와 서버가 같이 씁니다.** 스키마 코드 생성 단계가 없습니다.
- **C#은 얇게 유지합니다.** 부트스트랩과 엔진 브리지(파일, 기기 저장소, 리소스, UI, 전투 월드, WebSocket, 오디오, 화면 출력, 번들 받기)만 C#에 두고 게임 로직은 TS에 둡니다.

## 목록

### A. 런타임 — `client`

- [x] **1. 앱 흐름 상태 머신** `P0` — Boot → Update → Login → Main. 상태가 바뀔 때 그 상태가 연 UI와 리소스를 정리합니다. Update는 원격 번들을 확인하고(35), 씬 정리는 전환 화면이 가린 동안 합니다(5).
- [x] **2. 재시작** `P0` — C# 부트스트랩에 스크립트 환경을 새로 만드는 API(`RuntimeFacade.Restart`)를 두고 TS에서 호출합니다. 로그아웃, 처리되지 않은 오류의 재시작 팝업(6), 번들 갱신(35)이 씁니다.
- [x] **3. 서비스 조립** `P0` — 네트워크·UI·리소스·계정·진행 서비스의 생성 순서와 의존을 한 곳(`composition.ts`)에서 조립합니다. 전역 싱글톤 대신 주입합니다. 이후 서비스(오디오 등)도 여기에 더합니다.
- [x] **4. C# 브리지 정리** `P0` — 직접 작성한 `csharp.d.ts`를 PuerTS 생성 타입 선언으로 교체합니다. TS가 부르는 C# API는 좁은 파사드로 모읍니다.
- [x] **5. 씬 전환** `P2` — 씬은 `01_Init` 하나이고 상태마다 그 상태가 연 루트만 바꿉니다. 내용이 모두 TS가 실행 중에 만드는 `DontDestroyOnLoad` 루트라서 상태마다 씬을 두면 빈 씬과 상태 → 씬 표만 생기고, 씬은 번들 업데이트로 바뀌지 않으며, 상태마다 적어도 한 프레임의 씬 로드가 더 들기 때문입니다. 씬 로드가 하던 정리(`UnloadUnusedAssets`)는 `ResourceFacade.UnloadUnused`로 직접 합니다. 전환 화면(`presentation/transition.ts`, `UI/TransitionScreen`, C# `Fade`)은 앱 흐름이 상태를 떠나기 전에 0.25초 동안 다 가리고(`cover`), 들어간 상태의 화면이 열리면 놓은 에셋을 내린 뒤 걷으며(`reveal`), Boot·Update 동안에는 업데이트의 진행을 보입니다. 38의 로딩 표시(`network.waiting`)는 한 상태 안의 서버 대기만 맡습니다. 6의 재시작 팝업을 물을 때는 전환 화면을 먼저 걷어(`lift`) 가려진 채 누를 수 없는 팝업이 되지 않게 합니다.
- [x] **6. 전역 오류 처리** `P2` — 처리되지 않은 예외와 Promise 거부를 잡아 로그를 남기고 재시작 팝업을 띄웁니다. PuerTS에서 오류가 닿는 길은 셋입니다: 처리하지 않은 Promise 거부는 `puer`의 `unhandledRejection`, 타이머 콜백에서 던진 것은 C# `ScriptEnv.Tick`, UnityEvent 리스너에서 던진 것은 `UnityEvent.Invoke`로 빠져나갑니다. 셋 다 JS에서 잡히므로 C# 콜백 없이 `unity/uncaught.ts`가 부팅할 때 Promise 거부를 듣고 타이머 전역을 감싸며, 바인딩의 `listen()`이 리스너를 감쌉니다. 잡은 오류는 `app.crash`가 `crash` 채널에 남기고 확인 팝업(38)으로 재시작(2)을 묻습니다.

### B. 게임 코어 — `shared/game-core`, `shared/big-number`

- [x] **7. 플레이어 상태 모델** `P0` — 직렬화할 수 있는 단일 상태 객체입니다. 저장 형식 버전과 마이그레이션은 서버가 맡습니다.
- [x] **8. 커맨드 리듀서** `P0` — `(state, command, ctx) → state 또는 오류`. 오류는 값으로 돌려주고, `ctx`는 `now`와 게임 데이터입니다. 클라이언트와 서버가 함께 씁니다.
- [x] **9. 큰 수 타입** `P0` — 방치형의 수치 증가에 대응합니다. 연산, int64 테이블 값 변환, 표기(1.2K, 3.4aa, 클라이언트)를 포함합니다.
- [x] **10. 시간** `P0` — 일일 리셋, 경과 시간 상한, 타이머 표시(클라이언트). 시계는 각 측이 둡니다.
- [x] **11. 방치 전투 시뮬레이션** `P1` — 고정 틱(100 ms)과 시드 난수(mulberry32)로 결정적으로 동작하고 공격·피격·사망 이벤트를 냅니다. 경계마다 체크포인트를 남겨 서버가 `BattleSettle`로 확정하고, 클라이언트는 같은 코드를 돌려 보여 줍니다. 사냥 + 보스 도전과 스테이지 클리어까지 있고, 스킬은 피해 배율만 씁니다(마나, 속성, 효과 태그는 아직 쓰지 않고 해당 항목도 없습니다). 보상은 14, 오프라인은 12에서 했습니다.
