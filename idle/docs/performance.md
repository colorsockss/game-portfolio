# 성능 수치

같은 방법으로 다시 재서 바뀐 것과 비교하려고 남기는 수치입니다(백로그 70). 항목마다 잰 날, 커밋, 환경을 적습니다.

## 기준: M4 시작 전 (2026-10-22, 커밋 7de7e79)

환경: Apple M4 Max, Node 22.14.0, Unity 6000.6.0f1 에디터.

### 전투 규칙 (`npm run bench`)

`idle/balance/src/bench.ts`가 중반 상태(레벨 30, 3005 사냥)에서 정산을 돌립니다. 앞의 세 번은 JIT를 데우려고 버리고, 100번(접속 1시간은 20번) 잰 값입니다. 두 번 돌려 비슷한 쪽을 적었습니다.

| 경우 | 중앙값 ms | p95 ms |
| --- | ---: | ---: |
| 정산 60초 (클라이언트가 60초마다 보냄) | 0.06 | 0.27 |
| 정산 10분 (다시 돌리는 상한) | 0.21 | 0.46 |
| 오프라인 보상 12시간 (상한) | 0.25 | 0.34 |
| 접속 1시간 (60초마다 정산 60번) | 1.71 | 1.91 |

정산 계산만 보면 한 코어가 60초마다 정산하는 동접 약 100만 명을 감당합니다(60초 ÷ 0.06 ms). 저장(SQLite)과 통신은 빠진 값이라, 서버 비용은 70의 부하 테스트로 다시 잽니다.

### 클라이언트 (에디터 Play 모드)

조건: Development 번들, 메인 화면에서 전투 중(오프라인 보상 팝업을 닫은 뒤), Device Simulator(1170×2532 노치 기기). 에디터라서 플레이어 빌드와 다르며, 플레이어 빌드 수치는 70에서 잽니다.

| 항목 | 값 |
| --- | --- |
| draw calls / SetPass | 17 / 14 |
| 삼각형 / 정점 | 324 / 650 |
| 메인 스레드 CPU | 0.75 ms (프레임은 60 FPS 상한이라 16.6 ms) |
| GC 할당 / 프레임 (`GC Allocated In Frame`, 100프레임) | 중앙값 550 KB, 할당 1,993번 |
| 비교: Play 모드가 아닐 때 에디터만 | 중앙값 852 B, 할당 17번 |

게임이 프레임마다 약 0.5 MB를 할당합니다(60 FPS면 초당 약 32 MB). 그림이 단색 사각형뿐이라 렌더 비용은 작지만, GC는 PuerTS 브리지 호출과 문자열 만들기 쪽을 나눠 봐야 할 곳입니다(70).

## 56 이후: 웨이브 전투 (2026-10-22)

## 58 이후: 발사체 (2026-10-22)

### 경계 결정: 경계에는 날아가는 발사체가 없다

쏜 전투원이 쓰러지거나, 대상이 모두 쓰러지거나, 적이 물러나면 발사체가 사라지므로 경계(웨이브 클리어, 보스 종료, 부활)에는 날던 발사체가 없습니다. 고르지 않은 두 방법과 비교한 값입니다(1시간 연속 진행).

| 계정 | 경계 | 쏜 발사체 (적) | 사라짐 | 경계에서 잘림 | 그중 영웅을 향하던 적의 것 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 중반 (3005, 레벨 30) | 957 | 850 (1) | 281 | 113 | 0 |
| 초반 (3003, 레벨 8) | 788 | 950 (8) | 171 | 73 | 2 |

- 날아가는 발사체를 체크포인트에 저장하면: 쏜 몬스터, 그 공격력, 스킬, 대상, 치명, 남은 틱이 필요해 빈 목록(`projectiles: []`)만으로 저장마다 13바이트(324 → 337, +4%), 발사체 하나에 약 73바이트가 늘고 저장 형식 8과 마이그레이션이 생깁니다. 경계에서 잘리는 것은 거의 모두 대상이 이미 쓰러진 영웅의 것이라 저장해도 맞힐 것이 없고, 의미가 있는 것(영웅을 향하던 적의 것)은 초반 계정에서 시간당 2개입니다.
- 발사체가 모두 떨어질 때까지 경계를 미루면: 잘린 경계마다 평균 0.3초(최대 0.4초) 늦어지고, "웨이브는 끝났지만 경계가 아닌" 상태가 더해지며, 그 사이 영웅이 맞아 쓰러지면 이미 이긴 보스전을 지는 경우를 따로 정해야 합니다.
- 정산은 마지막 경계까지만 확정하므로 정산하는 순간에 날던 발사체(위 두 계정 모두 60초 정산 60번 중 1번)는 확정되지 않고, 다음 정산이 체크포인트부터 다시 돌려 한 번 맞힙니다. game-core 테스트가 7.3초마다 정산한 결과와 10분을 한 번에 정산한 결과가 같은지 봅니다.

### 저장 크기

체크포인트의 모양은 그대로라 중반 계정의 10분 정산 뒤 `player.battle`이 102바이트, 저장 데이터 전체가 324바이트로 같습니다. 발사체도 `nextId`를 받아 10분 뒤 `nextId`가 461 → 590(중반), 194 → 380(초반)이 되므로 MessagePack 정수가 1바이트 길어지는 때가 앞당겨집니다(초반 계정 303 → 304바이트).

## 59 이후: 소환수 (2026-10-22)

### 경계 결정: 영웅의 소환수는 체크포인트에 남는다

발사체(58)는 경계에서 모두 사라지게 했지만, 소환수는 웨이브보다 오래 살도록 만든 것이라 다르게 정했습니다. 1시간 연속 진행의 값입니다.

| 계정 | 경계 | 소환수가 없는 경계 | 하나 | 둘 | 평균 경계 간격 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 중반 (3005, 레벨 30) | 1,102 | 2 | 577 | 523 | 3.3초 |
| 초반 (새 계정, 레벨업 있음) | 863 | 19 | 253 | 591 | 4.2초 |
